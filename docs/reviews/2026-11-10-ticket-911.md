# Review: the wake tests no longer race the Hub's own poll (#911)

Change: `plugins/bundled/lib/helyx/hub/wake.ex` (`next_poll/0`), `plugins/bundled/test/test_helper.exs`, `plugins/bundled/test/helyx/hub/wake_timer_test.exs` (new). Base `2f744920`.

Cause, reproduced: a poll between the setup of a test and its own poll. With `Process.sleep(1_200)` after the setup, master failed both tests of the ticket: `wake_tasks_test.exs:42` got 2 Tasks for 4, and `wake_test.exs:74` got `run: 2`. An extra poll 30 ms before `poll_suspended` gave the `{:callback_failed, ..., {:error, :badarg}}` of the ticket: `:erlang.suspend_process/1` of a Task that the earlier poll started and that had ended, with its `:DOWN` not yet taken. With the change, both probes pass.

Fix: the test-only app env `:hub_poll_timer` of `helyx_plugins`; `false` (exact) arms no poll timer. `test_helper.exs` sets it, so after the start poll a Hub of the bundled tests polls only when a test sends `:wake_poll`. No Hub test waited for the timer (grep, and the Hub, transport, and coordinator tests pass, the slow ones too).

The `provider process crashed: :function_clause` line: not reproduced, with log capture off, in the full fast suite, the slow suite (`HELYX_SLOW=1 --only slow`), and the race probes. The ExUnit capture server of Elixir 1.19.5 (`capture_server.ex:233`, `log/2`) sends each log event to every active capture, so a failed async test shows the logs of other tests that ran at that time. The crash fits `Helyx.Provider.Fake` `echo` on a context with no user message (`Helyx.Message.text(nil)`); no test of the bundled project made it on this master. Not a part of the wake tests.

Bounds sensor: `0 candidate functions, 0 flagged, 0 without an answer`.

## Round 3 (reduced)

- Spec and failure path: the test still passed with a period of 10 s (within the 30 s wait), with a re-arm only after polls that found rows, and with a re-arm capped at two. A second finding on the one mechanism, so the mechanism changed: the test reads the timer itself. After one delivery by a timer poll it checks, with `Process.read_timer/1` in the Hub, that a timer is armed for at most 1,000 ms (or fired during the read), and waits for two empty timer polls to arm a new one. All three mutations now fail it; 9 of 9 runs passed.

## Small-fix round (reduced; a test file only)

- Spec: no random failure; `read_timer` gives the time left on the Hub's own timer, `false` or 0 to 1,000 ms, which load cannot raise. Found: a poll that keeps its timer but stops reading the store after an idle poll passes.
- Failure path: a period of 1 ms passes (no lower bound).
- Both are mutations of the code that no caller or input makes; the Hub code has no defect. The loop stops here (the round limit and the 45-minute limit of `/ship`); both are accepted as limits of the test, below.

## Accepted

The timer test proves that a timer poll runs and re-arms for three periods with at most 1,000 ms each. It does not prove a re-arm past a count larger than that, a period far below 1,000 ms, or that every later timer poll reads the store. The bundled tests other than `wake_timer_test.exs` never run the timer.
