Date: 2026-10-03. Base: `origin/master` at `800bd63` (after #380), rebased onto `7236b9c` (after #393) before round 3 and onto `5d07ee2` (after #390) before the commit. ## Invariant

The session is the one owner of the assistant message boundary. It closes the open assistant message at a `message_end` event (still sent by `Helyx.Provider.Loop`, with usage), at the first `tool_result` of a call of the open message (`Messages.close_for_result/2`: stop `:tool_use`, usage `%{}`), at a taken steer, at an abort or a failure when the open message holds a tool call (`Messages.close_with_calls/1`: stop `:tool_use`, before `abort_open_calls/1`), and at the terminal. At all of these but the terminal, each call of the closed message gets `tool_execution_start`. A partial message with text only of an aborted or failed turn stays out of the transcript, as on master. Claude Code and Codex send no `message_end`, and `Codex.Check.in_order?/3` is gone.

Accepted holes:

- Claude Code and Codex messages have no per-message usage (owner decision). The turn usage stays on `done`.
- A call of a closed message that still runs at the next close gets `aborted`, and its later result is dropped: the generic answer. No run showed it (#365).
- A Helyx `tool_request` does not close the message, so `tool_execution_start` of a harness Helyx call comes at its first result, as before.
- A Codex `item/completed` with no start reaches the session and is dropped.
- A failed harness turn with a tool call now leaves an assistant message, so `Transcript.resumable/3` resumes that program session. Whether the program resumes while its own call has no result is not tested: no real binaries here.
- The terminal close gives the calls of the open message `aborted` with no `tool_execution_start` (unchanged from master; the TUI folds a result with no start as a closed cell). Stated in the feature doc.

## Round 3 (full)

The coordinator found one defect after round 2: an abort (Esc) while the program's own tool runs lost the assistant message and its calls, because no close point had come yet. On master the harness providers lost it too (Claude Code closed only at the results line or a steer, Codex only at the first `item/completed`). The fix: `abort_turn` and `fail_turn` call `Messages.close_with_calls/1` before `abort_open_calls/1`. Tests: a new provider-process test (abort with a call in the open message keeps the message and aborts the call); the oversized-result test expects `[:user, :assistant, :tool_result]` again. Three plugin tests recorded the old loss and now record the new rule: the Claude Code abort test (`turn_test.exs`, it now waits for the tool call before the abort), the Codex abort test (`commands_test.exs`, the thread is resumed with only the new prompt), and the slow Codex test "a failed turn with an open command stops the provider process" (the next program resumes the thread; the precommit run after the reviews found it).
