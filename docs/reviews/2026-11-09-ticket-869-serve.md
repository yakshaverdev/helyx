# Review: ticket #869, `helyx serve` runs a Hub

Slice of #869 (`docs/features/hub.md`, decisions 15 and 16): `CodingAgent.Serve` starts Core, then `Helyx.Hub` (`core: Helyx.Core`, `default_owner: "owner"`, `server_token:` the closure of the token of the server file; the store `hub.db` in the data folder), then asks `Helyx.Hub.authority/1`, then starts the transport with `authority:` in place of `token:`. The stop runs the transport, the Hub, Core, the remove of the server file, and the release of the lock. A Hub that does not start, or does not answer the authority call, ends the start with one line and 1. The TUI client waits for an operation the deadline of the server under a Hub (`Ops.deadline/2`) and 15,000 ms: the slot margin of 5,000 ms and the `check` and `result` Hub calls, 5,000 ms each. `serve.md` and `tui-attach.md` follow.

Invariant: a server of `helyx serve` answers every connection through the authority of its Hub, the server token proves the default owner, and the start and the stop run their steps in the order Core, Hub, transport and transport, Hub, Core, with no server file left by a failed start.

Review: one round in fast mode (owner, 2026-11-09): the failure-path agent and the Codex review.

| # | Source | Finding | Resolution |
|---|---|---|---|
| 1 | Failure path (low) | A `hub.db` that is a regular file but not SQLite, a store of mode 0400, or a read-only data folder that holds a store ends the start with `could not start the Hub: :failed`: the line names no cause. | Fixed: `:failed` has the text "hub.db in the data folder cannot be opened as a store"; `serve_test.exs` checks it for a file that is not SQLite. |
| 2 | Codex (high, retracted in its own text) | A failed Hub start also sends an `EXIT` to the serve process; "no material failure is established". | No change: the `EXIT` stays in the mailbox of a serve process that then stops Core and returns. |

The failure-path probes passed for a FIFO, links, a hard link, a folder at `hub.db-wal`, a missing store in a read-only folder, a store of another version or another program, a store held by an OS process (`store_locked` after 5,017 ms), a stop of the VM during that wait, and a WAL left by a running server. Not reached: a crash between the Hub start and the authority call, a stop during the seed read of the Hub, and the margin of the TUI under a real slot wait.

A probe of the failure-path agent ran a server on the real data folder of the machine (`~/.helyx/sessions`), which made `hub.db` and `server.lock` there; both were born at the probe and held by no process, and they were removed.

## Accepted holes

- The Hub of `helyx serve` has no registered name and no supervisor: its end stops the server with 1, as the end of Core or of the transport does (`serve.md`, decision 10).
- The TUI waits as for a Hub also on a server with no Hub: a server that never answers gives `timeout` 10,000 ms later than before.
- A resume of a folder picks the newest session by its file time in seconds, then its id (hub.md, decision 7), not by the header time of Core: two sessions saved in one second are ordered by id. `attach_test.exs` gives its older file an older time.

## Assumptions

- The text of each start error of the store is fixed in `CodingAgent.Serve` (`hub_text/1`); any other error is the term of `Helyx.Reason.text/1`.
- The client cannot tell a server with a Hub, so its one wait covers both.
