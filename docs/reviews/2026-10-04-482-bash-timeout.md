# Review: bash timeout argument and default limit (#482)

Date: 2026-10-04. Base: `origin/master` 58ae388.

Invariant: the bash tool's `run/2`, the entry point of the model's tool call, takes an optional integer `timeout` of 1 to 600 seconds, checked there, default 120 s; at the limit `collect/4` stops waiting (the deadline is checked before each receive), the tool releases its own handles with `Helyx.Watchdog.Group.release/4` in `:cancel` mode, the release of an abort, in a Task beside the drain, and one deadline of `Group.max_cancel_ms/0` (15,500 ms) bounds the drain and the wait for that Task; then the result is an error with the output so far. Accepted holes: the wait for the watchdog marker and the wait to hold a handle stay unbounded; a process that left the command group and keeps stdout open holds the drain to its deadline and outlives the call, as before; the hands release the same handles again at delivery.

Checked before the build: `collect/3` existed as the ticket names it; the hands' abort calls `release(handles, :cancel, deadline)`; `Helyx.Watchdog.start/4` did not return the command group, so it now returns the handles it held.

## Simplify

- Round 1: the watchdog handle is held inside the `case` (no one-element `Enum.each`); `collect/4` returns `{:exit, ...}` or `{:timeout, ...}`, not two 3-tuples told apart by type; `render/2` has no fake status 0; the stop deadline is `Group.max_cancel_ms/0`, derived from the grace and the wait, not a copied 15,500. Skipped: a `Helyx.Watchdog.stop/2` helper (the drain needs the bash buffer and `keep_tail/1`); the `run_command/3` test seam (precedent: `Helyx.Watchdog.launcher/5`).
- Round 2: no change; `duration/1` keeps its ms clause so the model reads seconds.
- Round 3: no change.
