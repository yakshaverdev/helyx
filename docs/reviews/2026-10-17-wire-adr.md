# Review of ADR 0008 and the wire protocol doc (#656)

Docs only. `/ship` with the Markdown exemption: the change touches `AGENTS.md` and a feature doc, so each round ran the Codex adversarial review, and a spec agent checked every claim about the code against its file:line. The bounds sensor and the failure-path agent did not run: the diff has no `lib/` code. The input was the draft of the orchestrator with two earlier reviews (Codex and Fable); the projection of large blocks was replaced by `part` frames on purpose.

## Changes from the draft before round 1

- A slow subscriber closes the connection with `4408` (owner decision 5 of the ticket); the draft ended only the subscription.
- The abort deadline is 46,000 ms, not 23,000 ms: an abort during an idle close waits for the armed kill of the close, 5,000 ms (`turn_loop.ex:104-109`), and the cancel release and the delivery of the provider process run one after the other in the hands process (`hands.ex:225`, `:279`). The transport keeps a constant with a test against `Hands.State.release_ms/0` and `State.provider_close_ms/0`, so it reads no internal module at run time.
- `queue_dropped` and `steer_unconfirmed` lose their texts on the wire; the messages carry them.
- The error of `message_end` is `{kind: "aborted"}` or `{kind: "failed", text}`: a failure text can be the word "aborted".
- `compact` takes `text`; `sessions.live` `status` is `idle` or `running`; a ping every 15,000 ms ends a gone peer within 45,000 ms; the stdio form stays (the ticket asks for it).

## Round 3

Codex (2 findings), spec agent (4 defects, 2 wording). Reproduced by reading the code. Not fixed: round 3 is the last round, and the findings land a second and third time on the memory and credit mechanism, so the small-fix round does not apply. The docs stayed as round 3 reviewed them until the decisions below.

Open defects:

1. **The byte credit exemption cannot work.** An event over 16 MiB goes only when no event is unacked, but the session sends `queue_update` right after `queue_dropped` in the same handler (`steering.ex:137-140`, `:153-158`), so the subscription ends with `:slow` before the client can ack, and the texts that the abort gave back are lost.
2. **Request results that wait for the one encoder are not bounded.** 16 `history` or `subscribe` results of about 64 to 80 MiB each can wait together: about 1.3 GiB, not the 256 MiB of the memory row.
3. **A resumed group is not bounded by the 64 MiB file.** `Transcript.repair` adds a result for each call with none (`transcript.ex:74-91`), and the codec has no block limit (`codec.ex:163-168`): 400,000 small calls are about 21 MiB of file and over 135 MiB after the repair.
4. **"8 MiB of JSON encode" is false for text.** Text and thinking deltas count raw bytes (`records.ex:32`); only tool calls count encode bytes (`stream.ex:152-155`).
5. **A subscription counts as a request in flight** until its process ends, so 16 open subscriptions take all 16 request slots. A subscribe must stop counting at its reply.

Wording: O4 puts replayed events after the `subscribe` reply, but the reply carries them; #605 is merged on master (`aabf8050`), so the `start` deadline row and the ticket list of the ADR are stale after a rebase.

The mechanism question for the owner: the memory findings come from content that Core admits with no byte bound at the wire (user text, groups of a resumed file). Bounding the admission (for example a user text of at most 1 MiB, so a `queue_dropped` is at most 64 MiB, and a block limit at file read) would make the credits, the tail, and the memory row each one number, and remove the exemption.

## Decisions after round 3

The orchestrator decided the mechanism question for the owner:

1. Core bounds what it admits. #672: `prompt`, `steer`, `follow_up`, and `compact` refuse a text over 4 MiB with `{:error, :text_too_large}`, so a `queue_dropped` is at most 64 texts of 4 MiB. #673: the file codec refuses a message over 1,024 blocks at read, so one resumed group is bounded. A wire request cannot carry a longer text: its frame is at most 4 MiB, so the wire gets no new error code.
2. The byte credits and their exemption go, and the rule of round 1, one encoding in flight per connection, becomes one request result per connection; the credits count 16,384 events only. The byte bound is in the transport: a subscription process encodes each event when it takes it and adds the frame with no wait; an add to a queue that already holds more than 64 MiB closes the connection with `4408`.
3. A request takes the one encoder slot before it reads its data from Core.
4. A `subscribe` stops counting as a request in flight at its reply.
5. The false claim, O4, and the `start` row are fixed (open defect 4 and the wording items).
6. The memory row is one sum with a number for each term.

Assumptions of this worker:

- The writers add a frame with a call that the connection process answers at once, one add at a time. So "at most 64 MiB plus one frame" holds for the queue, and each writer holds at most one frame outside it.
- The largest frame is the `queue_dropped` of 64 texts of 4 MiB: 1,536 MiB of JSON with control characters, 256 MiB with plain text.
- Open: term (e) of the memory row, the events in the mailbox of a subscription process that it did not take yet, has a count (16,384 by the credits) and no byte number. The process takes each event with no wait, so the mailbox grows only while the encoding is slower than the session emits.

## Round 4

| Finding | Resolution |

| Wording: the mailbox of the subscriber, not of the session; no public unsubscribe in Core; `coding-agent.md` still cites #116; the ADR requests row has no subscribe rule; stale review-record lines; the 10,000 messages compared with events | fixed |

Open, on the memory and credit mechanism (the fourth round on it):

1. **A frame over 64 MiB is always followed by a close.** After its add the queue holds more than 64 MiB, and the next add closes with `4408`. `queue_update` follows `queue_dropped` in the same handler (`steering.ex:137-140`, `:153-158`), so a `queue_dropped` over 64 MiB of JSON always closes the connection, and its texts are lost: the ring skips an event over 4 MiB, and the snapshot holds no dropped texts. A `subscribe` reply over 64 MiB during a turn closes the same way, and the client gets the same snapshot at each reconnect while the turn runs. A suggested change: leave out the frame that the socket writes now from the check.
2. **Term (e), the mailbox of a subscription process, has no byte number** (Codex, spec agent). The credits bound the count of events, not their bytes: 64 different `queue_dropped` events of 256 MiB are 16 GiB in one mailbox under 16,384 events. The sum of the memory row is then not a bound of the connection.
3. **The encode needs heap that the sum does not count.** The spec agent measured `:json.encode` on OTP 28.5: 1 MiB of byte 0x01 gave 40 bytes of iodata for each input byte. With the worst escapes, term (b) is about 10 GiB for each subscription process, and the sum is about 190 GiB, not 30.2 GiB. The plain-text figure holds.
4. **The terms count content bytes, not heap.** Small decoded terms take about 13 times their JSON in a heap (100,000 empty maps: 300,001 bytes of JSON, 4,000,000 bytes of heap). Large texts are shared binaries, so term (b) counts 16 copies that are one. The doc does not say whether the queue holds the JSON or the base64 parts, which are 4/3 of it.
5. **The resumed group is not bounded by the file size** (Codex). A one-call file with a 60 MiB call name gives about 120 MiB after the repair, under the 1,024-block cap of #673.
