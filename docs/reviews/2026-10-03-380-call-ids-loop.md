# Review: the Loop uses the model call id as the request id (#380)

Date: 2026-10-03. Base: `origin/master` (`591fb5d`). Scope: `lib/helyx/provider/loop.ex`, its test, `test/helyx/session/loop_test.exs`, `test/support/interfaces.ex`, and `docs/features/one-provider-path.md`.

Target 2 of #380 only. Target 1 (remove `{:rejected_tool_call, ...}`) is not in this change: the session's rejection path carries only the integer reason of `Stream.check/1`, so a bad-JSON call cannot get its "tool call not run" result there without new code. The orchestrator asked to stop and report before any new code. Target 3 follows target 1.

## Invariant

`Helyx.Provider.Loop` sends each `tool_request` with the model's call id and keys the results by that id. Every result reaches the transcript once, in call order, under its real call id. A call id that repeats in one model message ends the provider process with `{:bad_stream_event, {:tool_call, call}}` in `call/3`, whether the session answered the first call or not. Entry points: the stream events `tool_call` and `rejected_tool_call`, `Loop.request/3` with `tool_result`, and the dispatch at `done`. Accepted (#369): a call id that repeats across two messages of one turn is checked only by the session's open-id check.
