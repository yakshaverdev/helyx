# Review: ticket #620, the provider_down steer test flake

Scope: `test/helyx/session/provider_process_test.exs` only. No `lib/` change.

## Cause

Found by reading; no reproduction of the failed run exists (its text was
not kept). The test "the provider_down in the wait after an abort ends its
open steer requests" received its own `:DOWN` of the provider process and
then asserted, with `:sys.get_state/1`, that the session held the process as
`:ending`. The session sets `:ending` only when it takes its own `:DOWN`
(`TurnLoop.monitor_down/1`). That `:DOWN` comes from the provider process,
the `:sys.get_state/1` message from the test: two senders, no order
(AGENTS.md, #592). The failure-path agent held the window open with
`:sys.suspend/1` on the session and saw `status: :ready` after the test's
`:DOWN`, so the old assertion fails in that window.

## Fix

- `stop_seen/2` stops the provider process, takes the test's `:DOWN`, and
  polls with `wait_until/1` until the session holds the process as
  `:ending`. Four tests use it: the flaky one and three siblings that act on
  the session (a prompt, a steer) after the same wait. Each suspends the
  hands first, so `:provider_down` cannot drop the process between polls.
- "an earlier turn's provider process that ends while the turn prepares"
  had the same class: the prepare Task's context, sent after the test's
  `:continue`, has no order with the session's `:DOWN`; a context first
  sends `{:turn, ...}` to the ended process. It now waits until the session
  no longer holds the old process as `:ready`; that state never comes back.
