# Review: a busy hands process at a provider start (#677)

Scope: the working tree against `HEAD` (`e9d86a5e`), the branch point. `origin/master` moved ahead during the work, so every review used `HEAD` as its base: a diff against `origin/master` showed the later commits of other tickets in reverse. Feature doc: `docs/features/session-lifecycle.md` ("Provider death", "The wait", "Deadlines", "Bounds").

## Reproduction

`test/helyx/session/hands_busy_test.exs`, run on the code before the fix with the hands suspended (`:sys.suspend/1`), as a stand-in for a release that blocks them: both tests failed at 5,000 ms. The client call `Session.prompt/2` exited with a timeout, and the session crashed with `exited in: GenServer.call(#PID<...>, {:start_provider, Helyx.Test.Provider, ...}, 5000) ** (EXIT) time out`, raised from `TurnLoop.connect/1`. The test with a real release that blocks the hands, in `hands_test.exs`, shows the order: the start answer comes after the result of the call whose release held the hands.

## Decision

The ticket gave two options. The fix is option 2, with a variation: `Hands.start_provider/3` is a cast that returns a ref, and the hands send `{:provider_start, ref, result}` to the session, as `run/3` sends its result. Option 1 (a longer call timeout) blocks the session: the client calls of 5,000 ms then time out, and the hands can be busy for many releases one after another (20 at most, 400,000 ms). `:gen_server.send_request/3` was not used: the session must match the answer before the catch-all clause of the wait cleanup in `TurnLoop.handle/2`, and its reply has an opaque shape. The provider process waits for `:start` from the session before `init/3`, because `{:provider_ready, pid}` comes from the process and the answer from the hands, and two senders have no order.

## Simplify

Four agents (reuse, simplification, efficiency, altitude).

| Finding | Resolution |
| ------- | ---------- |
| `start` is set to nil after the answer for no use | Fixed: the ref stays; `start` is an enforced key |
| `Summary.started/2` makes a fake `{:provider_down, nil, text}` | Fixed: `ended/2`, which the start error and `provider_down` both call |
| The comment of `connect/1` says that a start with no answer is reused | Fixed: removed; an idle session never has a start with no answer |
| The two refusal clauses of the conn repeat the turn/wait split of `provider_down/3` | Skipped: `provider_down/3` also settles the steer ledger and reconnects once in `preparing`, a change of behaviour |
| The summary start answer goes through `TurnLoop.handle/2`, not `server.ex` | Skipped: `server.ex` would pass the 400-line limit (404) |
| A separate struct for a pending start in `conn` | Skipped: larger change; every reader of `conn.pid` needs a ready or submitted process (checked by the round-1 and round-2 agents) |
| `handle_cast` builds `{result, state}` in an `if` | Skipped: minor |
| The `refuse` helper in two test modules | Skipped: the modules do not share a case module |

## Accepted holes

- The answer of the hands to a start has no timer of the session. The hands' release deadlines bound it: at most 20 releases of 20,000 ms (`session-lifecycle.md`, "Bounds").
