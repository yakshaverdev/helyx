# Review: bound the memory and the work of one frame decode (#787)

Scope: the working tree against the branch base `ca4f78bf`. Files: `plugins/bundled/lib/helyx/transport/web_socket/frame.ex`, `plugins/bundled/test/helyx/transport/web_socket_test.exs`, `plugins/bundled/test/helyx/transport/web_socket/frame_test.exs` (new), `docs/features/wire-protocol.md`.

Invariant: the decode of one inbound frame, one text or joined from parts, stops at the first value over 65,536 counted values (each array, object, scalar, and object key counts one; an array or an object counts at its start, with its key when it is the value of a key) and at the first integer token over 1,024 characters before it converts it. A frame over either bound closes with `4400`, the answer of bad JSON.

## Decision

- `Frame.json/1` passes `JSON.decode/3` decoders for arrays, objects, and integers. The accumulator carries the count through the whole text, and a throw ends the decode. No pre-scan of the text: a prompt text can hold any number of commas and brackets.
- The bound is a value count and an integer length, not a word count of the decoded value. The count also bounds the depth. Floats get no bound: their decode is linear (2 to 4 ms for 1,000,000 digits).
- The `rescue SystemLimitError` of #782 is gone: 1,024 characters are far under the BEAM limit.
- The bound is in the "Bounds" table, not in the schema, so the protocol number stays 3, as for the row of #782.
- The "transport feature doc" of the ticket is `docs/features/wire-protocol.md`: the moduledoc of `Helyx.Transport.WebSocket` links it, and no other feature doc covers the transport.

## Measurement (author)

OTP 28, Elixir 1.19.5, the dev machine.

- 1 MiB prompt frame: 1,266 µs against 1,195 µs with the old decode (median of 21 runs, +71 µs).
- 25 MiB of `[`: refused after 3 ms. Old: about 1.1 GB (review of #782, extrapolated).
- 20 integers of 1,262,592 digits: refused after 1 ms. Old: 232 ms for one of them.
- 25 MiB frames that pass: a `\n` string 266 ms, 25,000 integers of 1,024 digits 146 ms, spaces 38 ms.
- Peak heap, the smallest `max_heap_size` with which the decode ends: 48.4 MiB for 25 MiB of 1,024-digit integers, 21.6 MiB for 64-byte strings at the value bound, 10.4 MiB for nesting, floats, and objects.
- The new tests fail on the old `frame.ex`: the two socket tests get a frame where they expect `4400`, and the two heap tests are killed at the heap bound (then 16 MiB).

## Simplify

One agent. Applied: `mix format` of `frame_test.exs`. Rejected: a shared part helper with `web_socket_test.exs` (that helper writes to a socket, and `Frame.encode/1` cannot cut a text that is not JSON); a module attribute for the decoders (a local capture cannot sit in one).

## Accepted holes

- The key-count test passes on the round-1 code too: a frame has the same count at its end in both, and only the point where the decode stops differs. A trace or a heap bound that tells the two apart is fragile. The code reading and the two probes cover it.
- No test asserts the decode time. The work bound is the value count and the integer length; the times are measurements.
- The decode of a frame that passes the bounds still takes its peak heap in the connection process, which has no `max_heap_size`.

## Open

- **The peak heap of one decode has no stated bound.** The largest peak found is about 69 MiB (an object of 30,200 pairs of 64-byte keys and 800-digit integers). Integers and short strings are on the heap, so the peak depends on the text, not only on the value count. A fix bounds the decoded size itself, for example a count of the words of each decoded value in the same accumulator, or a lower integer length. That is a code change for a new round, past the limit of this ticket.
