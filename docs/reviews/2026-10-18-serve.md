## Decisions of the orchestrator on the open defects of round 4

1. The owner of the lock owns the file: every operation on `server.json` runs where the `flock` is held, by the holder.
2. The token stays in a closure until the one call that writes it; a test refutes every printed form of it in the outputs of a start that fails during the write.
3. The launcher handles every signal that ends a shell by default and that it can catch.
4. The launcher sends SIGTERM again until the VM ends, with a stated bound.
5. `run/1` refuses a second `run/1` in a VM (the smaller of two options).
6. The tests make the data folder with mode 0700.
7. The docs match the code.

Decision 1 is possible with the existing lock, with no second mechanism. After its answer, the perl process that holds the `flock` reads file commands on its stdin: `w` writes a file through `<path>.tmp`, made with `O_EXCL|O_NOFOLLOW` and mode 0600, and a rename; `r` removes a file. `Helyx.Session.Lock.write_file/3` and `remove_file/2` send them. Perl holds the `flock` for its whole life, so a server whose perl ended can do no operation on the file: its command finds a closed port. A session release still sends `x`, which ends perl as before (`docs/features/session-lock.md`, decision 6). The private folder `.server.tmp` is gone. A probe before the round showed:
- the write gives mode 0600;
- a link at the temporary path is removed, not followed, and its target is not made;
- a write over a folder gives `Is a directory`;
- after a `kill -9` of perl, a write and a remove give `the lock has ended`, and no file is made.

Before the round, the branch was rebased on `origin/master` at `3c289be0`; `c72ac81c` is now `6ba59ed3`. `/ship` changed on master during this work (#780): simplify is one agent, standards runs in the first round only, and a rerun round is reduced unless the two-findings rule applies.
