# Review: #821, the wire connection reads while it writes

Base: `60853668` (merge base with master). The change was uncommitted during the review.

## The cause, traced before the fix

A throwaway test sampled the client connection process and the Bandit process of the server every 500 ms during a steer of 4 MiB of `\u0001` and then a follow-up, with the write in the connection process. From 1,525 ms to 11,055 ms both were in `prim_inet:send/4`: the client in `Connection.send_frame/2` with `send_pend` 1,338,500, the server in `Bandit.WebSocket...send_frame/3` with `send_pend` 345,204, and the receive counts of both did not move. At 11,110 ms the follow-up got `no connection to the server` and the connection ended with `{:shutdown, {:closed, nil}}`. The acceptance test failed the same way before the fix, after 31.3 s. Confirmed: neither side reads while it writes.

## Precommit of round 2 (first stop)

The first run (on the precommit host, during round 2) failed in the acceptance test: under the load of the whole suite, the follow-up got `{:reject, "no answer from the server"}`. The server sends the reply after the events of the steer, about 24 MiB of JSON each, and the deadline of the request (slice 2) counts them. The test now takes `:ok` or that timeout for the follow-up and still waits for both turns on the open connection; tui-attach.md has the accepted hole. A test change with no review round.

The second run failed in the same test: the connection ended with `{:shutdown, {:closed, nil}}` while the test waited for the events of the turns. Probes on the dev machine, the client connection suspended after the steer:

- A steer of 4 MiB of `\u0001`, and a pause of 1,000 ms or 3,000 ms: `{:shutdown, {:closed, 4408}}`. The events of its turn, each about 24 MiB of JSON, pass the outbound queue of the server, 64 MiB (`Helyx.Transport.WebSocket.Outbound`), when the client reads them late. This is the bound of the server for a slow client; it holds with the write in the connection process too.
- The same with a 4 MiB plain text and a pause of 3,000 ms: the connection stays open.
- A steer and a follow-up with a pause of 1,000 ms: the writer failed with `:closed` at 2,908 ms and ended the connection before it read the close frame (round 2, finding 3), so the code shows as nil.

So on a loaded machine the acceptance test of #821 cannot hold: the server closes the slow client, and the race of finding 3 makes that close look like the old deadlock. Not committed at the first stop: precommit did not pass, and the work is past the 45 minutes of `/ship`. Open: a decision on the text bound of `Helyx.TUI.Link` (4 MiB of text in its worst JSON form) against the outbound queue of the server (64 MiB); the fix of finding 3 (the writer gives its failure to the connection as a message, so a close frame that came first is read first); then an acceptance test that tells a 4408 from a deadlock.

## Decision of the orchestrator (2026-10-20) and the fix

1. The acceptance is a plain 4 MiB text at the bound, then a follow-up, and the connection stays open. The worst JSON form meets the slow-client policy of the server (64 MiB, 4408): an accepted hole, with a test that the client ends with 4408.
2. The writer reports a failed send to the connection as a message, and the connection reads what the socket holds before it ends.
3. The writer queue is bounded: 16 request frames, acks coalesced to the latest seq, one pong.
4. One full round past the limits of `/ship` (simplify, spec, failure path, Codex), with the invariant "the connection never waits on a write, every frame waits in a bounded queue, and a close by the server reaches the owner with its code".

Probes before the fix (throwaway scripts on the dev machine, macOS):

- A peer sends `HELLO` and closes with unread bytes of the client (a reset); a writer process sends until it fails. Then `gen_tcp:recv/3` gave `{:error, :closed}` with `exit_on_close` true and false, and with `inet_backend: :socket`; the `:socket` module gave `{:ok, "HELLO"}` and then `{:error, :econnreset}`. With a reset and no failed send, `gen_tcp` read `HELLO`. So `gen_tcp` drops the bytes at a failed send, and the kernel keeps them.
- `:socket.open/2` on the descriptor of a `gen_tcp` socket (`:inet.getfd/1`) needs the domain on this machine; the peer sees the close only when both descriptors are closed.

The fix: `Helyx.TUI.Wire.Writer` (new, `@moduledoc false`) sends on its own `:socket` descriptor of the socket, answers each batch, and tells the connection of a failed send and ends; `Helyx.TUI.Wire.Reader.held/3` reads the held bytes, at most the receive buffer, until a close frame; the connection counts the unwritten request frames, batches a pong and the acks, and kills the writer in `terminate/2`; `Wire.send_frame/3` became `Wire.masked/2`. Mutants of the drain, of the count of unwritten frames, and of the batch each failed their test (`connection_test.exs`).

The plain-text acceptance test also passed with the code of the base on this machine, with and without a pause of the client before the follow-up: it does not show the reads during a write. The tests of the connection with a fake server that does not read while it writes show them.
