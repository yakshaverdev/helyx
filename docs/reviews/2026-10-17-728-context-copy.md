Date: 2026-10-17. Base: `origin/master` at `e7a3d6f6` in rounds 1 and 2; the commit is rebased on `6b3ababb` (#721 and #730: Memory sync and TUI tests, not the prepare path). ## Invariant

The context that reaches the provider (`:turn` and `:context` requests) is always the messages that the plugins saw, also when the transcript grows during the build. When the plugins kept the message list, the reply of the prepare Task holds `:base`, and the session puts back the list that it stored in `Turn.prepare` (`{ref, pid, messages}`). The session takes a reply only with the ref of its current Task (round 3). The kill bound of the Task, its monitor and `:DOWN` path, the kills at the stop and at the turn end, and the check of `Helyx.Session.Stream.prepare/4` (in the Task, before the swap) do not change. Accepted holes: the Task start and the provider request still copy the whole transcript (the context request of `Helyx.Provider.Loop`, ADR 0002, is out of scope); after a summary, and in a `{:summarize, plan}` reply, the reply still holds its messages; no test checks the size of the reply (the send trace in the devlog does).

## Round 3 (full): a merge-gate finding

The orchestrator rebased the commit on `3bc3aa58`, then on `db47a031` (#712, #667, #695). The resolved conflict in `prepare.ex` was a comment (`deadline_ms.prepare` of #712). The Codex merge gate found one defect:

> [medium] Match the Task reference before restoring :base (lib/helyx/session/server/prepare.ex:85-89). The reply handler checks the turn id but ignores the Task reference. The new :base path can therefore combine an old reply with the current Task's messages.

Its reproduction: a turn waits in a context build; the session is suspended; the provider sends `done`, then `turn_start` with the same id, a text, `message_end`, and a context request; the old build replies; the session resumes. The old reply then cleared `prepare` of the new build and got its messages. The new test (`provider_process_test.exs:1094`, "a late reply of an ended turn's build is dropped by a new turn with the same id") failed on `521a00f9` with `left: nil`, `right: #PID<...>` at `assert prepare_task(pid) == new`.

Fix: `Turn.prepare` is `{ref, pid, messages}`, and the reply is `{ref, {:prepared, result}}`. `TurnLoop.handle/2` takes a reply only when its ref is the ref in `Turn.prepare`. The turn id left the reply, because the ref names the Task. The `:DOWN` path still matches the pid, and the kills use the pid. `Helyx.Test.SessionCase.mailbox/1` takes a pid. The test fails again when the clause ignores the ref. This closes the reused turn id hole of round 1.

Simplify (4 agents). Applied: the turn id out of the reply (simplification and altitude); `SessionCase.mailbox/1` in place of a copy in the test (reuse). Not taken: the 2-line `:DOWN` clause (`{_, pid, _}` is over the line length of the formatter; the file has 390 lines); `{%Task{}, messages}` in place of `{ref, pid, messages}` (judgement call). Efficiency: no finding.
