# Review: the 17th-request busy test fails at random (#769)

Scope: the working tree against the branch base `bbc1f532` (`origin/master` moved to `9787a062` with #772 before round 1, so every round used the base sha). One test file: `plugins/bundled/test/helyx/transport/web_socket_subscribe_test.exs`.

Invariant: the test of the 17th request in flight opens its own connection, so no worker of an earlier request holds a place in flight, and a failure prints the frame of each request. Accepted holes: each of the 16 calls waits while the session is suspended, under its 5,000 ms call timeout (a window of 16 frame sends and one `busy` round trip); the busy limit is out of scope.

## Measurement

The assertion got a failure message with the replies. Runs on the local machine with the plain test runner: loops of the whole `plugins/bundled` suite, in parallel with `mix test <file> --repeat-until-failure N`. No load generator.

- Before the fix, 5 failures (2 of the file repeats, 3 in the suite loops). Each run with the print shows request `"16"` answered `busy`. `Client.request(socket, "17", ...)` skipped that frame, so the original test read `{:error, :timeout}` from `recv` as its 16th reply. This matches "15 of the 16 replies were ok" in the ticket.
- Cause: the setup sends `start` on the same socket. A worker counts in flight "from the `req` to the end of its worker" (`docs/features/wire-protocol.md`, bounds row "requests in flight per connection"). `replied/3` in `connection.ex` keeps a worker in `flight`; only its `:EXIT` removes it. Under load the `:EXIT` of the `start` worker reaches the connection after the client's frame 16. The code keeps the contract; the test assumed that a reply frees the place.
- The cause is not a deadline, so the 5,000 ms window stays as an accepted hole.
- After the fix: 300 of 300 repeats of the file passed under the same load.
- The failure on the precommit host was not seen with the print; the local symptom is the same (15 `ok`, then nothing).
