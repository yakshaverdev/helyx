# Review: retry temporary API errors before the stream starts (#479)

Date: 2026-10-04. Base: `origin/master` 58ae388.

Invariant: `Helyx.Provider.OpenAI.stream/4` (through the Go and Zen plugins and `Helyx.Provider.Loop`) retries a request whose `Req.post/1` result is a 408, 409, 429, or 5xx response or a `Req.TransportError`, at most 3 times. Each wait is the first valid `retry-after-ms`, else the first valid `retry-after` in whole seconds or as an HTTP date, else `min(0.5 * 2^n, 8)` s less up to 25% jitter. A server delay over 60 s fails at once with `{:retry_after_over_limit, status, delay_ms}` and the body not read. Each retried response has its async body cancelled. Nothing is retried once a 200 body starts: a mid-stream error still raises into `task_exit`. The wait runs in the model Task, so an interrupt kills it. The loop is the only retry layer: the request sets `retry: false` and `http_errors: :return` over Req's `:default_options`. A delay value longer than 12 bytes is skipped, so a delay in an error term stays small. Accepted holes: a transport error is retried for every reason, also a permanent one such as a TLS failure or `nxdomain`; a wait for the response headers can take 120 s on each of the 4 attempts before the user aborts; a fractional `retry-after-ms` and a past HTTP date count as absent; the `:openai_req_options` test seam can override any Req option; `Req.Utils.parse_http_date/1` is internal to Req.

Checked before the build: Req 0.7.4 `retry/1` (`deps/req/lib/req/steps.ex`): `:transient` covers 408, 429, 500, 502, 503, 504 and the transport reasons `:timeout`, `:econnrefused`, `:closed`; it reads `retry-after` only on a 429 or 503 and never `retry-after-ms`; `do_retry/3` does not cancel the async body of the response it retries; a `retry` function sees the retry count only through the private `:req_retry_count`. `Req.Response.get_retry_after/1` raises on a value that is neither an integer nor an HTTP date. An interrupt runs `Task.shutdown(task, :brutal_kill)` on the model Task (`Helyx.Provider.Loop`), so a `Process.sleep/1` in it ends at once.

## Simplify

- Simplification: `fail_or_retry/3` matched a tuple of result and delay with a guard on the retry count. Fixed: `delay/2` returns `:none` at `@max_retries`, and the case matches the delay only.
- Reuse, altitude: the code comment gave wrong reasons against Req's `retry`. Fixed: the reasons are the ones above, and they moved to the bounds table of `docs/features/coding-agent.md`.
- Reuse: the `ok/0` test helper copied the 200 reply of `stub/1`. Fixed: both call `reply/2`.
- Simplification: the backoff formula was in the moduledoc and in a comment. Fixed: the comment is gone.
- Simplification: `attempts/0` reads the mailbox. Kept: one count per test reads more clearly than a pair of `assert_received` and `refute_received`.
- Efficiency: two tests wait one real backoff (about 0.4 to 0.5 s each). Kept: under the 1 s limit for a fast test, and a test-only backoff knob would add config to the code.
