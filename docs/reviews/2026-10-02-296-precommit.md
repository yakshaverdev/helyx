# Review: #296, precommit races and process starts

Scope: the working tree against `origin/master` at `511d68b`. The branch
was updated from `58471ac` before the review. The update applied without
conflicts. The measurements in the devlog identify their original base.

Invariant: preparation finishes before each project's parallel checks.
Updated runners serialize Hex registry writes. Checks reuse prepared
builds and PLTs. The fake Codex keeps its shell PID and signal behavior.
Test synchronization keeps the process-death and error assertions.
Failed-start error text has the existing 2,000-byte cap and initialization
kill. No production timeout, grace, or cap changes.

Accepted limits:

- The source and checkout location must stay stable during a run.
  External edits, directory replacement, and retargeting checkout aliases
  are unsupported. A lock coordinates runners, not other filesystem writers.
- Old runners and standalone Hex commands do not take the new lock.
- Locks assume each project uses its normal build directory. A custom
  shared `MIX_BUILD_PATH` or `MIX_BUILD_ROOT` was already unsafe on master;
  this change does not add support for it.
- `Mix.Sync.Lock` is an internal Mix API. Recheck the runner probe when
  upgrading Mix.
- Existing test weaknesses listed in #296 stay unchanged.
- SIGKILL of the runner can leave child Mix VMs alive. This reproduces on
  `origin/master` too. The new locks coordinate live runners; they do not
  solve the existing interrupted-run cleanup defect. After a forced kill,
  remaining child VMs must finish before another build uses the checkout.
- The three battery runs exceeded 25 seconds. The user accepted their
  times and requested a commit and PR. The PR must state this result.
- Host measurements used a shared host. They are observations, not an
  isolated benchmark or proof of each change's contribution.

## Round 3 (full)

The second lock finding required a review of the mechanism. The locks are
needed: one owns a checkout's build use, and one serializes shared Hex
writes. The checkout is a filesystem object, not a path string. Its key
now uses the device and inode from `File.stat!/1`, so aliases identify the
same object. The key change is four lines added and one removed in one
code file after the simplify pass. The two-findings rule requires a full round.

Round base: `e466d6bb21982710724f1e8c1d0551c59ac292a8` (stash snapshot).
Simplify reran all four reviewers. It removed `minor_device` from the key:
for directories it is `st_rdev`, which is zero; `major_device` holds
`st_dev`. It added a comment explaining the path-alias reason. The alias
probe passed before and after that edit.

The coordinator did not accept the mutable-alias case as a defect within
this change's supported operation. It requires another writer to replace
the active checkout location during a run. The runner cannot guarantee a
consistent source/build snapshot under external source or path mutation.
Resolving a path once also cannot prevent later replacement of that
physical directory. Keep the scope to coordinating live runners on a
stable checkout; `AGENTS.md` now states that constraint. The review's
inference is retained here, not reported as an approval.

Round 3 reproduced no defect within that scope. No code changed after
review. The loop ends after three full rounds. Remaining limits are stated
above and in the PR. All raw review output is in `.scratch/296/ship-*`.
