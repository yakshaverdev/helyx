`Helyx.Session.start/2`, `Helyx.Session.Lock` (its mkdir removed), the
bounds row "sessions folder mode" and the rule "The sessions folder." in

## Round 3 (full: two findings on one mechanism)

Fix: the sessions folder is the path text through `Path.absname/1` and
`Path.expand/1` (a leading `~` stays a name); `mkdir_p` of its parent, one
`File.mkdir` decides a new folder, the chmod goes only to a folder that this
mkdir made; the project folder uses the raw `dir`. Tests: a new folder for
`""`, `/`, `/.`, `/new/..`; an existing folder for `sessions`,
`sessions/new/..`, `gone/../sessions`. The spec reviewer probed relative
paths, `~`, `//`, a read-only parent, symlinks, and a resume, and found no
break.

Open (reproduced, not fixed):

1. Failure-path: the sessions folder is removed after the chmod and before
   the `mkdir_p` of the project folder. The `mkdir_p` makes it again at the
   umask mode, the start succeeds, and later starts keep that mode.
   Reproduced 3 of 3 with `:file_server_2` suspended and `:prim_file.del_dir`.
   It needs another actor that removes the folder during a start.
2. Failure-path: the caller is killed between the `File.mkdir` and the chmod
   (a VM kill during the first start, or the end of the TUI while a linked
   `/new` Task runs). The folder stays at the umask mode, and every later start
   sees it as one that exists. Reproduced 3 of 3. The row states the window,
   not that the mode stays after it.
3. Codex: another process with write access to the parent swaps the new
   folder for a symbolic link to an existing folder between the mkdir and the
   chmod; `File.chmod/2` follows the link and closes the existing folder.
   Not reproduced on disk (Codex ran read-only); the control flow is as stated.
   Such a process can rename the sessions folder anyway.

The fix that closes all three makes the folder with its mode in one call,
which the BEAM has no API for (`file:make_dir/1` takes no mode). Codex names
perl, which Core needs already for the lock: `mkdir($path, 0700)` applies the
mode in the mkdir. That adds a port spawn to a start that makes a folder, and
is a change of the mechanism, so it is for the owner.

Other round-3 notes, not fixed (judgement, after the limit): the comment in
`Lock.take/1` says that `mkdir/2` made the folder, which is not so for a
resume, whose folder exists because a file was picked; the rmdir branch of
`restrict/2` has no test; `mode/1` is the third copy of the same test helper.
