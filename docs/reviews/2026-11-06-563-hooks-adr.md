## Round 3 (reduced): Codex and spec

Invariants: as round 2.

Findings, **open**: round 3 is the last round, and the fixes below do not meet the small-fix conditions of `/ship` (the approval id and the record are second findings on mechanisms that round 2 patched). They are not in the committed ADR. The committed ADR is the text that round 3 reviewed.

1. **Codex: approval id history.** Detecting a repeat `approval_id` in a turn needs the ids of ended requests, a buffer that the 8/16 bound does not cover. Proposed mechanism fix: check only the pending ids (running and waiting), as `ToolQueue.request/5` checks only open ids (`tool_queue.ex:35-46`, "no real provider reuses an id", #369); bound `approval_id` at 1 to 256 bytes, as a call id (`lib/helyx/session/input.ex:67`).
2. **Codex: record order.** A Codex call is in the partial assistant message until its first result (`lib/helyx/session/server/records.ex:32-40,56-57,190-194`), so a saved `hook` entry can name a call that the file does not hold after a crash; the claim that the transcript supplies the arguments fails on this path. Proposed mechanism fix: the entry holds the tool name and the JSON of the arguments cut at a byte bound, so it stands alone; this also meets #503's "size bound of its arguments" as written.
3. **Spec: abort.** A chain cut by an abort: the ADR does not say which earlier answers are recorded. Proposed fix: one entry for each hook answer, written when the session gets it, so a cut chain loses nothing already answered.
4. **Spec: the end of a hook Task.** The ADR does not say who tells the session that a hook Task ended. Proposed fix: the session monitors the Task that asks and ends its asks at its `:DOWN`.
5. **Spec: refusal.** After an unconfirmed release, the ADR does not say that the hands refuse a hook Task start too. Proposed fix: they do, and the chain then fails by the rule of its point (§5).
6. **Spec: a false sentence.** §3 says the concurrency of calls bounds the hooks that run at once; with the harness set and `before_settle`, up to 17 hook Tasks run at once. Proposed fix: state that bound.
7. Wording: a request that Core denies at once (past 8/16, a repeat for one call, no open call) gets no entry; a waiting harness chain can wait the sum of the limits of the hooks ahead of it.

## Round 4 (reduced, asked for by the caller after round 3): Codex and spec

Base: `13acb757` (the round-3 commit after a rebase on `origin/master`). The six open findings of round 3 were fixed as proposed above:

1. A repeated `approval_id` is checked only against the pending requests, read from the set of harness chains that the turn keeps anyway; no list of ended ids. `approval_id` is 1 to 256 bytes. Derived, not stored.
2. The first `hook` entry that a chain on a call writes holds the tool name and the JSON of the arguments, cut at 4,096 bytes with a cut flag. A stored copy: the transcript cannot supply a call that a crash kept out of the file, so it cannot be derived.
3. Each hook answer is one entry, written when the session gets it; an abort keeps the answers before it. The outcome of a chain is not stored.
4. The session monitors the hook Task that asks, and ends its open asks at its `:DOWN`.
5. The hands refuse hook starts after an unconfirmed release; a refused start is a failed hook, handled by the rule of its point.
6. §3 states at most 17 hook Tasks at once.

- Codex: approve, no material findings.
- Spec, **open** (the caller allowed one round, so these are not in the committed ADR; the commit holds the text that this round reviewed):
  1. §4 and ticket 3 place the check of the pending `approval_id` in `Helyx.Session.Stream.check/1`, which holds no state (`lib/helyx/session/stream.ex:117-173`). Only the byte bound belongs there; the pending check belongs in the session, against the harness set, as `ToolQueue.request/5` returns `:open` (`tool_queue.ex:35-46`). Proposed fix: say so in §4 and ticket 3.
  2. Context still says "the call of an approval request is in the transcript before the request comes". False, as §6 now says: a Codex call stays in `partial` until its first result closes the message (`records.ex:56-57,197-199`). Proposed fix: say the call is in the open assistant message, not yet in the transcript or the file.
  3. §6 says the outcome of a chain follows from its entries ("the first deny, or an allow from each hook"). The file does not hold how many hooks the chain had, so a crash after hook 1 of 2 allowed looks like a full allow; and a failed hook denies by §5 but its entry is a failure, not a deny. Proposed fix: the first entry of a chain holds the count of hooks on its point, and a failure at `before_tool` counts as a deny in the derivation. A closing outcome entry is the other choice; it is stored state with its own crash window, so the count is preferred.
  - Wording: the time of one hook and of a waiting chain leave out the release deadline of ADR 0004; the reason cut is "at a character boundary" in the table only; an ask from a process that a hook spawned with the copied context is not covered by the monitor of the hook Task.

## Round 5 (reduced, after the owner decision of 2026-11-06 on the outcome): Codex and spec

Base: the round-4 commit after a rebase on `origin/master`. Applied: the owner rule (record no outcome; a resume reads no decision from the `hook` entries; a chain with no closing answer counts as not run), with the text that derived an outcome removed; the pending `approval_id` check moved to the session against the harness set, with only the shape and the 1 to 256 bytes in `Helyx.Session.Stream.check/1`, in §4 and ticket 3; the false Context sentence replaced; the release deadline of ADR 0004 in the time bounds; every reason cut at a character boundary; an ask from any process but a hook Task refused.

- Codex: one finding, medium. Same as spec 1.
- Spec, **open** (the caller allowed one round; the commit holds the text that this round reviewed):
  1. §6 says a Helyx call with no result gets the interrupted result of `Helyx.Session.Transcript.repair/1` at the resume. That holds only for a call already in the file (`transcript.ex:71-78`). A Helyx tool request of a harness provider (Codex `item/tool/call`, Claude Code MCP) runs while its assistant message is still open (`records.ex:56-57`), so a crash during its chain, or during an `after_tool` hook after the tool ran, leaves the call in neither the file nor the repaired transcript: it is gone, not denied, and the model gets no warning about effects that ran. The interrupted result also says the call "may have run" (`transcript.ex:10-12`), which is not a deny. Proposed fix: state the guarantee for stored calls only, and state as an accepted hole that a call still in the open assistant message is absent after a crash; no stored outcome is needed for that.
  2. A hook Task has the call's context, so it can call `Helyx.Tool.ask/1`, which sends `{:ask, call_id, ...}` with no caller check (`tool.ex:267-273`); the session takes it for any process while the call id runs (`asks.ex:20-27`). That ask has no hook-Task monitor and stays open after the hook is killed at its limit, until the call's result. Proposed fix: `Helyx.Tool.ask/1` is taken only from the call Task, and `Helyx.Hook.ask/1` only from a hook Task; name it in ticket 1.
  - Wording: "closing answer" is undefined and, as a resume reads no entry, can go; a `message_end` or the turn end also closes the open message (Context); the two bullet lists of §6 can join.
