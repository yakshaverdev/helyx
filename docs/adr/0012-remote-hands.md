# Remote hands: one serializable hands protocol, first on one runner

Ticket #856, part of the roadmap #853. Owner decision of 2026-11-06: the hands use the same wire. The other points stand as the ticket proposes them. This ADR revises the update of 2026-10-12 of ADR 0003 for every hands, local and remote. The codec, the numbers, and the ownership table go in a feature doc, `docs/features/remote-hands.md`, which the first build ticket writes.

User story: `helyx serve` runs on a server. On a laptop, `helyx hands --connect <address>` registers as the hands of a folder. A client starts a session for that folder. The session runs on the server; every tool call runs on the laptop, and so does the harness program (Claude Code, Codex). The laptop disconnects: the running calls get their release, the turn fails as a Core stop fails it, and the session file stays. The laptop connects again: a client resumes the session, and it runs with the same hands.

## Context

- ADR 0003 made the hands a process so that the session and the tools could run on two machines. Its update of 2026-10-12 notes that the session builds the tool set and runs the tool checks on its own node (`Helyx.Tool.specs/2` and `Helyx.Tool.check_available/1`, in the caller of `Helyx.Session.start/2` and `resume/2`, `lib/helyx/session.ex`), so remote hands would need that decided again.
- The session talks to its hands with OTP messages that hold pids, refs, and a function. `Helyx.Session.Hands.start_provider/3` takes a closure, `Helyx.Session.ProviderProcess.run/1`, whose arguments hold the session pid (`lib/helyx/session/server/turn_loop.ex`). The answers name the provider process by pid: `{:provider_start, ref, {:ok, pid}}`, `{:provider_down, pid, reason}`. The provider process sends its events and replies to the session pid (`Helyx.Session.Stream.send_checked/3`, `Helyx.Session.ProviderRequest`). So a pid on another node is not enough.
- A tool calls into its session: `Helyx.Tool.ask/1` and `Helyx.Tool.transcript/0` make a `GenServer.call` to the session.
- A death of the hands stops the session (`Helyx.Session.Server`, the `:EXIT` clause), and a resume gives every open call the interrupted result of `docs/features/interrupted-calls.md`.
- The wire of ADR 0008 has a token proof, a protocol number, frame bounds, parts, and a ping that ends a connection whose peer is gone within 45,000 ms (`docs/features/wire-protocol.md`).

## Decision

### 1. A Core construct, not an interface

The hands protocol is Core, behind the split that ADR 0003 made. It is not a sixth interface: Core does not dispatch to a hands plugin, and every provider needs it, because every provider process runs on the hands side (ADR 0007, amendment of 2026-10-02). The local hands, `Helyx.Session.Hands`, become one implementation of the protocol. The session speaks only the protocol, to local and to remote hands alike, so the two kinds have one path and one set of tests.

Core does not name the wire. It defines the protocol as terms of data, and a public entry point through which a connection hands Core a remote hands that speaks those terms. The WebSocket transport carries them as frames, and it uses only the public API, as ADR 0008 §1 requires.

### 2. The protocol

Every term is data: strings, numbers, booleans, lists, and maps that encode as JSON. No pid, reference, function, or module name crosses it (ADR 0003). A provider process, a call, and a cancel are named by ids that the session makes. The protocol has these parts:

- **Capability discovery.** At each start and resume of a session, the hands build the tool set and run the tool checks on their own node, and report the specs, the names of the concurrent tools, and the providers that they can start. The session resolves a `provider/model` reference as today, and a start whose provider the hands did not report fails as `{:unknown_provider, id}`. The session takes what the hands report, keeps the tools of its `:tools` option, and checks the report as it checks plugin output today: the rules of `Helyx.Tool.specs/2`, unique names. A hands that reports an unavailable tool fails the start as `{:tool_unavailable, name, reason}` does today. The plugin tables of the two nodes do not change during a session (#473 stays open). This reverts the update of 2026-10-12 of ADR 0003, for local hands too.
- **Tool call and result.** The call with its turn id, its call id, and the context of `Helyx.Tool.context/0`, but without the Core name: the hands add their own. The result as today. The start answer and the end of a background run, and the `taken` of a run end.
- **Reads of the folder by the session node.** A plugin that runs on the session node and reads the working directory or the user's home, such as `Helyx.ModelContext.Default` (the context files from the root down to the folder) and `Helyx.Skills.scan/2`, reads them through the hands, never from the server's filesystem. Core gives such a plugin a bounded read that goes through the protocol; the feature doc names the call and its bounds, and the two bundled readers use it, for local hands too.
- **Calls from a tool into its session.** `Helyx.Tool.ask/1` and `Helyx.Tool.transcript/0` become requests from the hands to the session, with the same bounds and answers. A tool that calls the session API of its Core itself needs the Core of the session. The one bundled tool that does so, `Helyx.Tool.Agent`, starts a child session on `context.core`; on a runner that Core is not the server's, and a child there would put session state on the runner. So a runner does not report it. A request from the hands that starts a child session on the server, with the parent link and the cleanup of `Helyx.Tool.Agent`, is a later decision.
- **Provider start without a closure.** The start names the provider by its registration id, with the model, the tool specs, the session id, the resume id, and the resume usage as data. The runner puts in its own Core and the folder. Every request to the provider process (a turn with its context, a steer, an interrupt, an idle close, a close) crosses as data too. So does the stop of a provider process, which today is an exit signal to its pid (`Helyx.Session.Server.TurnLoop.stop_provider/2`): on remote hands it is a request, and the runner stops the process on its node. The answer, the ready signal, every event, every reply, every request, and the end of the provider process carry the provider id, not a pid. The `:provider_opts` of a session with remote hands are a keyword list whose values encode as JSON; the runner turns a key back into an atom only when that atom exists, so network data makes no atom, and a start with another key fails. A start or resume with other options fails before the session starts. The provider config and the credentials that the runner's node holds stay on that node (section 6).
- **Reasons as text.** A provider error, a failed start, an error reply, and the end of a provider process can hold any term today. They cross as the text of `Helyx.Reason.text/1`, made on the runner (ADR 0006 §2: Core turns reasons into text in one place). The runner logs a reason with `Helyx.Reason.log/2`, as Core does: the log gets the kind of the term only, never the term, because a term can hold message text, tool arguments, or a credential (ADR 0006, revision of 2026-10-19).
- **Cancel and stop, with release confirmation.** A cancel of a turn answers `ok` when every release returned, or an error that names the handles that stay unconfirmed. A stop answers the unconfirmed handles as text, in place of the terms that `Helyx.Session.Hands.stop/3` returns today. The rules of ADR 0004 hold inside the hands node unchanged: `Helyx.Tool.hold/1`, `release/3`, the links, and the watchdog at the port.
- **Disconnect.** Section 4.

### 3. Fencing and lease

- One session instance owns one hands at a time. Every term carries the instance id of the session. The hands refuse a term of an instance that they do not hold, and the session drops a term of an instance that is not its own.
- A runner holds one hands for each session id. When it gets the start of a newer instance of a session id that it still holds, it stops the older hands and waits for its release before it starts the new one.
- A hands that lost its session ends with every tool process, and the release path of ADR 0004 frees its resources (the kill below). A runner whose connection closes does this at once. A runner that cannot tell, such as on a connection that is half open, does it when the runner's lease ends: no frame from the server for the lease duration (below).
- One connection for each runner name. A second registration of a name replaces the first: the server closes the older connection, and its sessions stop as in section 4.
- **Durations, never instants.** Every bound that crosses the protocol is a duration in milliseconds, never a point on a clock: a monotonic instant of one node means nothing on another. A stop carries the release duration, `Helyx.Session.Hands.State.release_ms/0` (20,000 ms), not the monotonic deadline that `Helyx.Session.Hands.stop/3` takes today.
- **The runner owns its bounds.** The runner arms every bound of its side on its own clock, as the local hands do today: the kills of ADR 0007, the connect kill of a provider start, and the release deadlines of a delivery, a cancel, a stop, and the end of a provider process. The server arms no deadline on a single answer of the runner.
- **One lease for each connection.** The server bounds one thing for each hands connection: a liveness lease. The connection process of the transport sends a liveness request every third of the lease duration, and each answer renews the lease. The lease duration is 45,000 ms by default; a product sets it from 30,000 to 120,000 ms. A third of the lease is the interval, so two lost answers in a row do not end it. The registration answer gives the runner the lease duration. The wire's idle close ends a connection with no inbound frame for 45,000 ms (`docs/features/wire-protocol.md`, the ping rule and the bounds table), so a lease over 45,000 ms matters only for a peer that still answers the WebSocket pings but not the liveness requests.
- **The queue that carries the answer.** The runner has one request queue for each connection: one process that reads every request frame of the connection in order and gives each request to the hands of its session without waiting for its answer. That process answers the liveness request when it takes it. A release runs in the hands of a session, not in this queue, so a slow release does not delay the answer, and a slow runner is not a dead one. An answer shows that the runner still takes requests; the bound of each request is the runner's own.
- **The runner's lease and its freshness.** Each liveness request carries its sequence number and the sequence number of the last answer that the server got. The runner notes, on its own clock, the instant at which it sent each answer. Its first lease runs from the instant at which it sent its registration, before any answer is acknowledged: the server cannot have started the lease of the connection before it got that registration. It renews its lease only when a request acknowledges an answer newer than the one its lease counts from, and it times the renewed lease from the instant at which it sent that answer, not from the instant at which the request arrived. The server renews its lease when the answer arrives, which is no earlier than when the runner sent it. So the runner's lease ends no later than the server's lease, whatever the delay of a frame: a late or repeated request acknowledges no newer answer, or one that the runner timed from its send. A sequence number alone would not do: a request sent before the end of the server's lease can arrive long after it, and a lease timed from its arrival would outlast the server's. Two clocks that run at different rates can shift this by their drift over one lease. The bounds have no margin for it, so the drift adds to both accepted-hole bounds (Consequences).
- **The kill at the end of the runner's lease** (owner decision, 2026-11-06). At the end of its lease the runner does not stop its hands with a call that waits in the queue of the hands, as `Helyx.Session.Hands.stop/3` does: a release that runs or waits there could hold that call for the sum of the queued releases. On its own clock, it ends the hands process and every tool process of the connection, the provider processes included, with an exit signal, `:kill`, sent to each process, so that a process that traps exits ends too. It does not wait for a queued release, and a queued release dies with its process. The release path that works when its owner dies does the rest (ADR 0004): each port closes with its process, and the watchdog ends the process group of the command, after its TERM grace (`Helyx.Watchdog.grace_ms/0`, 500 ms, or 5,000 ms for a harness program, `Helyx.HarnessIO`). The runner reports no unconfirmed handles for these hands: the server already counts them `:unknown`. So the commands of those hands end within the TERM grace after the end of the runner's lease, at most 5,000 ms, with the holes of ADR 0004: a command that leaves its process group, and a Codex command that its program does not end at TERM. A runner whose connection closes ends its hands the same way.
- **The end of the lease.** When the lease ends, or the connection closes, every hands of that connection counts as dead: the connection closes, and each server process that stands for a hands of it exits with a `{:shutdown, _}` reason. That ends every wait of a session on those hands: on remote hands, each end or answer that a session waits for (a provider start, the answer to a provider request, the end of a provider process after its stop, a cancel answer, the capability report, a read of the folder) comes through the stand-in, and the session also watches the stand-in in each such wait. A wait that watches a local pid today, such as the wait for the end of a provider process in `Helyx.Session.Server.Stop`, watches the stand-in on remote hands.
- **One stop deadline.** On remote hands, `Helyx.Session.Server.Stop.run/1` arms one deadline when it starts, `@hands_stop_ms` (the release duration of 20,000 ms plus 2,000 ms, 22,000 ms in all), and two waits share it: the wait for the end of each provider process that it closes, which today has no `after` (`stop.ex`, the `receive` after the close requests), and the wait for the stop answer of the hands. Each wait is a `receive` with an `after` that ends at the shared deadline, as the call timeout of the stop of the hands bounds that wait today. The stand-in ends right after it passes on the stop answer of the runner, so the wait for its `:DOWN` in `stop_hands` (`stop.ex`, the `receive` after the stop call) is the third wait inside the shared deadline: it comes at once after the answer, and past the deadline the session kills the stand-in, as `stop_hands` kills local hands that do not answer. Past the deadline, or when the lease ends first, the stop report gives `:unknown`, and the runner still releases within its own bounds. The local hands keep their two waits: the armed close kill of a provider process (`State.provider_close_ms/0`, 5,000 ms), then `@hands_stop_ms`.
- **The stop fits its budget.** The supervisor kills a session after `Stop.shutdown_ms/0`: `provider_close_ms` (5,000) + `@hands_stop_ms` (22,000) + a load margin (3,000) = 30,000 ms. On local hands the waits take at most 5,000 + 22,000 = 27,000 ms, as today. On remote hands they take at most 22,000 ms for both shared waits, with 8,000 ms left. This holds with two queued releases on a live runner, which can hold the end of a provider process for up to 40,000 ms: the shared deadline ends the wait at 22,000 ms, the report gives `:unknown`, and the runner finishes the releases by its own bounds. So the supervisor never kills the session before the stop report, and `shutdown_ms` does not change.
- **A stuck hands on a live runner.** The runner arms every bound of its side on its own clock, so a hands that is stuck on a runner that still answers the lease is bounded by the runner's own bounds. The server trusts the runner for that, as it trusts a local hands today, and it adds no bound of its own: its only waits on a stuck hands are those that the stop deadline or the lease ends.
- **Every death of the stand-in reaches the runner.** The connection process of the transport watches the server process that stands for each remote hands on it. At any end of that process, a lost hands, a crash, or a kill with its session (the link of ADR 0004), the connection sends the runner a stop of that session instance and does not wait for its answer; the runner stops those hands and releases their handles within its own bound. A death of the connection process closes the socket, and the runner releases at the close or at the runner's lease. So no end on the server leaves hands on the runner past a stop, a close, or a lease.

### 4. Disconnect and reconnect

- A runner that does not answer the liveness request cannot be trusted to release on request. So at the end of the lease the server closes the runner's connection, which stops every session on it; the runner releases at the close, or at the runner's lease when the close does not reach it.
- A closed connection, or the end of the lease of section 3, is a lost hands. The session stops as at a death of the hands today: the turn fails, the session file stays, and the stop report gives `:unknown` for the handles of the hands, as `Helyx.Session.Server.Stop` does today when the hands are gone or do not answer the stop. The server cannot list handles that only the runner held. A `notice` event tells the clients that the hands are lost, before `session_end`.
- New: the session stops with a `{:shutdown, _}` reason, so `Helyx.Session.end_reason/1` gives `stopped`. A lost connection is an expected event, not a crash, and `session_end` keeps its two reasons. A crash of the hands process, local or the one on the server that stands for remote hands, still ends the session as `crashed`.
- The runner kills every hands of that connection (section 3).
- No call survives a disconnect. At a resume, every open call gets the interrupted result of `docs/features/interrupted-calls.md`, as after a Core stop.
- The session file records the runner name. A client resumes the session as after any stop, and the resume goes to the runner of that name. Without a connected runner of that name, the resume fails with an error, and nothing starts. The server does not resume a session by itself.

### 5. Transport: the same wire

- The runner connects on the WebSocket wire of ADR 0008 with a `hands` role and its runner name in `hello`, the proof of section 5a, the protocol number that every client sends, and the same frame size and parts. There is no second listener.
- The frames of the hands are a namespace of operations and events, `hands.*`, on the frame types that the wire has. A runner registers with one `req`, with its name and its folder. On a hands connection the server sends `req` frames for the terms that the session sends, and the runner answers with `res` and sends `event` frames for the terms that the hands send. The calls of a tool into its session are `req` frames from the runner.
- **5a. The hands credential.** The proof mechanism of the wire stays: the `hello` of a runner carries the HMAC-SHA256 of the nonce, keyed with the SHA-256 of a secret, and no secret crosses a frame. The secret is a hands credential, not the server token. The server token permits every client operation, and a runner that the agent controls (section 6) must not hold it: the agent can read what its runner holds, and with the server token it could open a second connection as a client and read or stop sessions that are not its own. The `unknown_op` rule below protects only the connection that chose the hands role.
  - **Scope.** A hands credential is valid only for the `hands` role and one runner name. The server checks the proof of a `hello` against the credential of the runner name that the `hello` gives. It closes with `4401` a `hello` with the client role whose proof matches no server token, which is every hands credential, and a registration whose runner name is not the name of the `hello`.
  - **Mint.** Through the public API of the server, by the code that starts the runner: a product or a bundled integration module. A call with a runner name returns a new credential of 32 random bytes and replaces any earlier credential of that name. Core names no container and no hub. The product hands the credential to the runner as it starts it, by the channel that it owns (an environment variable or a file of the container, or a command line of the owner on a laptop), and never in a frame.
  - **Lifetime and revoke.** A credential is valid until it is revoked, replaced, or the server stops: the server keeps only its SHA-256 in memory, as it keeps the key of the token (ADR 0008, revision of 2026-10-18), and writes it to no disk. A revoke through the same public API, or a new mint for the name, closes the connection that proved the old credential, so its sessions stop as at the end of the lease (section 4), and refuses the next `hello` with it. The code that starts a runner revokes its credential when it stops the runner. After a restart of the server, that code mints again.
  - **The server token on the hands role.** A `hello` with the hands role may also prove the server token, for any runner name. That serves the runner of an owner, such as a laptop, whose owner holds the server token anyway. A runner that the agent controls gets a hands credential, never the server token.
- A hands connection counts against the 64 connections of a server. A client operation on a hands connection, and a hands operation on a client connection, get `unknown_op`.
- The role and the `hands.*` operations change the schema, so the build ticket raises the one protocol number that clients and runners share. A bump of another ticket, such as #857 or #858, is separate.
- **The sender checks each term.** Some terms have no Core size bound: a tool spec, the system prompt and the context of a turn, the answer of `transcript/0`. So no limit derived from Core bounds covers every legal term. A hands connection has its own limits for one term, in joined bytes, in decoded values, and in integer size, which the feature doc states and which both sides know. Before it sends a term, the sender checks it against them; a term over them fails the one operation that it belongs to with an error (the turn, the start, the call, the read), not the connection. The receiver enforces the same limits, and a frame over them is a contract break of its peer, which closes the connection.
- The server checks every frame of the hands as plugin output. It trusts no check that the runner ran, because that check ran on a node that the server does not control: the text of a tool result goes through `Helyx.Message.cut_result/1` again, and every provider event passes `Helyx.Session.Stream.check/1` on the server. This is a second check next to the one of the provider process on the runner, and it is deliberate. A result that carries blocks other than text is #858. The session mailbox bound of `Helyx.Session.Stream.send_checked/3` applies on the server: past it, the server stops the provider process on the runner, and the turn fails, as today.

### 6. Who provisions

Starting a container, a snapshot of `.agents/setup`, secrets, portals, and any process that starts a runner belong to a product or a bundled integration module, never to Core. The provider options and credentials that a provider process needs come from the runner's node, because the process runs there.

**The key rule** (owner decision, 2026-11-06). A runner that the agent controls, such as a container, never holds a long-lived secret that grants more than it needs. For the wire, that is the hands credential of section 5a, never the server token. For a model, it never holds a long-lived model key. It gets model access through a proxy on the server, with a token that is valid for one session. The secrets follow-up builds the proxy; this ADR states the rule. A runner that its owner controls, such as a laptop, may hold the owner's own keys. Reason: the agent runs commands on its runner, so whatever the runner holds, the model can read; a token for one session limits what a leak gives.

## Bounds

| Input | Bound | Where |
|---|---|---|
| hands per session instance | 1 | the instance id in every term |
| connections per runner name | 1; a new one replaces the old | server |
| hands credential | one for each runner name, 32 random bytes, valid for the `hands` role and that name only; until revoked, replaced, or the server stops; the server keeps its SHA-256 in memory only | server |
| a frame of a hands connection | 1 MiB, with parts | transport |
| one term on a hands connection | the joined-byte, value, and integer limits that the feature doc states; over them the sender fails the one operation, and the receiver closes the connection | sender and receiver |
| a bound of one operation on the runner (a kill, a connect, a release) | armed by the runner on its own clock; a bound that crosses the protocol is a duration; the server arms none | runner |
| liveness lease for each hands connection | 45,000 ms by default, set from 30,000 to 120,000 ms; renewed by each answer to a liveness request, sent every third of the lease and answered by the runner's request queue of the connection; at its end the server closes the connection and every hands of it is dead | server |
| stop of a session's hands | on remote hands, one deadline of `@hands_stop_ms` (22,000 ms) shared by the wait for the provider ends and the wait for the stop answer; past it or at the lease end, `:unknown`; the whole stop path fits `Stop.shutdown_ms/0` (30,000 ms) | server |
| hands on the runner after the stand-in ends | a stop from the connection, or the close, or the runner's lease | transport and runner |
| a tool result from the hands | the cut of `Helyx.Message.cut_result/1`: valid UTF-8, at most `Helyx.Message.max_result_bytes/0` bytes | server |
| a provider event from the hands | `Helyx.Session.Stream.check/1`, and the session mailbox bound | server |
| a capability report | the checks of `Helyx.Tool.specs/2`, in one request | server |
| runner's lease | the lease duration from the send of the newest answer that a request acknowledges, on the runner's clock; it ends no later than the server's lease; from the send of the registration until the first acknowledged answer; at its end the runner kills its hands and tool processes, and the commands end within the TERM grace of the watchdog, at most 5,000 ms | runner |
| reconnect | the open calls get interrupted results, as a resume after a Core stop gives them | session resume |

## Considered options

- **A second listener for the hands.** Rejected by the owner: a second port, a second auth, and a second set of bounds, for frames that the wire can carry.
- **A Hands interface in Core.** Rejected: Core would not dispatch to a hands plugin; it speaks a protocol to a peer.
- **Erlang distribution between the server and the runner.** Rejected: the closure and the pids would cross as they are, but distribution trusts the whole peer node, and a runner that is not on the BEAM, or a server on a runtime that cannot run one, could not take part.
- **The provider process on the server for an API provider.** Rejected: two provider paths, against the one path of ADR 0007's amendment of 2026-10-02.
- **A deadline on each answer of the runner** (owner decision of 2026-11-06). Rejected: the runner runs the releases of a session one after another, so an answer can wait for the sum of them, and a deadline per answer closes a runner that is only slow; an instant of the server's clock means nothing on the runner; and each patch of these deadlines showed the next wait without one (`docs/reviews/2026-11-06-remote-hands-adr.md`, rounds 1 to 4).
- **Calls that survive a reconnect.** Rejected: a call's result would come to a session instance that did not start it, and the interrupted result already tells the model to check the effects.

## Consequences

- ADR 0003 gets an update note: since this ADR the hands report the tool set and run the tool checks, for local and for remote hands.
- `docs/features/wire-protocol.md` names this ADR for the `hands` role. Its schema does not change until the build ticket.
- Accepted hole: the commands of old hands can still run for a while after the server counts them dead. After the end of the lease: at most the TERM grace of the watchdog (5,000 ms at most), because the runner's lease has ended by then and the runner kills its processes at once, plus the clock drift over one lease. After a replace or a half-open close: the runner kills at the close when it gets the close; otherwise its lease ends no later than the server's lease would have ended, at most one lease duration after the close, so at most one lease duration plus the TERM grace, plus the clock drift. No session gets the output of those commands, and a resume on the same runner stops the older hands first. The model gets interrupted results at the resume and checks the effects.
- Accepted hole: the holes of ADR 0004 hold on the runner. A command that leaves its process group, and a Codex command that its program does not end at TERM, outlive the kill.
- Accepted hole: a hands that is stuck on a runner that still answers the lease is bounded only by the runner's own bounds; the server trusts the runner, as it trusts a local hands today.
- Accepted hole: a hands credential lets the agent that controls its runner open hands connections with that runner name. Such a connection replaces the runner's own connection (section 3), which stops its sessions, and it then receives the requests of new sessions for that runner. It reaches no client operation and no other runner name.
- Accepted hole: `Helyx.Tool.Agent` is not available on remote hands until a child session can be started from the hands.
- The background folder of a session moves to the hands node, and the hands delete it at their stop, no longer `Helyx.Session.Server.Stop`.
- This work gives the means to choose a runner: a start option that names it, a `hands` parameter of `start` on the wire, and the runner name in the session file. Which runner a session gets in a product with a hub is the executor assignment of `Helyx.Hub` (#857), which uses these means.

Later tickets of #853 build, in this order:

1. The feature doc `docs/features/remote-hands.md`: the terms, their codec on the wire, the term limits, the durations on the protocol, the lease setting, the bounds, and the ownership table.
2. Core: the protocol terms; the local hands as one implementation of them; the capability report in place of the tool set that the session builds; the provider start without a closure; reasons as text; the read of the folder, and `Helyx.ModelContext.Default` and `Helyx.Skills.scan/2` on it; the entry point for a remote hands.
3. The wire: the `hands` role, the `hands.*` operations and events, the hands credential with its mint and revoke in the public API of the server, and the new protocol number. Its tests: a hands credential in a `hello` with the client role closes with `4401`; a hands credential for one runner name in a `hello` or a registration with another name closes with `4401`; a revoke and a new mint close the connection of the old credential and refuse its next `hello`; a `hello` with the hands role and the server token is accepted; after a restart of the server an old credential is refused; the logs of the WebSocket server that the token tests capture hold no credential; a hands operation on a client connection and a client operation on a hands connection get `unknown_op`.
4. The runner, `helyx hands --connect`, and the runner choice at start and resume.

Out of scope: containers, snapshots, portals, and secrets, the model proxy of the key rule included (follow-ups after this ADR); a tool set that changes during a session (#473); a UI for harness approvals.
