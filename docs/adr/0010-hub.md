# Helyx.Hub: identity, records, routing, and wake-ups beside the transport

Status: accepted on 2026-11-06, ticket #857 (decision of the owner in the ticket, 2026-11-06). Part of the roadmap #853.

`helyx serve` is one user, one data folder, and one token that the server file holds (`docs/features/serve.md`). A session has no owner, no project, no labels, no title, no visibility, no search, and nothing that wakes it at a time. None of that is a Provider, Tool, ModelContext, Compaction, or Memory, so it is not a plugin (ADR 0009). It is not Core either: Core knows only interface constructs (`AGENTS.md`).

User stories:

- A user starts a session on the laptop, gives it a title and a label, and finds it on the phone with a search. Another user of the same server does not see it.
- A user saves a prompt that runs each morning at 8:00 in one session. The session was stopped overnight; at 8:00 it runs the prompt once, and the user reads the result in any client.

This ADR revises ADR 0008 in two places. §1: push to an app that is closed moves from a product client host to Hub. §6: when a product gives the transport the authority of Hub, a user credential replaces the one server token, and the check covers every operation and every subscription, not only `hello` (§3). The wire codec of the new operations, the bounds, and the storage schema are in the feature doc of Hub (Consequences).

## Context

- ADR 0008 §1 made a transport a bundled module, `Helyx.Transport.WebSocket`, that a product starts and that uses only the public session and server-management API. Core does not name it.
- The transport authorizes a connection once, at `hello`, with the proof of one server token (ADR 0008 §6, revision of 2026-10-18). After `welcome`, every operation and every subscription is open to that connection. There is no user.
- A session record today is the header of its session file and the `saved_session` of `sessions.saved` (`docs/features/wire-protocol.md`): `id`, `cwd`, `model`, `mtime`, and the first prompt. The session file is a Core construct that every product runs.
- Two Cores can hold one session id with two instances (`CONTEXT.md`, "Session instance"). Nothing decides which instance a client reaches.
- A session runs only while its process lives. Nothing starts a prompt at a time or on an outside event, and a timer in a session process ends with it.

## Decision

### 1. A bundled module, not a plugin, not a product, not Core

`Helyx.Hub` is a bundled module in `plugins/bundled`, under the rule of `Helyx.Transport.WebSocket` (ADR 0008 §1): a product starts it in its own supervision tree, it uses only the public session API and the server-management API (`Helyx.Session`, `Helyx.Sessions`), and Core never names it. It implements no interface and has no registration entry. A product becomes a deployable that starts Core, the transport, and Hub, and a product that starts no Hub runs as today.

Reason: Hub adds no behaviour that Core dispatches to, and every product that serves more than one user or wakes a session needs the same identity, records, and delivery. A product that built them would build them again for the next product.

### 2. What Hub owns

- **Identity and authorization.** Users, and their credentials: tokens first, OIDC later. Hub decides the user of a connection at `hello`, and it authorizes every operation and every subscription of that connection, not only the discovery operations. A session that a user may not see gets the same answer as a session that does not exist, so a refusal does not tell that the session exists. The default is deny.
- **Projects and session records.** Owner, project, title, labels, visibility, archive, and search. A record lives in Hub storage, keyed by the session id, outside the session file. The session id names a session across its instances and across Cores (`CONTEXT.md`, "Session instance"). Core has no namespace of ids: the name of a Core is an atom that scopes its processes in one node (`lib/helyx/core.ex`), so it is not part of the key. A Hub over several data folders decides its key when it is built. The session header does not change, and a session file stays runnable by a product with no Hub.
- **Routing.** A session id maps to the node that holds its instance. Hub decides which instance a client reaches, so one session id has one instance that a client of the Hub reaches. A client never names a node. The first Hub serves one Core in one node, where the map is that Core; several Cores in one node, which can hold one id twice, are a case for the feature doc of Hub, and the mechanism across nodes (`:pg` or a Registry across nodes) is decided when a deployment needs more than one node.
- **Executor assignment.** Which hands a session gets (local, a runner, a container), once the ADR of remote hands (#856) exists. Hub decides it at the start and the resume of a session; Core keeps the hands contract of that ADR.
- **Schedules and wake-ups.** A schedule is a saved prompt that Hub sends to a session at a time. An event subscription is an outside event (a webhook, such as one from GitHub) that sends a prompt to a session. Push notifications go to the apps of a user. Hub owns their durable delivery, deduplication, and recovery after a restart; none of them is a Core timer. A wake-up goes through the public session API: Hub resumes the session when it does not run (`Helyx.Sessions.resume/2`), then sends the prompt with the product origin, `origin: %{kind: :product, id: id}` of `Helyx.Session.prompt/3`, whose id names that delivery of the wake-up.

Out of Hub: the transcript, the turn, the tools, the session file, the replay ring, and the credit count of each subscription stay Core (ADR 0008 §4); the frames, the parts, the `ack` frames, and the outbound queue stay the transport.

### 3. Hub operations on the same wire

Hub operations go on the wire of ADR 0008, on the same connection as the session operations, in a `hub` namespace of operation names (`hub.<name>`), with a new protocol number. There is no second listener for clients.

- **One connection, one check.** The user that Hub decides at `hello` holds for every frame of the connection. Hub authorizes each `req` before it runs, the session operations too, and each `subscribe` before the subscription process calls Core (`Helyx.Session.subscribe/2` in `plugins/bundled/lib/helyx/transport/web_socket/subscription.ex`). So the check that guards a record also guards the event stream of its session.
- **The session operations keep their codec.** Under a Hub, `sessions.live` and `sessions.saved` list only the sessions that the user may see, and `start` and `resume` make or check the record of the session. A server with no Hub answers every `hub.*` operation with `unknown_op` and authorizes as today.
- **The transport does not name Hub.** The product gives the transport, at its start, the authority of its connections; Hub provides one. The transport asks that authority for the user at `hello`, for a decision before each operation and each subscription, and to run the `hub.*` operations. A transport started with no authority keeps the server token of ADR 0008 §6.
- **No secret in a frame.** The rule of the revision of 2026-10-18 of ADR 0008 holds for every credential of a user: `hello` carries a proof for the nonce of the connection, never the credential.
- **Version.** The protocol number goes up with the first `hub.*` operation in the schema of `wire-protocol.md`, under the rule of ADR 0008 §7: equality, no compatibility code.

Reason: the council of the 2026-11-01 thread asked that authorization cover subscriptions. With two listeners, a client holds two connections with two checks, and the event stream of a session would be guarded by a check that does not know its record.

### 4. Storage behind one boundary, SQLite first

Hub reads and writes its state through one storage boundary, a behaviour of Hub (`Helyx.Hub.Store`), from the first commit. Users, projects, records, schedules, pending wake-ups, and delivery state go through it; nothing of Hub reads a file or a database around it. A deployment on another backend replaces the implementation and keeps Hub.

The first implementation is SQLite in the data folder (`:sessions_dir` of Core, the data folder of `docs/features/serve.md`, decision 4). `helyx serve` refuses a data folder that its group or other users can write. One Hub owns its store: under `helyx serve`, the lock of the data folder makes one server per data folder, so one Hub writes the file. A product that starts Hub outside `helyx serve`, and a Core with no data folder (`:sessions_dir` nil), are cases that the feature doc of Hub settles. The SQLite library is a new dependency of `helyx_plugins`.

Reason: records, search, labels, and due wake-ups are queries over many records, and a wake-up and its delivery state change together. A file per record gives neither a query nor an update of two records at once. Postgres needs a server process that a single-user deployment does not run; it is the next implementation, behind the same boundary.

## Considered options

- **Hub as a product.** Rejected: products become deployables, and each would build identity, records, and delivery again (thread of 2026-11-01).
- **Hub in Core, or a Hub interface.** Rejected: Core would dispatch nothing to it, and users, projects, and schedules are not interface constructs.
- **A second listener for Hub operations.** Rejected: two connections and two authorization checks, and a subscription that the record check does not cover (§3).
- **Records in the session header.** Rejected: the header is Core, a product with no Hub would carry fields it does not use, and a title or label change would rewrite a session file.
- **A file per record.** Rejected for the first implementation: no query across records and no update of two records at once (§4).
- **Postgres first.** Rejected: a server process that a deployment of one user does not run. It is the next implementation behind `Helyx.Hub.Store`.
- **Schedules as Core timers or session timers.** Rejected: a timer ends with its process, is lost at a stop of the server, and cannot be deduplicated across a restart.

## Consequences

- The extension surface does not change: Provider, Tool, ModelContext, Compaction, and Memory. `AGENTS.md` and the README name Hub as a bundled module beside the transport when its code lands.
- ADR 0008 gets a revision note for §1 (push to an app that is closed is sent by Hub; the client host receives it) and §6 (under the authority of Hub, a user credential and a check of every operation and subscription). `wire-protocol.md`, "Out of scope", points here.
- The transport takes an authority option, and its authorization moves from `hello` alone to every operation and every subscription when an authority is given.
- Later tickets build, in this order of dependency:
  1. The feature doc `docs/features/hub.md`, from `docs/features/TEMPLATE.md`. It states the user model, the credentials and their proof in `hello`, the visibility values, the `hub.*` operations and their errors, the authority callbacks of the transport, the schema of the store, and the bounds: records per user, labels per session, schedules per session, pending wake-ups, the size of a webhook payload, and the wait of a wake-up when its session is stopped. It also says how a Hub outside `helyx serve` owns its store, where a Core with no data folder keeps it, how routing picks between several Cores in one node, how a session that has no record, such as one started before the Hub, gets one, and what a wake-up does when a turn runs.
  2. `Helyx.Hub` with users, tokens, records, and the authority of the transport; `Helyx.Hub.Store` and its SQLite implementation; the `hub.*` operations in the schema of `wire-protocol.md` with the new protocol number.
  3. Schedules and wake-ups, with durable delivery and recovery.
  4. After #856: executor assignment.
  5. Event subscriptions with their webhook endpoint, push, routing across nodes, and OIDC, each when a deployment needs it.
- Out of scope: several humans in one session (multiplayer), billing, and a web client.
