# Review checklist

Invariants the review axes check on every diff. Add one when a review or a PR comment finds a defect that a checklist line would have caught. The failure-path brief in the ship skill names the probe categories; the lines here are the invariants the probes must not break.

A line that a review adds for one case ends with its source: the issue or the run that found the case, and the class of its input. The class is observed (a real provider, program, or user sent the input), constructed (a probe or a test made it), or not verified. The class guides the next reviewer; it does not decide whether the line stays. When a mechanism changes, review each line about it, whatever its class. Source: the joint review of 2026-10-16 (#642).

A class of defect that the reviews find a second time gets a mechanical check: its line names the check that could find it, or says why none can. Source: #660 and #763, where a secret in buffered frames took a defect in each round.

## Specs and bounds

- The feature doc states the bound of every input, buffer, and wait, or says "unbounded, ticket #N". The spec axis checks that table against the diff.
- A numeric limit has tests for the exact maximum and the first rejected value, or a property test that covers those decisions. Retained tests also cover an ordinary accepted input. Test character boundaries, transformations, framing, and accumulation when they change the checked size. A separate one-under example is required only when it covers a distinct case.
- Every `ponytail:` marker names a ticket. Judge whether the debt is safe to ship, not only whether it is recorded.
- A design decision that the tools research (`docs/research/coding-tools.md`, issue #17) covered cites it in the feature doc, so the spec axis can check the design against how codex, opencode, and pi behave.
- Every external resource in the diff (OS process, process group, port, file handle, socket, temp file) has a row in the feature doc's ownership table. A row whose release path dies with its owner is a design flag the spec axis raises (ADR 0004).
- A change that replaces a mechanism has the "Replaced mechanism" section of `docs/features/TEMPLATE.md`. The spec axis checks it against the code. A part or a test of the old mechanism with no row is a finding. Source: reviews 1 and 2 of the provider design (2026-10-02), where a contract derived from a summary missed the guarantees of the start ask, the interrupt order, and the completion wait.
- A change that removes or moves doc text (a moduledoc trim, a doc split) checks each sentence that stays, with its `@doc` neighbours, against the code without the removed text. A removed qualifier can turn a kept sentence false. Each bound in the removed text has a row in the doc that the link names; a link does not move a bound. Source: #306 (2026-10-02), where the trim removed the connected steer rules and left `steer/2` promising a delivery that a connected turn does not guarantee; #445 (2026-10-04), where the cut Replay section took the `wire_id/1` and Codex `tool_name/1` bounds with it.
- A doc sentence that says how a state changes (a message closes, a call ends, a request is answered), or what a value holds, is checked against every writer of that state: search the code for each function that writes it, not only the path the change touches. A second writer makes an exclusive claim false. Source: #307 (2026-10-03), where the context rule said only `message_end` closes an assistant message, and `Server.take_steer/2` closes it too.
- A doc sentence that says what Core rejects or enforces names the function that does it, and the reviewer reads that function. A rule with no such function is cut, not reworded. A shorter doc that is true is the target. Source: #446 (2026-10-04), where the lifecycle doc said a repeated open call id stops the provider, and only a repeated Helyx tool request is rejected (`ToolQueue.request/4`). This is the third false doc claim after #306 and #307; no mechanical check can read prose, so the rule cuts claims.
- Abort, delivery and release end released or unconfirmed: `Helyx.Session.Hands` (its private `release/4`) and `Helyx.Watchdog.Group.release/4` stop at their deadline, and `TurnLoop.progress/1` answers the abort callers after either outcome. A doc never says that a resource is gone, a directory is clean, or work has stopped after one of them; it says released, or reported unconfirmed. Source: #447 (2026-10-04), where three gate rounds found six such guarantees.

## Boundaries

- Each input is checked at its boundary (see `AGENTS.md`, "Elixir guidelines"). The spec axis names the boundary of every new input.
- A library function that parses boundary input can raise on some inputs, not only return an error. `OptionParser.parse/2` raises `ArgumentError` on `-=` (#148). At the boundary, contain the exceptions of such a parser by name, and probe it with generated input, not only with the cases a reviewer thinks of.
- A reviewer reports defensive handling in inner code (`AGENTS.md`, "Validate at boundaries") as a finding, with every caller and the upstream check (`file:line`). A repeated check follows `AGENTS.md`, "Remove a repeated check".
- `AGENTS.md`, "Use the checked value": a new read of the source is a finding only when its value is used under the earlier check with no check of its own.
- `AGENTS.md`, "Reject the smallest unit": the failure path names what one bad value destroys, and the feature doc states each case where missing identity, damaged structure, or an unresolved resource requires a larger failure.
- A public plugin entry (a tool's `run/2`, a provider's `stream/3`) is a boundary for all of its arguments, because code outside the hands and the session can call it.
- A finding needs a reachable input: its reproduction enters through a boundary. Source: the boundary review of 2026-09-26.
- A value from outside that confirms a safe state (an empty queue, a finished command, a ready context) is matched on the exact safe value. A missing field, `null`, a wrong type, or an unknown status takes the unsafe path: stop or fail. The failure-path review sends each of these to every such check. Source: the Codex findings of #199 (a nil context), #200 (a missing `still_queued`), and #201 (a command completed with `inProgress`), one class three times; no mechanical check can know which state is safe, so the rule is here.
- A path that the code opens on disk is boundary input, and so is the type of file at that path. The failure-path review puts each file type there (a regular file, a folder, a FIFO with and without a reader, a device, a symlink to each, a dangling symlink) and checks that no type blocks the open past its bound or leaves a process or a handle behind. An open that can block on a FIFO or a device needs a non-blocking open and a type check on the open handle. Source: the Codex gate round 1 finding of #579 (a FIFO at the lock path left one perl process per retry).
- A secret mask runs on the text that reaches the user or the log, after the code has read the fields it needs. A mask over the structure that the code still reads changes what it reads. Source: #760, Codex round 3 (the key mask ran over map keys before `message` was read), constructed.
- A secret does not travel in data that a dependency can log: frames, buffers, plug options, start arguments, child specs. The mechanical check is a test that drives each such path, takes the log events, the process states, and the child spec, and refutes every printed form of the secret, as the "no log, option, or process state holds the token or the key" tests in `plugins/bundled/test/helyx/transport/web_socket_test.exs` do. Source: #660, where the token in a buffered frame reached three dependency log paths, and #763, which removed it from the frames; constructed.
- A reader of untrusted text accepts a stated subset and fails closed. The subset is checked against the text of the specification, not only against a parser. Source: #471, where a full YAML parser and then a reader that looked for the end of a value took defects in three runs; constructed.

## Races and resource ownership

- A race is closed structurally or stated as a hole. It is never accepted by window size or by who the caller is today. An open race is written in the ownership table as "open, ticket #N", the same vocabulary as an unbounded input.
- Two findings on one mechanism stop the patching. The next round fixes the mechanism, not the path. The first question is whether the mechanism can be deleted, for example a stored value that can be derived on read (#269).
- A `receive` loop with a deadline checks the deadline before each `receive`. A matching message in the mailbox wins over `after`, even with a timeout of 0, so a sender that never stops keeps the loop past its deadline. The failure path queues messages past the deadline and checks that the loop acts on it. Source: the Codex round 1 finding of #11.
- A `receive` that waits for one message of a sender (a `:DOWN`, a reply) skips the earlier messages of that sender. When those messages carry state (a queue, a text), the code takes them first, in mailbox order, up to the one it waits for. The failure path puts such a message before the awaited one and checks that it is not lost. Source: the Codex gate round 1 finding of #551.
- A Task that a shutdown must end at once does not trap exits. With the trap on, a shutdown is a message: it waits behind every message queued before it and behind any work or blocking call that runs with the trap on. A trap that a graceful stop needs (the Codex interrupt) has its wait stated in the feature doc. Source: the four findings of #167 on the trap of the Claude Code stream.
- Every resource has a release path that works when its owner dies (ADR 0004): inside the VM through links to the owner, at the OS boundary through the port watchdog. The resource is still held with the hands, with `Helyx.Tool.hold/1`, before the external work starts.
- A step that repeats in one owner (a relaunch per prompt, a reconnect, a retry) gives up what the step before it held, or the held set grows with the number of turns. The failure path runs the step three times and checks the held count, also with one earlier resource that cannot be proved gone: a release with a deadline checks every cheap proof (a dead pid, an absent group) before it waits on one resource. Source: the Fable gate finding and the Codex gate round 2 finding of #651.
- A cleanup acts on the process that it started, never on a new lookup of a name or an id that can name a later process. Source: #735, Codex gate round 1 (the cleanup found the child again by id and stopped a later instance), constructed.
- A new process names its supervisor and its cap: the most instances that can run at one time. Source: the orchestrate run of 2026-10-18 (#776), not verified.
- A test that monitors a process it just spawned uses `spawn_monitor/1`. With `Process.monitor(spawn(...))` the process can exit before the monitor is set, and the `:DOWN` reason is `:noproc`. Source: the Codex round 1 finding of #170.
- A wait that orders two effects (a barrier: act only after another process has handled something) has no timeout that falls through to the act. A timeout there is a path that breaks the order. The failure-path brief states the order as an invariant, and the review treats each timeout, error, and exit of the wait as a path of it. A bound on such a wait comes from the monitor of the process it waits for, or is stated as "unbounded, and accepted". Source: the Codex round 1 finding of #189.

## Events

- Every `message_start` gets a `message_end` on the same turn, on success and on failure.
- Every turn ends with one `turn_end` and its `outcome`, on success, abort, and failure.
- Sequence numbers increase by one per event within a session instance, with no gaps. Every event and every snapshot carry the instance id (#204).
- A rule that a snapshot equals the fold of the events is checked against every path that writes to the transcript: for each write, the live fold and the snapshot create cells by the same rule, or the difference is a stated limit. `grep` the callers of the transcript writers (`record_result`, `abort_open_calls`), not only the paths the ticket names. Source: #163, Codex round 2 (an external turn, now a connected turn, that ends normally records `aborted` results for calls that never started; the live fold ignores the result event, and the snapshot makes a closed cell).

## Sessions and turns

- A failure in a turn never crashes the session. The turn fails, the session accepts the next prompt.
- A message from a Task that is no longer current never touches the session.
- A stream that ends without a terminal event fails the turn.
- A partial assistant message from a failed or aborted turn is added to the transcript. One with text only has stop `:aborted` or `:error` (#432); one with a tool call has stop `:tool_use`, and its calls get `aborted` results (#385). A provider cannot send `:aborted` or `:error` (`Helyx.Session.Stream`).
- An id of outside state (a harness session, a remote job) is reused only when that state has received everything it needs, for example the whole replay. The failure path builds the table of the id's life (stored, first use, completed) crossed with abort, steer, failure, a Task crash, a restart, and a change of that state by its owner (a native compaction), and tests each cell. Source: the Codex round 1 finding of #10; the compaction row from the gate of #552. A change that widens when an id is reused also checks every value that a resume derives (a cost mark, a count): the resumed value matches the live one, or the feature doc states the ceiling. Source: gate round 3 of #552.

## Plugins and Core

- A bad plugins value returns `{:error, reason}` from `Helyx.Core.start_link/1`; it never raises, and Core does not start. This includes a value that is not a proper list (nil, a string), an entry that is not a loadable Elixir module (an integer, a string, nil, an Erlang module such as `:lists`, a module that does not exist), a module listed twice (`{:duplicate_plugin, module}`, a provider too, #522), a module that implements no interface, two plugins for a single-mode interface, no provider plugin, and two different providers with one id. The shape check in `Helyx.Core.Plugins.resolve/1` runs first, and the checks after it trust the shape (#517). A child spec that fails when the supervisor starts (two plugins with one explicit child id) fails Core's start as any OTP `start_link` does: a caller that traps exits, such as a supervisor, gets `{:error, reason}` (#525).
- Core knows no interface by name except `Helyx.Provider`, of which `Helyx.Core.start_link/1` requires at least one plugin.

## Inputs from plugins

- The contract-break rule is in `AGENTS.md`, "A contract break gets one generic answer". A finding that asks for a case-specific handler names its evidence. A finding that asks for a case-specific handler of output that no real provider shows is rejected with this rule, and the review record says so. A finding that the generic failure path does not fire (the output reaches session state, or the provider process does not stop), a race between Core processes, and a broken safety bound stay findings. When a test exists only for such a case, deleting the test and its handler is a valid fix. Source: owner direction of 2026-10-03 (#360).
- A removal of a handler that a review calls unreachable needs a probe through the boundary that shows that no input reaches it. A claim of unreachable is not a fact. Source: the orchestrate run of 2026-10-18 (#776), not verified.
- A value from a plugin is checked by shape before it reaches a process that holds state. Match the whole tuple or struct, never elements by index.
- Providers are compiled into the node. Shape is checked; individual field values are not.
- No stacktrace from any reason term reaches the error text of a client event, whatever wrapper holds it. One bounded walk puts a marker in place of every stacktrace in the whole term before the text is written, so the safety does not hang on a list of crash shapes: a raw Erlang error carries its stack in the reason, and an exception field or the term of a `MatchError` can hold one. Plugin code that writes the text runs so that its failure gives no stacktrace text: the `message/1` of the exception is called directly, not through `Exception.message/1`, and `inspect/2` runs with `safe: false` in a catch. Text that plugin code writes is plugin text, with a stack or not: a string reason, a string in the reason, an exception message, and `inspect` output of a plugin struct. Core does not scan text for a label such as `Stacktrace:`, because a label does not prove a stack and a valid message can hold it. The text has its bound. Source: #509, the Codex gate round 1 and its rerun rounds 1 to 3, where a list of crash shapes took a finding in each round; #535; #633, where the scan of the label cut a valid message.
- No `inspect` and no `Exception.format` of a term that can hold a stacktrace, a pid, or a plugin struct (an exit reason, a raised or thrown value, a plugin return outside the contract, a plugin handle, a start error with no clause of its own) goes into a tool result, a client event, or the stderr text of the coding agent, except through `Helyx.Reason.text/1`. A plugin return outside the contract and a plugin handle get a fixed text. The log of a session gets the kind of the term (`Helyx.Reason.log/2`), and a handle keeps its term (`Helyx.Reason.log_term/2`). Source: #535, #756.
- A plugin value that ends a deadline (a prepare Task that cancels its armed kill, a reply that a phase waits for) is checked before the cancel. An invalid value takes the failure path of that deadline. A value equal to a sentinel of the waiting state (nil for "not ready yet") never reaches that state, or the phase waits with no deadline. The failure-path review sends nil, a forged struct, and a wrong field type through each plugin callback of the change. Source: the Codex round 1 finding of #199.
- Tool call arguments that are not a plain map, such as raw text that is not a JSON object, fail the turn through the generic path (`docs/features/rejected-tool-call.md`, #636). No transcript entry, session file entry, or error holds the raw text; Core's own errors name such a call with `%{}` (#380). A reply that `Helyx.Provider.Loop` holds and that stopped at `:max_tokens` runs none of its calls (#494).
- A plugin callback that runs at start (a provider `id/0` at Core start, a tool spec callback at session start or resume) has its return value checked: a bad value is `{:error, reason}`. A tool's `check/0` and `concurrent?/0` get the generic answer: a value outside the contract raises in the caller, as a raise does. Its raise, throw, or exit is not contained and goes to the caller of `Helyx.Core.start_link/1`, `Session.start/2`, or `Session.resume/2`. Core does not check that a plugin exports the required callbacks of its interfaces; a missing callback fails where it is called. A provider `id/0` runs once, at Core start, and a bad or a shared id stops the start (#169); `Helyx.Provider.find/2` calls no plugin code. Source: #142, #169; #632 removed the containment.
- A plugin check that can fail a session start or resume runs in the `with` chain of `Session.start/2` and `Session.resume/2`, before the sessions directory is read and before any file or process is created. The tool `check/0` runs there through `Helyx.Tool.check_available/1`, right after `Helyx.Tool.specs/1`, and `concurrent?/0` through `Helyx.Tool.concurrent/1` right after it; the hands do not run them. With `:id` and no `:cwd`, `Session.resume/2` reads the folder from the header in its pick, after these checks (#758); the order is in `docs/features/server-management.md`, "Order of the checks". Accepted (#104): `resume/2` resolves the model ref (`Helyx.Provider.find/2`) after the read of the file (`Helyx.Session.File.resume_picked/3`, in the session process since #589, after its `init/1` since #605), because the ref comes from the file, so a failed provider check on resume can leave a repaired file. The repair only appends a missing newline (`Helyx.Session.File`), so nothing is lost. Source: #150 and its round 2 failure-path review.

## Tools and hands

- A tool Task that dies without a result still produces a tool result, with `is_error` true.
- The tool calls of one assistant message start in call order. Only calls of tools whose `concurrent?/0` is `true` run together; a tool that writes declares no `concurrent?/0` (`docs/features/concurrent-tool-calls.md`).
- Truncation holds for trailing blank lines, for a line exactly at the byte limit, and cuts on a character boundary.
- Two tools with one name are rejected at session start.
- Truncation holds when one line is larger than the byte limit.
- A `rescue error in ErlangError` also catches the exceptions that the BEAM normalizes, such as `SystemLimitError` and `ArgumentError`, and these have no `:original` field. Format a caught exception with `Exception.message/1`, never with a field of one exception type (#141).
- A tool never loads unbounded input or buffers unbounded output. A model-chosen path can be a device or a huge file; a command can write forever. A result that dropped output says so.

## Tests

- A change to how a test waits keeps what the test checks. When a poll or a sleep is replaced by an event wait, the exit condition of the old poll (for example `map_size(state.held) >= n`) stays as an assertion after the new wait. For each removed wait, the spec axis names the assertion that replaces its exit condition, and a mutation that breaks that condition still fails the test (#264).
- An option with two forms (a value and a closure) has a test of each form through each start path: `start_link/1` and a supervisor child spec. Source: #763, gate round 1 (`child_spec/1` wrapped a closure token twice), constructed.
- A test of a limit runs on a resource that holds nothing else (its own connection or session), so its setup takes no slot. Source: #769 (a worker of the setup still held a slot when request 16 came), observed on the precommit host.
- A count of log lines in an async test counts only the lines of its own process: `with_log/2` with the `pid` metadata. `with_log` and `capture_log` catch the lines of every process in the node. Source: #738, observed in a #660 precommit run.
