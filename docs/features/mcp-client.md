# MCP client and tool search

Status: design, ticket #492 with #473 folded in (owner decisions of 2026-10-23 and 2026-11-06: feature doc first; tool search comes with the MCP client; the tool source inside the Tool interface and the restart after a call with no response are accepted, decisions 3 and 14). No code yet; "Slice order" lists the build.

## Goal

The user names MCP servers in a config file. Their tools reach the model as Helyx tools, on every provider, without filling the context window: the model sees a search tool, and a tool's schema goes to the model only after a search finds it.

Facts about other MCP clients and about tool search are in `docs/research/mcp-client.md`; the decisions below stand on Helyx reasons.

User stories:

- I add a server to `~/.helyx/mcp.json` and start a session. The model sees `tool_search`. When my task needs the server, the model searches, the matching tools load, and the model calls them by name, as it calls `read`.
- My config names 10 servers with 300 tools. The first request of a session holds the bundled tools and `tool_search`, not 300 schemas.
- A server's command is wrong. The session starts as before; a search answers that the server failed, with the reason, and the other servers work.
- A server crashes in the middle of a session. Its open call ends with an error that says the call may have run; its tools leave the session; nothing restarts it.
- I resume a session in which the model loaded three tools of a server. After the resume, the three tools are loaded again once the server lists them.

### Decisions

1. **Config: one user file, JSON.** The MCP plugin reads `~/.helyx/mcp.json` at each session start and resume. A product sets another path with the application env key `:mcp_config` of `helyx_plugins`, as `:memory_markdown_dir` sets a folder (`plugins/bundled/lib/helyx/memory/markdown.ex:222`). Reason: Helyx already parses JSON and keeps user state under `~/.helyx`; a file read per session start makes a config change apply to the next session with no reload command. Helyx reads no project file of servers: a project file would start programs that a cloned repository names, and Helyx has no trust gate (#503). That waits for #503; see "Out of scope".
2. **Config shape.** `{"mcpServers": {"<name>": {"command": "...", "args": [...], "env": {...}, "disabled": false}}}`. The key `mcpServers` and the keys of a server are the shape that server READMEs give for copy and paste, so a user pastes a snippet unchanged. Helyx ignores a key that it does not know. A server with `url`, `httpUrl`, or `type` other than `"stdio"` is skipped with a reason: Helyx speaks stdio only (see "Out of scope"). Decided in slice 7 (`Helyx.Tool.MCP.Config`): a missing file names no server and gives no notice; a file that is not UTF-8, not a JSON object, has an `mcpServers` that is not an object, or repeats a key at any depth (the decoder fails closed, `Helyx.JSON.decode/2`) is refused with one notice, and one with no `mcpServers` names no server. A server with `"disabled": true` is skipped with no notice and takes no place among the 16; the first 16 other servers by name order are checked, so one that fails a check keeps its place, and the rest are skipped with one notice; a `disabled` that is not a boolean skips that server. A notice names a server or an env variable by `inspect/1` of its first 64 bytes, never by an env value. The bounds of `args` and `env` are per item: a file of 64 KiB holds fewer at their largest size.
3. **One Tool plugin, `Helyx.Tool.MCP`, as a tool source.** Accepted by the owner on 2026-11-06 (#492): `announce/1`, `put_tools/2`, a per-session tool registry, and `context().source`, with no sixth interface. A Tool plugin today is one module, one tool, with a fixed name (`lib/helyx/interfaces/tool.ex:52-65`). The MCP plugin learns its tools only after it starts the servers, so the Tool interface gains a second kind of plugin, the **tool source**: a plugin that runs one process per session in the hands and offers tools that it learns at run time. Each MCP server runs in a server Task of the hands that the source starts with `launch/1`. Reason: the hands already hold every OS process of a session (ADR 0004); a server Task holds its server's groups with `Helyx.Tool.hold/1` through `Helyx.Watchdog.start/4`, and the hands release them when the Task ends and at the stop of the session, as they release a provider process. No new interface: a source is a Tool plugin, so ADR 0009's extension surface stays.
4. **A session's tool set changes during the session.** The session keeps a **registry**: every tool it can run, from the fixed tool plugins and from the sources. Each entry has an **exposure**, `direct` or `deferred`. The **active set** is the direct tools plus the deferred tools that a search **activated**. A provider gets the specs of the active set, sorted by name. Reason: the session is the one process that sees the registry, the provider requests, and the tool calls, so it alone can keep the three in step.
5. **MCP tools are deferred, always.** Reason: the bytes of a server's tools are known only after it starts, so a threshold would make the first request depend on how fast the servers started; a fixed rule keeps the first request the same on every start and resume. A server's tools cost the context nothing until the model searches.
6. **Search is a plain Tool plugin, `Helyx.Tool.ToolSearch`, named `tool_search`.** It ranks the deferred tools of the registry by BM25 over the name, the description, and the parameter names and descriptions, and activates the matches. An empty query lists the groups (servers) with their state and tool count. Reason: the search reads only the registry, so it serves any source, not only MCP; it is a fixed tool, so it is in the first request.
7. **An activation is a session log entry, `tools_change`.** It holds the full list of activated names after the change, so a resume restores it by the last entry, as `model_change` restores the model (`lib/helyx/session/file/reader.ex:96-97`). The registry is not written: a resume starts the servers again and lists their tools. Reason: the activation is what the model saw and what it decided; the registry is the servers' state, which a restart gives again.
8. **Unique names.** An MCP tool is `<server>__<tool>`. A server name matches `^[a-z0-9][a-z0-9-]{0,15}$`: it has no `_`, so the first `__` ends the server part and two servers never give one name. Each character (Unicode code point) of the tool name outside `[A-Za-z0-9_-]` becomes `_`; two names of one server that map to one name of 52 bytes or fewer are one name, and Core refuses the second, below (decided in slice 7). A name over 52 bytes keeps its first 43 bytes, then `_`, then the first 8 hex digits of the SHA-256 of the MCP tool name. Core rejects a source tool whose name is in the registry already (a fixed tool, or another group's tool), with a notice; the earlier one stays. Reason for 52: every tool name, fixed or not, matches `^[A-Za-z0-9_-]{1,52}$` from now on (slice 1). The smallest name limit that a Helyx provider is known to have is 64 (OpenAI function names; the Codex rule `^[a-zA-Z0-9_-]+$` is in `docs/research/codex-app-server.md:42`), and Claude Code shows a Helyx tool as `mcp__helyx__<name>`, 12 bytes more (`plugins/bundled/lib/helyx/provider/claude_code/mcp.ex:22-23`): 52 + 12 = 64.
9. **A failed or dead server.** No restart after a failure, and no retry of a call. A server that does not finish its start in 30 s, or exits, or breaks the protocol, is **failed**: its tools leave the registry, its open call gets an error result, and a search names it with the reason. Reason: a `tools/call` can have side effects, so a retry can run it twice; a server that crashed once tends to crash again, and a restart loop costs the user processes and tokens with no answer. A new session or a resume starts it again. One case is not a failure: a call that ends with no response (decision 14).
10. **Providers that resend and providers that render.** A model provider (`Helyx.Provider.Loop`) gets a fresh context for each model call (`lib/helyx/provider/loop.ex:41-42`), so it sends the active specs on each call: a tool that a search activates is callable at the next model call of the same turn. Before slice 6 a harness provider got its tools once per program or thread (`claude_code.ex` `init/3`, `codex/program.ex` `open_thread/1`). From slice 6 it compares the tools of each `{:turn, ...}` context with the tools of its program, and a change takes effect at that turn start, through the path that a prompt change takes today (`docs/features/provider-parity.md`, "The prompt"): Claude Code restarts its program with a resume of its harness session and the new tool list; Codex starts a fresh thread with the replay, because a thread's tools are fixed at `thread/start` (`docs/research/codex-app-server.md:128-129`) and its stored id already holds a digest of the tools (`codex/program.ex:46-58`). So on a harness provider a tool that a search activates is callable from the next turn. Reason: both paths exist and are tested; an in-turn path for a harness is an open research question (`docs/research/mcp-client.md`, "Open questions") and needs an observed run with a real program before any build. Decided in slice 6: the comparison is of the exact list of specs, sorted by name as the session gives it, so a changed schema or description is a change too; on Codex a first turn with other tools than `init/3` replaces the program, because its `initialize` and its stored id hold the old tools (`docs/features/provider-parity.md`, "The prompt").
11. **No source in a session that names its tools.** A session started with `:tools` (the child sessions of the agent tool, `plugins/bundled/lib/helyx/tool/agent.ex:54,63`, or a product that picks tools) opens no source. Reason: each child would start its own copy of every server, and a source process belongs to one session's hands, so it cannot be shared. The agent tool leaves `tool_search` out of the list of a child (slice 10).
12. **The environment of a server.** A server gets `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER`, `TMPDIR`, and `LANG` of the node, then the `env` of its config; every other variable of the node is unset for it. Reason: a server is a third-party program, and the node's environment holds the provider keys. The values of `env` are never logged and are masked in a start error, as the harness providers do (`docs/features/harness-no-state.md`, "Never logged"; `Helyx.Watchdog.start/4`, option `:env`).
13. **The config file must not be writable by others.** A file whose group or other write bit is set is refused, with one notice, and no server starts. Reason: the file names programs to run, the same reason the server refuses a data folder that the group or other users can write (`docs/features/serve.md:53`).
14. **A call that ends with no response restarts its server.** Accepted by the owner on 2026-11-06 (#492), in place of the rule to stop the server for the rest of the session, with the loss of the server's memory state as a stated hole ("Accepted holes"). At the time limit of a call, and when an abort kills the call Task, the server Task sends `notifications/cancelled` and ends; the hands release its process group, which kills the server; the source launches a new server Task, as at the session start, only after the hands' release message for the old Task (`launch/1`), not at its `:DOWN`: the `:DOWN` comes when the Task ends, before the hands got their own and ran the release, so a new server could start while the old group still runs. The call is not run again. Reason: MCP gives no confirmation that a cancelled request stopped (the SDK server only aborts a signal, `docs/research/mcp-client.md`), so a server that stays up can run the cancelled call while the next one starts, and repeated cancels pile up calls with side effects. The kill of the group ends any handler. A server restarts this way at most 3 times per session; at the fourth call that ends with no response it is failed, as in decision 9, so a server that never answers cannot loop.
15. **One server's failure stays with that server.** Each server has its own server Task, which owns its port. The source traps exits, so the exit of a server Task, to which it is linked (`launch/1`), is a message to it, not its end. An exit of that port, such as the `:epipe` of a write to a dead watchdog (`plugins/bundled/lib/helyx/watchdog.ex:291`, `plugins/bundled/test/helyx/provider/harness_epipe_test.exs`), ends that Task only: the hands release its group, the source sees the `:DOWN` and fails that server. The source holds no port. Reason: a port linked to a process that holds the ports of other servers would take their tools with it.

## Interface changes

### `Helyx.Tool` (Core)

- **Two kinds of Tool plugin.** A fixed tool exports `name/0`, `description/0`, `parameters/0`, and `run/2`, as today. A tool source exports `source/1` and `run/2`, and none of `name/0`, `description/0`, and `parameters/0`. Core checks each Tool plugin at its start: any other plugin, one with no `run/2` too, gives `{:error, {:invalid_tool_plugin, module}}`, next to the existing checks of `Helyx.Core.Plugins`. `Helyx.Tool.specs/2` skips the sources.
- **Name rule.** `Helyx.Tool.specs/2` accepts a name only when it matches `^[A-Za-z0-9_-]{1,52}$`; another name gives `{:error, {:bad_tool_spec, label}}` as a bad name does today (`tool.ex:102-114`). The bundled names (`read`, `bash`, `edit`, `write`, `agent`, `skill`, `question`) pass.
- **`source(info)` (new optional callback).** The session calls it in a new Task of its hands, the **source process**, once per source plugin, after the hands start (`lib/helyx/session/server/open.ex:188`), at a start and a resume of a session that has no `:tools`. `info` is `%{core, session_id, cwd}`. The Task runs for the life of the session: it is not a tool call, it counts against no call cap, and an abort of a turn does not touch it. Its handles, held with `hold/1`, are released when it ends and at the stop of the session, as those of a provider process (`tool.ex`, `hold/1`). When it ends, the session removes every group that it put, with one notice per group.
- **`launch(fun)` (new).** Called from a source process. An asynchronous request, as `Helyx.Session.Hands.start_provider/3` is (`lib/helyx/session/hands.ex:82-86`, a cast with a ref): it returns a ref at once and never waits for the hands. The hands handle the request after the messages before it, and a release of a delivery runs in the hands' own process for up to `release_ms`, 20,000 ms (`hands.ex:302-308`), so the answer can come late; no wait of the source depends on it. The hands start `fun` in a new Task, a **server Task**, whose tool is the plugin of the source, so its `hold/1` calls are kept and the plugin's `release/3` frees them, and send the source `{ref, {:ok, pid}}`, or `{ref, {:error, reason}}` when they refuse it: a handle is unconfirmed (`docs/features/tool-resource-release.md`, rule 6), or the source has 16 server Tasks. The server Task's first act, before `fun` runs, links it to its source; a link to a source that is gone already ends it at once. The server Task does not trap exits, so the exit signal of its source ends it even while it is blocked, in `let_go/2` for example, where it could not handle a message; a source's kill timer dies with the source, and the link takes its place. The source traps exits, so the exit of one of its server Tasks reaches it as a message (decision 15). Core ends a source when its hands end: a guard process that monitors both kills the source, because a trapped exit signal of the hands would only be a message that plugin code may never read. Any other exit signal but a kill reaches the source as a message too, and a contract of a tool source is that its loop ends at an `{:EXIT, pid, reason}` from a process that is not one of its server Tasks. A server Task's exit and the hands' `{ref, {:ok, pid}}` come from two senders and have no order, so an `{:EXIT, pid, _}` of a pid that the source has not learned may be of a server Task whose answer is on its way: while a launch is open, the source takes the hands' answers before it decides (decided 2026-11-07 on #492: the link-and-trap design stays, and the doc follows the code; the MCP plugin of slice 10 is checked against it). The hands run `source/1` in a Core wrapper that ends its Task with `:shutdown` when it returns, and also when it calls `exit(:normal)`: the wrapper catches that exit and exits with `:shutdown` in its place. So a source never ends with `:normal`, which a link would not pass on, and a linked server Task never outlives its source. When the hands have run the release of a server Task's handles, after its end however it ended, they send the source `{ref, :released, outcome}`, with outcome `:ok`, or `:unconfirmed` when a handle stays unconfirmed; then the hands refuse every later tool call and launch request, as for any tool (`docs/features/tool-resource-release.md`, rule 6). The source keeps each server's deadline on its own timer, set when it sends the request, and gives the absolute deadline to `fun`, so no wait in the hands can move it. An answer `{:ok, pid}` that comes after the timer of its server fired gets that Task killed, and the hands release its handles. Like the source process, a server Task is not a tool call, counts against no call cap, and an abort of a turn does not touch it. The hands release its handles when it ends, however it ended, and at the stop of the session. A source has at most 16 server Tasks and launch requests together: one per server, because the source sends a server's request only when that server has neither a Task, nor an open request, nor a release that it waits for (a restart waits for the release message of the old Task). The hands answer a request past 16 live server Tasks with `{:error, :too_many_tasks}`. Exits outside a source process.
- **`announce(groups)` (new).** Called once from a source process, before its first `put_tools/2`: the names of all its groups, possibly none, each put as `:starting`. It returns `{:ok, kept}`, the groups that the 64-group cap of the session kept: the room that earlier announces left takes the first of this announce by name order, so a source never puts to a dropped group; a notice names the rest (decided 2026-11-07 on #492: with two sources a source cannot know its room from its own groups). From the start of its Task until this call a source is **pending**. Reason: the session starts the Task before the source has read its config, so without it a search that comes first would see no group and not wait. A second call, or a `put_tools/2` before it or to a group that it did not keep, exits the caller.
- **`put_tools(group, value)` (new).** Called from a source process. `group` is a group that `announce/1` kept. `value` is `:starting`, `{:ok, entries}`, or `{:error, text}`. An entry is `%{name, description, parameters, exposure}` with exposure `:direct` or `:deferred`. It replaces the group's entries; `{:error, text}` removes them and keeps the text for the search. The session checks each entry at this boundary, rejects the smallest unit (one entry) with a notice, and keeps the rest; see "Bounds". A group that would pass the registry's tool cap is rejected whole, with its own `{:error, text}`. Exits outside a source process.
- **`deferred(version, wait_ms)` (new).** Called from a tool call. Returns the registry's `version`, a counter that each `announce/1`, `put_tools/2`, and end of a source raises, the deferred entries, the activated names, the state of each group (`:starting`, `:ready`, or `{:error, text}`) with its tool count (decided in slice 5, for the empty query of `tool_search`), and the pending sources. It answers at once when the registry's version is above `version` (nil asks for the current state at once); else it waits for the next change or until `wait_ms` passed, at most 30,000. The version makes a change between two calls answer at once, so no change is missed. The search tool decides when to wait, so a ready group answers at once whatever another group does.
- **`activate(names)` (new).** Called from a tool call, with the names in rank order, best first. The activated list is kept in **drop order**: the front leaves first. `activate/1` takes the registered deferred names among its names, removes them from where the list holds them already, and appends them in reverse rank, the lowest ranked first and the best last. Then it applies the cap of "Bounds" by dropping from the front. So the names of older calls leave first, and among the names of this call the lowest ranked leave first: when this call's names alone pass the cap, it keeps its best matches. The `tools_change` entry holds the list in this order, so a resume keeps it. Writes one `tools_change` entry and emits one `:tools_change` event when the list changed. Returns the activated list. A name that is not a registered deferred tool is ignored.
- **The cap after every change.** The byte cap of the activated list counts the spec JSON of the names that the registry holds now, so a `put_tools/2` with larger schemas, or a group that lists its tools after a resume, can pass it. The session applies the same cap after each `put_tools/2`, by dropping from the front of the list in its drop order, so the same order holds: older activations first, and within one activation the lowest ranked first, and writes a `tools_change` entry and a `:tools_change` event with a nil turn id when that drops a name. So no context holds more activated spec JSON than the cap.
- **`context/0`** gains `source`: the pid of the source process of the called tool's plugin, or nil. An MCP tool's `run/2` reads `context().tool` for the name that was called and `context().source` for the process that owns its server.

### The session (Core)

- The state fields `tool_specs` and `tools` (`lib/helyx/session/server/state.ex:76-77`) become the registry and the activated list. The base context of each provider call holds the active specs, sorted by name (`prepare.ex:37` today holds all specs). A ModelContext plugin can still change them on one call (`lib/helyx/session/stream.ex:84-89`).
- The hands' map of tool name to module (`open.ex:249`) follows the registry: the session sends each change to the hands before it builds any context that holds it. Both messages go from the session to the hands, so a tool call of a model that saw a tool reaches hands that know it. A call of a name that is no longer registered gets the error result `unknown tool: <name>`, as today (`lib/helyx/session/hands.ex:354-356`).
- `{tools, concurrent}` of `Helyx.Session.start/2` and `resume/2` (`lib/helyx/session.ex:89-100,131-138`) stays the fixed tools; source tools are never concurrent. Reason: an MCP tool's `readOnlyHint` comes from the server and nothing checks it.

### Event and session file

- **Event `:tools_change`**, `%{activated: [String.t()]}`, with the turn id of the call or hook that activated while it runs in that turn, else nil: a background run left its turn, and the cap after a put has none (decided in slice 3).
- **Entry `tools_change`**: `{"type": "tools_change", "activated": [...]}`, plus the `id`, `parent_id`, and `ts` that every entry gets (`lib/helyx/session/file.ex:386-398`). The reader folds it as it folds `model_change`: the last one gives the activated list. Names that no source registers yet stay in the list and are sent once their group lists them.
- **An older Helyx and this entry.** The reader of today returns `{:error, {:invalid_file, "entry the writer never produces: \"tools_change\""}}` for an entry type it does not know (`reader.ex:128-129`), so an older Helyx refuses to resume a file that holds a `tools_change` entry. The refusal changes nothing on disk, and the file resumes again in a Helyx that knows the entry. The header version stays 1: a version 2 would make an older Helyx refuse every new file, also those with no activation. The rewrite of #834 keeps this rule for unknown entries (branch `ticket/834-resume-reads-all` at `7c9403de`, `reader.ex:227-228`), so slice 3 adds its fold clause to whichever reader is on master then; this run changes no file of `Helyx.Session.File`.
- **Snapshot** gains `activated`, the same list.
- **Wire.** The event and the snapshot field enter the schema of `docs/features/wire-protocol.md`, with a new protocol number, as the schema test of #660 requires (ADR 0008): protocol 8, after the protocol 7 of #870 (the schedules of a Hub). A client of the old number is refused with `4426`, as for any schema change.

### `Helyx.Tool.MCP` (bundled, `plugins/bundled/lib/helyx/tool/mcp.ex`)

A tool source. Its `check/0` reports a missing `perl`, as the bash tool does (`plugins/bundled/lib/helyx/tool/bash.ex:101`). Its source process reads the config, calls `announce/1` with the names of the servers that passed the checks, and starts one server Task for each of them. A server Task starts its server through the watchdog (input `:open`, stderr to `/dev/null` as `Helyx.HarnessIO.launch/4` does) and speaks JSON-RPC 2.0 over stdin and stdout, one JSON message per line, in the steps below.

**Each server runs in its own server Task.** `Helyx.Watchdog.start/4` blocks its caller until the watchdog's marker, and two of its waits have no time limit: the marker read (`read_marker/4`, `plugins/bundled/lib/helyx/watchdog.ex:324-336`) and the read of a failed start's reason up to the exit status (`read_to_exit/2`, `watchdog.ex:216-220`). The release of a failed start (`let_go/2`, `watchdog.ex:190-210`) runs `kill(1)` through `System.cmd/3` with no timeout of its own (`plugins/bundled/lib/helyx/watchdog/group.ex:108-116`). The hands accept a `hold/1` only from one of their Tasks (`lib/helyx/session/hands.ex:142-147`; a hold from another process is dropped), so the launch cannot move to a plain process. It moves to a Task of the hands instead: the source starts each server with `Helyx.Tool.launch/1` (slice 2), and the **server Task** runs the whole life of that server. It calls `start/4`, holds the groups there, owns the port, and speaks the JSON-RPC below. Every wait of the start path then blocks only that Task, so a stalled start holds no other server's start, and the source loop only receives results: the server Task sends its listing to the source, and the source calls `put_tools/2`.

The start path gets two changes in slice 9, both in `start/4`, both behind a new option `:deadline`, an absolute `System.monotonic_time(:millisecond)`, default none, so the bash tool and the harness providers do not change:

- The marker read and the reason read wait only until the deadline. When it passes, `start/4` closes the port, lets the watchdog go as a failed start does today, and returns `{:error, "the perl watchdog gave no marker before the deadline"}`.
- After the marker, `start/4` holds the command group (`watchdog.ex:175-176`) and then checks the deadline again, before it writes the go-ahead (`watchdog.ex:177-179`). Past the deadline it closes the port and returns the same error, so the go-ahead never goes out late. The watchdog holds the command until the go-ahead (`watchdog.ex:18-19`), so a start that passed its deadline never ran the server; the held handles stay with the Task, and the hands release them when it ends.

The server Task passes to `start/4` the absolute deadline that the source set when it sent the launch request: 30,000 ms from that send, so a late start of the Task by the hands shortens its time and never lengthens it. When `start/4` returns an error, the Task sends it to the source and ends; the hands release its handles with the release deadline, the same release as at the end of a provider process (`hands.ex:302-308`, `Release.run/4`, whose Task the hands kill at the deadline, `lib/helyx/session/hands/release.ex:8-9`). The cleanup of `let_go/2` runs in the server Task, so a stalled `kill(1)` holds only that Task. The source keeps a timer of 30,000 ms for each server, from the send of its launch request to the last page of `tools/list`; when it fires, the source kills that Task, or, with no answer of the hands yet, kills the Task that a late answer names, and the hands release its handles. The waits that no deadline covers: `Port.open/2`, a spawn by the OS that Helyx does not time; the `hold/1` and `unhold/1` calls to the hands, which wait behind the releases that the hands run one at a time, each within `Helyx.Session.Hands.State.release_ms/0` (`docs/features/tool-resource-release.md`, row "release deadline"), as every hold of a tool does today; and the `kill(1)` runs of `let_go/2`. All three block only the server Task, and the source's timer ends that Task at 30 s.

1. `initialize` with protocol version `2025-06-18` and no client capability (no roots, sampling, or elicitation). The server's answer must name a version of `2024-11-05`, `2025-03-26`, `2025-06-18`, or `2025-11-25`; another fails the server.
2. `notifications/initialized`, then `tools/list`, following `nextCursor`. A tool whose `execution.taskSupport` is `"required"` is left out, with a notice: Helyx sends plain `tools/call` requests only, and the SDK server refuses those for such a tool (`server/mcp.js:116-118` of the SDK copy that the research note names). Then `put_tools(server, {:ok, entries})`, every entry deferred.
3. A `tools/call` from `run/2`: the call Task asks the source process, which passes it to the server Task of that server; the server Task sends the request, monitors the call Task, and answers it. At the time limit the call gets an error result that says the call may have run, and the server Task cancels as decision 14 says. When the call Task dies (an abort kills it), the server Task sees the `:DOWN` and cancels the same way.

   **An abort waits for the server's group.** An abort returns only after every call of the turn is released or recorded as unconfirmed (`docs/features/tool-resource-release.md:20`), the contract of every tool; the hands do not change. So the call Task holds a handle of its own, and the group gets one release right that both handles name.

   - **One release record per group, in `Helyx.Watchdog` (slice 8, owner decision of 2026-11-06 on #492).** Every group that `Helyx.Watchdog.start/4` makes, the watchdog process and the command group, gets one release record, and its handle carries it: `{:watchdog, os_pid, record}` and `{:command, group, record}`. `Helyx.Watchdog.Group.release/4` takes the record before any signal, on every path: the `release/3` of `bash` and of the MCP plugin, `let_go/2`, and the cleanup of a failed start. The release that takes it signals; a release that finds the group confirmed gone sends no signal and confirms; one that finds the record taken waits for that release's outcome or for its lease, the deadline of that release, and sends no signal while it waits. So each group gets signals from one release at a time, and a number that the OS gave to a new group after a confirmed release is never signalled. The rule, with its states, is in `docs/features/tool-resource-release.md`, "The release record", because it covers `bash` too. The MCP plugin keeps no record of its own and gives `start/4` no option for it.
   - **The call handle.** The server Task reports the handles of its server to the source after its start, and the source gives them to a call Task with the route. Before the call Task passes its request on, it holds `{:mcp_call, handles}` with `hold/1`: the same handles, with the same records.
   - **At an abort** the hands kill the call Task and release `{:mcp_call, handles}` with `:cancel` (`lib/helyx/session/hands.ex:213-224`); the plugin's `release/3` gives the handles to `Group.release/4` (TERM, the grace of 2,000 ms, KILL). That release takes the records and stops the server's groups, so the abort returns with the groups stopped, or with the handle unconfirmed and the hands refusing later calls (rule 6), as for `bash` today. It does not wait for the server Task: a server Task that is suspended, or that has not handled the `:DOWN` yet, does not hold the abort. When the server Task later ends, the hands release its own handles; their records say confirmed gone, so that release sends no signal, and the hands send the source the release message, after which decision 14 starts the server again. A wait in the abort for that release message could not work: the abort runs in the hands' own process (`hands.ex:193-200`), and the release of the server Task's handles needs that process.
   - **At a delivery**, `release/3` with `:deliver` returns `[]` for `{:mcp_call, handles}` and does not call `Group.release/4`: the call ended, and the server Task still holds its groups. A time limit or a restart (decision 14) ends the server Task, and the release of its own handles takes the records.
   - **Rule 9 holds as written.** `Helyx.Tool.unhold/1` drops only handles whose resources the caller released itself, and only those that the release confirmed (`docs/features/tool-resource-release.md`, rule 9). The MCP plugin never unholds a handle of a server group: each one leaves the hands by the return of `release/3` (rule 2), and the record of `Helyx.Watchdog` decides which release signals. `let_go/2` still unholds only what its own release confirmed (rule 9); a server Task killed between that release and its `unhold/1` keeps the handle in the hands, whose later release finds the record confirmed and sends no signal. The hands do not change: they release each Task's handles as today, one `Release.run/4` at a time in their own process (`hands.ex:223,305`), so two releases of one record never run at once. Only the record of the aborted call's server is in the handle, so the other servers keep running. A call of a server that is restarting waits in the source for the new server Task's start, within the call's own time limit.
4. A result becomes text: each `text` block as is; an `image` or `audio` block as the line `[image <mimeType>, <n> bytes, not shown]`; a `resource_link` as `[resource <name>: <uri>]`; an embedded resource as its text, or `[resource <uri>, <n> bytes, not shown]` for a blob; with no content block, the JSON of `structuredContent`. Blocks join with a newline. `isError: true` gives `{:error, text}`. The hands cut the text to `Helyx.Message.max_result_bytes/0`, head and tail kept (`lib/helyx/data/message.ex:266-292`).
5. `notifications/tools/list_changed` lists the tools again and puts the group again. A listing that does not end within 30,000 ms fails the server, as a start does. A request of the server gets the JSON-RPC error `-32601`, but `ping`, which gets `{}`. Any other notification is dropped.

### `Helyx.Tool.ToolSearch` (bundled, `plugins/bundled/lib/helyx/tool/tool_search.ex`)

A fixed tool, `tool_search`, with `query` (a string) and `limit` (an integer, default 5). It calls `deferred(nil, 0)` and ranks the entries of the ready groups. It answers from them when it has a match, or when no group is `:starting` and no source is pending. Only with no match while some group is `:starting` or a source is pending does it wait: it calls `deferred/2` again with the last version and the time left of 30,000 ms from its first call, and ranks again after each change. So a search never waits for the start of a server that stalls; it can wait behind a stalled call, as every call can ("Accepted holes"). Then it calls `activate/1` with the matches, and answers with one line (`name: description`) per loaded match ("The answer" below), a line that names the other matches, and a last line that says that the listed tools are callable from the next model call. An empty query activates nothing and answers with the groups. An exact name in the query ranks first.

Decided in slice 5, inside this design:

- **Words.** The words of a text are its runs of letters and digits, split where a lower case letter meets an upper case one, in lower case, so `docs__search_files` and `getPage` give `docs`, `search`, `files`, `get`, `page`. The text of an entry is its name, its description, and the property names and descriptions of its parameters at any depth. BM25 runs with k1 = 1.2 and b = 0.75 over the deferred entries of the registry, and an entry with a positive score matches. A rank reads at most 1,024 entries of at most 4,096 bytes of description and 16,384 bytes of parameters; one look over 1,024 entries at these bounds took about 4 s of CPU in the tool Task (the failure-path review of slice 5, 2026-11-08, the dev machine). The deadline is checked after each look, before each wait, so a look that starts before the end of the 30,000 ms runs to its end; a later look reads only the entries that changed.
- **Exact names.** A word of the query, split at whitespace, that is the name of a deferred entry ranks that entry first, in the order of the query; the other matches follow by score, highest first, then by name.
- **The end of the wait.** A `deferred/2` that answers with the version that the search gave it ends the wait: its bound passed, or 32 callers wait and the session answered at once, so no search loops on it.
- **`limit`.** null is the default, 5.
- **The answer.** A match is loaded when one `deferred(nil, 0)` after the activation holds it in its entries and in its `activated` list: the activated list keeps the names of a group that emptied since an earlier activation, and a put after the activation can drop a name by the cap, so the list that `activate/1` returns does not show it (two findings of the slice 5 review). The match lines and the state lines come from that view, so the answer is the state of one moment. A match that turned direct since the look shows as not loaded, though the tool list holds it. One line per loaded match, `name: description`, the description cut to 1,024 bytes; a line `Not loaded, by the cap of loaded tools or a change of their group: <names>.` for the other matches; `Groups still starting: <groups>.`; `Tool sources still starting: <sources>.`; one `Group <group> failed: <text>` per failed group, as decision 9 asks; and the last line. Each run of line breaks of any kind that Unicode names, in a description, a group name, or a failure text, becomes one space, so a text of a source stays on its line. With no match, `No tool matches the query.` and the state lines. A failure text is cut to 512 bytes, so the answer stays below `Helyx.Message.max_result_bytes/0` and the hands never cut it: their cut marker could start a line with a source's text (the slice 5 review). The answer holds at most 10 match lines of 1,078 bytes, the left-out line of 10 names, and at most 591 bytes for each of 64 groups (a failed group's line; a starting group takes 66 bytes of the shared line), about 50,000 bytes, and the labels of the pending sources, `inspect/1` of each source plugin that has not announced. The plugin list of the product bounds those labels, not a source: past about 15,000 bytes of them (the small-fix review of slice 5 reproduced it with 119 source plugins of 236-byte names) the hands cut the answer again. A stated ceiling of the product config. A change after the view (a put, the end of a source, another activation) can change what the next model call holds.
- **The empty query.** A query of whitespace only. One line per group, `<group>: ready, <n> tools` (`1 tool` for one), `<group>: starting`, or `<group>: failed: <text>`, the text cut as above, then the pending sources; with neither, `No tool groups.`

## Replaced mechanism

The fixed tool set of a session.

1. Old: `Helyx.Tool.specs/2` builds every spec once at a start or resume (`tool.ex:85-97`); the private `start_child/3` of `Helyx.Session.Server.Open` stores `tool_specs` and `tools` once (`open.ex:134-151`; the ticket calls it `Helyx.Session.start_child/2`, which does not exist); the hands get a fixed map (`open.ex:249`); every context holds every spec (`prepare.ex:37`); `context().tools` is the keys of the hands' map (`hands.ex:346-351`); harness providers take the specs at `init/3` and never again. New: the fixed tools are built the same way and are direct entries of the registry; the registry changes through `put_tools/2` and `activate/1`; the contexts hold the active set; `context().tools` holds the registered names; harness providers read the tools of each turn context. No reply is removed.
2. The one ordering guarantee that changes: "a tool that the provider was given is in the hands' map". Today it holds because both are fixed at open. After the change the session process, which sends both the hands' map and every context, sends the map first.
3. Tests that assume a fixed set keep their property for the fixed tools: `test/helyx/session/hands_test.exs` (unknown tool), `plugins/bundled/test/helyx/provider/codex/helyx_tools_test.exs` and `claude_code/helyx_tools_test.exs` (the tools reach the program), `test/helyx/session/provider_process_tools_test.exs`. The test of the stored Codex id with a digest of the tools keeps its property; slice 6 adds the change case.
4. Users see: `tool_search` in the tool list of a product that registers it, the `tools_change` event, the snapshot field, and the new protocol number.
5. State with no bound: none new; see "Bounds".

## Accepted holes

- After a resume, a call of an activated tool before its server lists it gets `unknown tool: <name>`; a search waits for the start and loads it again.
- On a harness provider, a tool that a search activates is callable from the next turn (decision 10). The search answer says "from the next model call"; on a harness that is the next turn.
- Each activation changes the tools of the next request, so a provider's prompt cache misses once per activation. The cap of activated names bounds it per session.
- On Codex each activation starts a fresh thread with the replay (decision 10), so the thread's native compaction and its history past the replay cut (400,000 bytes, `Helyx.HarnessIO`) are gone: the model gets the replay of the Helyx transcript, which holds no compaction summary (`docs/features/harness-compaction.md`). Found in the slice 6 review; it follows from decision 10.
- An abort or a time limit during an MCP call restarts that server, so the server loses the state it held in memory, a browser page for example (decision 14, accepted by the owner on 2026-11-06).
- The start of a server may wait for releases in the hands: its `hold/1` and `unhold/1` calls, and the answer to its launch request, come after the releases that the hands run before them, at most 20,000 ms (`release_ms`) for each release. So a stalled server delays the start of other servers or the source only through the release of its group in the hands, at most 20 s per release. Accepted by the owner on 2026-11-06 (#492).
- A release in the hands delays a search as it delays every tool call today (ADR 0004): the hands start no call Task while they run `Release.run/4` in their own process (`lib/helyx/session/hands.ex:302-305`). The delay is at most `release_ms`, 20,000 ms, for each release that waits before the call. A stalled server never delays the start of other servers or the source; a release in the hands can delay a search.
- A stalled MCP call delays the other calls of the session and `tool_search`: source tools run alone (`Helyx.Session.ToolQueue` does not change), so they wait at most one call limit, 60,000 ms, behind it, as they wait behind a stalled `bash` call today. Accepted by the owner on 2026-11-06 (#492).
- A search answers from the ready servers as soon as one of them has a match, so a better match in a server that is still starting is not in that answer; a later search finds it once that server is ready.
- A server's stderr is dropped, so a start failure shows the exit status and no log text.
- A server group that the release of the hands cannot confirm gone makes the hands refuse every later tool call of the session, as for any tool that holds a resource (`docs/features/tool-resource-release.md`, rule 6).
- A server process that leaves its process group is not released, the known limit of `docs/features/tool-resource-release.md`.
- The config file is checked by a stat and then opened (`Helyx.Tool.MCP.Config`, slice 7): a file swapped between the two, a group-writable file or a FIFO, passes the mode check or blocks the open, as for every bounded read of `Helyx.Text.read_file/2` (review 2026-09-17-issue-19). Reason: the file is in the user's own folder, and one who can swap it can write it; the mode check guards against a wrong setup, not against that user.
- The server checks see every server of the file: the sort by name and the notice of the servers past the cap cost work in proportion to the file, at most some thousands of servers in its 64 KiB, not to the 16 that start (found in the slice 7 review).
