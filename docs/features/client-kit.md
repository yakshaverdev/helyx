# Client kit

Ticket #860, part of #853. The owner's decisions are in the ticket body and its comments of 2026-11-06. Ticket #931 moved the network layer of the desktop app into a crate of its own and added the bindings for Swift ("The network layer", "Bindings for Swift").

## Goal

An adopter of Helyx gets a cross-platform app from a shared client core and a thin reference app per platform, and needs no client change for a new mode: the logic lives in Helyx Core and the plugins, and the wire conformance fixtures (`test/fixtures/wire/`, #855) are the contract.

Decisions, each fixed by the owner on 2026-11-06:

- **A shared core in Rust**, in `clients/rust/` of this repo, so the fixtures and the client change in one commit. Desktop apps link it; mobile apps call it through generated bindings (#931).
- **GPUI for the desktop, macOS first**, the owner's daily client.
- **The gate is `precommit.sh`**, as for a Mix project. The repo has no CI.
- **Rust is pinned in `.tool-versions`** (`rust 1.99.1`), so `mise exec` gives `cargo` on the owner's Mac and on the precommit host, where `~/.cargo/bin` is not on `PATH`.
- **Auth is the token proof of the wire** (rule O1). Hub auth follows #869.
- **No client extension point** in the first version: a block of a kind that the kit does not know shows its fallback text (#858). A content block of a kind that the core does not know keeps its kind, and a renderer shows a placeholder with that kind. Protocol 5 (#878) adds UI blocks with a fallback `text`: the core checks and holds them (`ui_block`), reads them into the models of the vocabulary (`vocabulary`, #885), and the reference app draws `form` and `approval` natively and any other kind as its text (`docs/features/ui-blocks.md`, "Rendering in the client kit").

## Slices

The ticket is built in this order. Each slice passes the gate; slices 1 and 2 are one commit, and the fixes of their review (cycle A) another.

1. **The gate.** `.tool-versions` pins `rust 1.99.1`. `.claude/skills/ship/precommit-run.sh` runs `mix precommit`, then, for each `clients/*/Cargo.toml`, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, and `cargo test --locked` through `mise exec`. `precommit.sh` runs that file here or on the host. Every step runs; the last line names each step that failed.
2. **The protocol core** (`clients/rust/core`, crate `helyx-client-core`). It does no I/O: a host feeds it the text of each server frame of one connection, and sends the frames it returns.
   - `json`: the JSON of the wire, lossless. The decoder serves these requirements: a number keeps its text, so an integer of a tool call keeps every digit and `1.50` stays `1.50`; no object key has a meaning of its own; a container of any nesting decodes without a stack for it, and no frame overflows the stack; the text of a frame, the values of its tree, and the characters of an integer have the bounds of the table "Bounds", and a text over one is a break; a lone surrogate escape and a text that is not one JSON value are breaks; an object with a repeated key keeps both pairs in their order, and a lookup takes the first, as `JSON.decode/1` of Elixir and `Helyx.Transport.WebSocket.Frame.decode/3` do (probed on 2026-11-06: `{"a":1,"a":2}` gives `a` 1); and `encode` writes a string with the escapes of the OTP encoder, so its bytes are the server's. `serde_json` with the `raw_value` feature serves every one: its parser holds the grammar, the string escapes, and the escapes of the writer, and the decoder reads each value as its text (`serde_json::value::RawValue`), so a number is never a value of its own and a key is a key; a container past 64 levels is kept as that text (`Json::Deep`), which `serde_json` walks with a stack on the heap, so the parse, the clone, the compare, and the drop of a tree recurse at most 64 levels. `decode` holds the outbound decode bounds of the wire, and an `int` of the schema is read by its value, so `-0.0` is zero, as the `>= 0` checks of the server have it.
   - `handshake`: `challenge` (a nonce of exactly 32 bytes), `hello` with `proof = base64(HMAC-SHA256(SHA-256(token), nonce))` or no proof with no token, then `welcome` of protocol 9 or `refused` with the server protocol, which is not 9: the server refuses only a protocol that is not its own. Any other frame or order is a break, and after a break, `welcome`, or `refused`, every frame is a break.
   - `frame` and `event`: `res` read by the op of its request (a `res` of no request in flight is a break), `event`, and `session_end`, each checked by the schema of `docs/features/wire-protocol.md`. An event of an unknown type is skipped with its envelope checked; a known type with a broken shape is a break. As in the TUI, `tool_execution_end` carries a tool result, and `queue_dropped` and `steer_unconfirmed` carry user messages only. A `tool_call_id` is optional, as the schema has it ("Pairing"). A `subscribe` result has exactly one of `snapshot` and `replay`. The origin kind `hook` is of protocol 4 (#880).
   - `ui_block` (protocol 5, #878, `docs/features/ui-blocks.md`): a UI block as the TUI checks it, as Core admits it: the envelope (a `kind` of 1 to 64 bytes of `a`-`z`, `0`-`9`, and `_`, a string `text`, `cut` absent or a boolean), at most 65,536 bytes of JSON counted as the server encodes it (a string with the escapes of OTP, a number at the text that the server sent), and no integer of more than 100 digits, also in a container kept as its text. A block over a bound is a break: the server cuts or refuses it. A tool result carries at most 8 blocks, and a message of another role none; a shown block of the snapshot or of a `ui_block` event has a key of 1 to 64 bytes. The request of an ask with a `kind` has the envelope. The fold holds the shown blocks in the order of the first of each pair of call id and key: a later one with the same pair replaces it in its place, `tool_execution_end` drops the blocks of its call id, and `turn_end` drops them all, as in the TUI.
   - `fold`: the state of one subscription, by the rules of `test/fixtures/wire/README.md`, "folds.json": a snapshot replaces it, a replay applies its events, an event applies. Every event of a subscription comes after its snapshot or its replay and is of that instance: a restart of the session ends the subscription with `session_end`, and a replay comes from the ring of the instance of `after` ("Replay" in `docs/features/wire-protocol.md`). So an event before a snapshot, an event of another instance, a replay to a state with no snapshot (the state sent no `after`), and an event whose `seq` is not the next one (O4: a duplicate, an older one, or one after a gap) are breaks and change nothing; in a replay, the events before the break stay applied. The TUI drops an event of another instance and an older one instead, so the core is stricter; the TUI subscribes again at a switch of the session on one connection, and the core keeps one state for each subscription. Only an assistant message is a partial that deltas stream into: a snapshot whose partial has another role is a break, as in the TUI, and a `message_start` of another role opens none. A `message_end` adds a user or an assistant message, and an assistant one ends the partial; a tool result joins the transcript at `tool_execution_end` only, as in the TUI.
   - `transcript::rows`: the rows that a client draws, derived on read ("Pairing"). `subscribe_params` adds `after` of the last applied event. `ack(sub, from, to)` gives the `ack` frame when a frame moved the `seq` past a multiple of 1,024, the cadence of the TUI, so a replay that crosses one acks too.
   - `operation`: the operations that a host sends, typed: `prompt`, `steer`, and `follow_up` (a text of at most 4 MiB, `Helyx.Session.max_text_bytes/0`), `abort`, `answer` (a JSON object of at most 16,384 bytes as encoded), `start` (`cwd`, a folder of at most 1,024 bytes, and an optional `model`), `resume` (an id, or a folder for its newest session), and `sessions.saved` (an optional folder, cursor, and a `limit` of 1 to 256). A constructor checks its input, and the fields are private, so an `Operation` is one that the server takes and a host cannot make another; the text is a Rust `String` and so UTF-8 by its type, and the core checks no text twice. `params` gives the params of the schema, `name` the op, and `text` and `session` what the request names. `form_answer` and `approval_answer` build the answers of the two input kinds of `docs/features/ui-blocks.md`, and `form_answer_item` one item of a form's answer, which the app counts for the room a later question still has. An answer is checked as `Helyx.Session.check_answer/1` checks it: a JSON object of at most `MAX_ANSWER_BYTES` as encoded, no integer over 100 digits, and every raw text of the value that the type keeps as text (`Json::Number`, `Json::Deep`) is JSON, so a host cannot make an answer whose frame would close the connection. A number in an answer must be an integer (`Invalid::AnswerNumber`): the server re-encodes a number for the size of the answer (`1e2` is `100.0`), so a fraction or an exponent can pass the client's count and fail the server's, and the forms send only strings, booleans, and integers. `deadline(op)` is the table of `docs/features/wire-protocol.md`, "Deadlines": 46,000 ms for `abort`, 77,000 ms for `stop`, 15,000 ms for `sessions.saved` (10,000 ms, or 15,000 ms under a Hub, so the larger), 5,000 ms for `subscribe`, none for `start` and `resume`, and 6,000 ms for every other op. The server owns the deadline: the core keeps no timer and holds the bound with the request (`Client::outstanding`).
   - Tests: `core/tests/fixtures.rs` runs every case of `server_frames.json` (handshake, `res`, `event`, `session_end`) and of `folds.json`; `core/tests/fold.rs` checks the rules the fixtures do not pin; `core/tests/checks.rs` and `core/tests/json.rs` check the bounds of the table below; `core/tests/transcript.rs` checks the pairing; `core/tests/operation.rs` checks each builder, each bound, the deadline table, the request in flight, the reply that matches it, and the lost reply.
3. **The connection** (`client`, `connection`, `parts`), still with no I/O: the host opens the WebSocket, calls `Client::connect`, gives each text frame to `Client::receive`, sends each `Output::Send`, and calls `Client::closed` with the close code, or none for a lost connection.
   - `parts`: a server frame of `"type": "part"` is joined: exactly the keys `type`, `n`, `last`, `data`, `n` from 0 with no gap, `data` of base64, the joined text UTF-8 and within the frame bound of `json::WIRE`, then decoded as one frame that is not a part. A frame while parts wait, a part inside parts, and any other broken part are breaks (as `Helyx.Transport.WebSocket.Frame`). A request whose text is over 1,048,576 bytes goes as parts of 786,000 bytes, and one over 26,214,400 bytes, the request size of the server, is refused (`Refusal::TooLarge`), so the server never closes with `4413` for it.
   - `connection`: the state of one socket: the handshake, the parts, the requests in flight by id (at most 16, the bound of the server; a 17th is refused with `Refusal::Busy`), each with the op and the deadline of the op from its send, and the live subscriptions by `sub`. A request goes only after `welcome`. An event or a `session_end` of a `sub` that the connection does not hold, a `subscribe` reply with a `sub` that it holds, and a reply of no request in flight are breaks.
   - `client`: the state of each session that the host followed, which outlives a connection, and the intent of the host for it (`follow`). Every `subscribe` carries `answers: true`, because a host of this core answers asks; without it the server opens no ask for the client. A close with `4401` stops the client also after a welcome: the server refused the token, and a new connection would send the same one. The intent is what the host stated, and only the host changes it: `subscribe` follows a session (at most 16, the subscriptions of one connection: `Refusal::TooManySubscriptions`; a session id whose subscribe cannot fit a request: `Refusal::TooLarge`), `unsubscribe` stops following it, whatever the connection holds, and both can be stated again with no harm. The live subscription and the requests in flight are read from the connection, not stored. After each input (a frame, a welcome, a host call), the client reconciles each session that is not held and has no subscribe or `unsubscribe` in flight, in the byte order of the session ids, while a request place is free (`reconcile`): a subscribe, with `after` of the state, for a wanted session with no subscription, while the live subscriptions of the connection and its subscribes in flight are under 16, the bound of the server; and an `unsubscribe` for an unwanted session with a live subscription. So a session has at most one such request in flight. So a lost connection, any close code, and the `4408` slow close resume with a replay or a snapshot, a request that finds no place goes at the next reply, an `unsubscribe` of a session whose subscribe is in flight goes at its reply, and a subscribe of a session whose old subscription ends goes when it has ended. A session is not subscribed while a subscription of it lives, so two subscriptions never feed one state. An error answer to a request that reconciles never changes the intent: the client gives `Output::Failed` with the session, the op, and the error, `Client::subscribed` says whether a subscription lives (a refused `unsubscribe` leaves it live, and its events still apply), and the session is held on that connection: no request for it until the host states its intent again or a new connection starts, so a server that refuses causes no request loop. A hold is derived on read (`Connection::hold`), from the number of the last statement of the host for the session (each statement of the host, for any session, takes the next number, so a forgotten and followed-again session reuses none) and the last answer of the server that stops the session, a refusal or an end, with the statement that it answered: an answer holds only while it answers the last statement, and a subscribe reply is the last answer that clears it. So an error answer to a request of an older statement holds nothing and is not told, as a `busy` to an `unsubscribe` that comes after the host followed the session again; `Output::Failed` comes only for the last statement. Neither the session nor the connection stores a flag of its own for a hold or a renewal. An `unsubscribe` whose sub id cannot fit a request holds the session too, with no report: a server of this build makes sub ids of a few bytes. A server never gives a sub id again on a connection (its `next_sub` only grows, `plugins/bundled/lib/helyx/transport/web_socket/connection.ex`), so an `unsubscribe` reply ends the sub that it named; a server that gives one again breaks the contract, and the next frame of the sub is a break. A refused `unsubscribe` of a session that the host forgot meanwhile holds nothing and is not told. `unknown_sub` to an `unsubscribe` means that the server holds the subscription no more: it is not live, and a frame of it still on the way is dropped. A `session_end` holds the session too: it stopped, so a subscribe would find none; the intent stays, and the next connection tries it again once. An `unsubscribe` reply ends only the subscription that it named. A `history` reply of `instance_changed` tells that the instance that the page named was replaced: the session started again, so an end of that instance holds the session no more, whether it came before the reply or after it; a refusal stays. The next subscribe reply tells the current instance, and the replaced one is dropped. A page of another instance lifts nothing. `Client::follow` gives the state of a follow, derived on read in the same way: unwanted, live, subscribing, waiting (no connection, its old subscription ends, no free place of the 16 subscriptions, with the sessions among them, live or with a subscribe in flight, that the host does not follow, or no free place of the 16 requests), or held (ended or refused). The app shows a wait for a place and an end in its status line (`net::follow_line`); a refusal keeps the line of its `Output::Failed`, which names the error. An end that comes after a statement of the host holds that statement: the session stopped, so a subscribe would find none (judged in cycle D2, round 1). An `after` whose `instance_id` would take the subscribe over the request size is left out, and the server sends a snapshot. After each frame that moves a `seq` past a multiple of 1,024, the client sends the `ack` (a snapshot is the credit base, so it is not acked). `closed`, also called for a connect or an upgrade that failed, gives `Next::Stop` for a connection that ended by a break or by `refused`, and for any end before the first welcome of the client, as the TUI ends at a failed first connect (`docs/features/tui-attach.md`, decision 10); after it, any other end gives `Next::Reconnect`, a failed open too, so an outage of the server or a refused TCP connect does not end the following. The client keeps that a welcome came, a fact of the frames of the server; no other state of it shows a past welcome, as a client can follow no session (#860, gate round 1). `closed` also gives the host's requests that were in flight, in send order, as their id and op (`Closed::unknown`): the connection took their replies with it, so each of them is `Unknown` (ADR 0006 §4). The client never sends one again; the user decides. A subscribe or an `unsubscribe` that reconciles the intent is not one of them, because the next connection states the intent again, and `Client::outstanding` lists the host's requests that wait. `perform` sends an `Operation`, and a reply is matched by id to the op of its request (`frame::parse`); a reply of no request in flight is a break. `forget` drops the state, and the hold, of a session that the host does not follow and that has no subscription or subscribe on the way. A subscribe reply with a sub id that the connection holds, or that the server ended (`unknown_sub`), is a break: a sub id is unique on the connection.
   - Tests: `core/tests/client.rs` runs every fold of `folds.json` through connections, closes, and the subscribe with `after` that the client sends at the welcome; and the rules above.
4. **The GPUI macOS app** (`clients/rust/app`, crate `helyx-desktop`), a first cut:
   - `settings`: the server of a data folder, read as the TUI reads it (`docs/features/tui-attach.md`, decisions 1 and 2): `<data folder>/server.json`, a regular file (not a symlink) of at most 4,096 bytes, with `address` an IP address, `port` from 1 to 65535, and `token` a string; a data folder that its group or other users can write is refused (on a platform with no Unix mode, every folder is refused), and a data folder that is not there is no server. The data folder is the first argument, else `~/.helyx/sessions`. The file is checked with `symlink_metadata` and then opened: a swap between the two needs write access to the folder, which only the user has. The `Debug` form of `Server` leaves out the token. `settings::source` gives the read to the network thread, which calls it before each connection, so a server that restarted at another port and with another token is found again in one connection after the pause. The start keeps its read, so a folder with no server is one line and exit 1, and no window opens; the first connection uses that server, and each later one reads the folder again. The line takes the three cases: while the source fails, the error of the read (for example that the folder has no server file, or that the file is not valid); a connect to a read server that fails shows the line of the failed connect, with its address; and a stale file, which names a dead port, fails its connect, so the thread waits the pause and reads again, and the new file gives the new port and token, within the pause of a reconnect. Not built: the test of the lock `server.lock` (the TUI waits while a server starts); the app shows the line of the failed connect instead.
   - `net` and `socket` are not in this crate: they are the shared crate `helyx-client-net` ("The network layer"), which the window uses as before. The app keeps `composer`, `ask`, `input`, `settings`, and `ui`.
   - `composer` (every platform, from `docs/features/multiline-composer.md`): a text with a cursor. Enter sends, Shift+Enter adds a new line, and Backspace, Delete, Left, Right, Home, End, and Cmd+Left/Right edit at the cursor; Cmd+V pastes a text cleaned as the TUI cleans it (CRLF and a lone CR become LF, and a control character other than tab and LF drops), and Cmd+C copies the field. While a turn runs, Enter sends `steer` and Option+Enter sends `follow_up`, as in the TUI; with no turn, Enter sends `prompt`. Escape and Cmd+. abort the running turn, also over an ask. A send of the composer is numbered, and the input marks it pending at Enter itself, before any network thread step, as the TUI blocks on its send (`Helyx.TUI.send_message/3`). While it is pending, Enter sends nothing and the text does not change: an edit key and a paste are ignored, and only a move, Escape, and Cmd+. act. It settles from one outcome of that number: `ok` empties the composer, and a refusal before it goes, an error reply, or a lost reply unlocks it with the text kept, its request line naming why. An empty composer sends nothing, and a text over 4 MiB is not sent: the window says `not sent: over 4 MiB`, and the text stays. The composer keeps its text while an ask takes the keys, and across a reconnect. Accepted: no paste marker (a GUI shows the whole text), no recall of earlier prompts, no undo, no Up/Down line moves, and a text of more than 8 lines shows its last 8; a line longer than the width wraps and the window cuts the text at 9 rows of height, so a very long wrapped line can hide its tail.
   - `ask` (every platform): the oldest open ask of a kind that the window reads, `form` or `approval`, takes the keys in the place of the composer, as in the TUI. A form shows each question, its header, and its options with a circle for a single pick and a box for a multiple one; Up and Down move the cursor over the options and the Other line, Space marks an option of a multiple pick (a single pick is the option under the cursor at Enter, so Space does nothing), and types a space on the Other line, Enter takes the question and moves on, and Enter at the last question sends. On a multiple pick, Enter takes the marks, or the option under the cursor when none is marked; the marks go out in the order of the options, not the order of the clicks, and only the question that the keys act on shows them. A typed character or a paste goes to the Other line, which takes the cursor, and Enter takes it when it has text; a paste is one line, its new lines becoming spaces, as in the TUI. A click on an option answers a single pick and marks a multiple one. An approval has Allow and Deny, and sends `{"decision": "allow"}` or `{"decision": "deny"}`. An answer goes on only while the answers so far and the longest option of each later question fit 16,384 bytes, so each later question can still be answered; else the question stays and the panel says `not sent: the answers are over 16 KiB`, as the TUI does. The Other line is bounded to 16,384 bytes. The answer goes as the `answer` op with the ask id, and the input marks it pending at the key or the click, keyed by ask id with its send, before any network thread step. The ask stays closed while that send is pending or after it got `ok`, across a follow of another session; a send that is refused, gets an error reply, or loses its reply clears the mark and opens the ask again with its last answer, because the user decides (ADR 0006 §4). An ask that is open behind the one that takes the keys shows `answer the earlier ask first`. An ask of another kind shows its text and the line that another client can answer it, and an ask whose request has no `kind` is not drawn; both stay open for another client (ADR 0011 §4).
   - `ui` (macOS only): one window. The left column lists the live sessions (a click follows one), the saved sessions from `sessions.saved`, newest first (a click resumes one, and `more sessions…` takes the next page), the folder of a new session (a click focuses the field, and Enter or the `start` button starts a session there), and `refresh saved sessions`. The right column shows the line of the connection and of the follow, the transcript of the followed session as the rows of `transcript::rows` (a tool call with its result or "awaiting result", an orphan result, a placeholder `[kind]` for a block kind that the app does not know), the UI blocks of a result, of the `ui_block` events, and of the asks with a kind (#885, `docs/features/ui-blocks.md`, "Rendering in the client kit"), the partial, and the notices; a GPUI `list` lays out only the rows in view. Under it are the lines of the last four requests, with a count of the older ones, the notice of the input, and the composer or the ask that takes the keys. While a turn runs, the row above the composer names the keys that steer and follow up, and carries the `abort` button. The window takes the changes of the network thread every 50 ms. The keys come to the root of the window, so a click only chooses the field that the keys act on; the composer holds the field by default.

## The network layer

`clients/rust/net` (crate `helyx-client-net`, #931) holds the network thread, a blocking WebSocket (`tungstenite`) driven by `client::Client`, with frames of at most 1,048,576 bytes both ways, and the guards of its socket. Its waits are `net::socket::WAITS`; the tests run the same code with shorter ones (`net::run_with`). A test whose batch of sends must outlast its deadline also caps the send buffer of the socket (`Waits::send_buffer`, built only with the feature `stub`), because the OS can buffer a batch of several MiB whole, and then every write returns before the deadline. It connects within 5,000 ms. Every later wait of a connection is a deadline of its socket, held by a watchdog thread that checks every 100 ms and shuts the socket down when one has passed, whatever read or write is in progress: the read deadline, 5,000 ms in all for the upgrade and the wait for `welcome` (a slow upgrade, pings, or a frame that comes a byte at a time do not extend it), then 45,000 ms from the last message read, an instant that only a read moves, so no number of sends extends it; and the deadline of each batch of sends, 5,000 ms, set at its start and cleared at its end. The watchdog sends no close frame: a write of the host can be in progress on the socket, and a frame in its middle would break the stream; the server sees the end of TCP. The close frame that the host sends after a break, and at `refused`, is not under the send deadline: it waits at most the write timeout of the socket, 5,000 ms (decided on 2026-11-08). A tap on the socket finds the end of the HTTP reply of the upgrade by the rules of the parser of `tungstenite` (a line ends at `\n`, with or without `\r`; empty lines before the status line are skipped), then reads the header of each frame of the server. At the first byte of a binary frame it gives only the bytes before it, and every later read fails: every frame before it is taken, read by read, and a binary frame that is not final, with pings or continuations after it, stops the layer at the first read after them. After the mark, any end of the connection is a break: a close, and an end that a failed send starts; `refused` keeps its own line, and stops the layer too. A close and a binary frame that come in two reads end as the close says: the mark is set only by the bytes that a read took. After the upgrade, the tap also keeps a write that fails, a timeout too, and gives `WouldBlock` to `tungstenite` in its place: `tungstenite` sends the pong of a ping at the start of its next read, and stops that read at a write error, but goes on at `WouldBlock`, so it still gives the frames that it read before; then every read of the tap fails at once, with no wait on a dead socket, and the connection ends, as a break after a binary frame and as a lost connection otherwise. So the frames that `tungstenite` read before a failed write, of a pong or of a frame of the host, reach the client before the end; bytes that it had not read are not taken. After a failed write no frame goes, and the commands of the host wait for the next connection. A write that fails during the upgrade ends it, as before: the handshake of `tungstenite` would take `WouldBlock` for a write to try again. The thread asks its host for the server before each connection (`net::Source`, a `Fn() -> Result<Server, String>` that is `Send` and `Sync`). A source that fails is a failed open: its error is the line, and the thread waits the pause and asks again, with no end while the host lives, also before the first welcome; a source that gives a server keeps the rules of a failed first connect. The handshake proves the token of the server of this connection, not the one of the first, and the state of the followed sessions outlives the change of the token. A server that ends without removing its file leaves a stale one: the next connect fails, the thread waits the pause and reads again, and the new file gives the new port and token, so the delay is at most the pause. A close with `4401` keeps its rule, that the client stops: with a fresh read before each connection, the token of the file is wrong for the server at that address. One open hole: a server that was killed leaves its file, and a new server on the same fixed port listens before it writes its new file; a client that read the old file and connects in that moment proves the old token, gets `4401`, and stops, and the user starts the app again. A server on a free port, the default, cannot meet this. An attempt adds no line of its own: a failed read repeats its error, and a failed connect repeats its own line. The thread reads with a timeout of 100 ms to take the commands of the host, sends `sessions.live` at each welcome, and follows the session that the host picks (and unsubscribes the one before); a refused follow shows on the line. It opens a new connection 1,000 ms after a close or a failed open while `closed` gives `Next::Reconnect`, and ends at the end of a connection when the host is gone (its sender of commands dropped). The pause is a wait on the commands: a host that goes in it ends the thread with no new connection, and a command that comes is kept for the next connection; between connections it takes the commands of the host, whose frames go at the next welcome; a binary frame, a text that is not UTF-8, a frame over the bound, a frame that the core refuses, and `refused` stop it, and at a stop it ends with one line (`refused` keeps its line). A reset with no close frame is a lost connection. The host asks five commands: `Follow`; an `Operation` of the core (a `prompt`, a `steer`, a `follow_up`, an `abort`, an `answer`, a `start`, or a `resume`), with the number of the send that it is when the host waits for its outcome (a send of the composer or the answer of an ask); a `Saved` page; `Live`, which asks the live sessions again; and `BecameActive` ("The rule of the active app"). Each request of the host is a line (`net::RequestLine`) with its op and a label of its text, `Pending` until its reply, then `Ok`, the error text of the server, or `Unknown` when the connection ended before the reply (ADR 0006 §4); the lines are the last 12 requests, and a pending line is never dropped, so the list holds at most the 16 requests in flight. A send that the client refuses (`Refusal::NotReady` with no connection, `Busy`, `TooLarge`) sends nothing, but it is a line too, in the `Error` state as `not sent: <reason>`, so no operation waits for a later connection and the next `connecting` or `connected` does not overwrite it. `Shared::outcomes` gives one outcome for each numbered send, of the composer or the answer of an ask: `Pending` when the client takes it, `Ok` when the server answers, and `Failed(reason)` for a refusal before it goes, an error reply, or a lost reply. The host drains the outcomes at each change, and the bindings drain them into their snapshot, so each is read once; the queue keeps at most 64 (the input holds at most 17 pending sends, of which each gives at most two), and the input's own map of hidden answers is bounded at 16. One page of saved sessions is asked for at a time, and the replace-or-append mode belongs to the id of its request, so two pages cannot replace and append in the wrong order; a second page asked for while one is on the way is a `not sent` line and changes nothing. `sessions.live` goes at each welcome, and the first `sessions.saved` at the first welcome of the run; a reply to `start` or `resume` follows the session that it names; a page of saved sessions replaces the list, or appends at the `next` of the page before, and each prompt is cut to 200 bytes for the list.

**The rule of the active app.** A mobile host suspends, and the system takes its sockets with no close: the server's end of the connection stays open and silent, so the silence bound of 45,000 ms would be the first sign. `net::became_active` (`Command::BecameActive`, which the bindings send as `Connection::became_active`) tells the thread that the host is active again: the thread drops the socket that it holds and ends the connection as a lost connection does. A wake-up that comes before the welcome of the current connection is dropped: its socket is new, so no suspend can have left it dead. After the welcome, the next connection goes on the same reconnect path, subscribes again with `after` of the state of each session, and starts at most the reconnect pause of 1,000 ms later. The rule neither waits for the silence bound nor sends a close frame: the socket of a suspended app can be dead in either direction. Test: `net/tests/net.rs`, "an active app replaces a dead socket without the silence".

## Bindings for Swift

`clients/rust/ffi` (crate `helyx-client-ffi`, #931): `crate-type = ["staticlib", "cdylib", "lib"]`, and UniFFI 0.32.2 with proc macros and no UDL file. One object and one callback:

| Surface | What it does |
| ------- | ------------ |
| `Connection::new(address, port, token, listener)` | starts the network thread of one server; the drop ends it |
| `follow(session)` | follows a session, and stops following the one before |
| `live_sessions()` | asks the live sessions now |
| `saved_sessions(after)` | asks a page of the saved sessions |
| `start_session(cwd)`, `resume_session(id)` | starts or resumes a session, and follows it; gives the number of the send |
| `prompt`, `steer`, `follow_up`, `answer` | sends one operation of the window, checked by the core before it goes; gives the number of the send |
| `abort(session)` | aborts the running turn; gives the number of the send |
| `became_active()` | the rule of the active app |
| `NetListener::on_snapshot(snapshot)` | the state of the window on each change: the line and the followed session, the live and saved lists, the request lines, the outcomes of the numbered sends, and the folded state of the followed session as rows |

A method that sends an operation gives the number of its send, 1 for the first and one more for each send of the `Connection`; the snapshot reports the outcome of that number in `outcomes`, as the numbered sends of the window do (`net::send::SendId`). Each type of the surface is owned: a record or an enum of `ffi` copies the type of the core or of the layer that it shows (a message, a block, a row, an ask, a shown UI block, a live or saved session, a request line, an outcome), and a JSON value crosses as its text. The core needed no change for the bindings. The callback runs on the network thread, so a host that draws with it hands the snapshot to its own thread. The drop of the object ends the thread, and its socket closes then; a drop that runs on the network thread itself, from `on_snapshot`, ends there with no wait for the thread.

`ffi/bindgen.sh` builds the library and runs the `uniffi-bindgen` binary target of the crate in library mode (`--library`), which writes `helyx_client_ffi.swift`, its header, and its modulemap into `ffi/generated/`. Git ignores that folder: a host generates the bindings at its own build. Run it with `cd clients/rust/ffi && ./bindgen.sh`.

The gate and the bindings: `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, and `cargo test --locked` in `clients/rust` cover both new crates on every host, and `ffi/tests/connection.rs` drives the object against the stub server of the network layer through a listener implemented in Rust, so the surface is proven without Swift. Only a Mac with Xcode checks the iOS build of the crate (`mise exec -- cargo build -p helyx-client-ffi --target aarch64-apple-ios-sim`) and that the generated Swift compiles in an app; the gate checks neither, because it builds no app.

## Pairing

The session pairs each tool result with its call: a live result follows its call, and at read `Helyx.Session.Transcript.repair/1` drops a second result of one call. That is a rule of the server, and the fixtures are the contract, so a client enforces at its boundary only what keeps it whole: the shape of each frame by the schema, and the bounds, so that it never crashes and never grows without a bound. It does not enforce the pairing, which needs state that only the server holds in full (a tail snapshot can start after a call). It shows what it gets:

- A result closes the oldest open call of its `tool_call_id`, as in the session. Only an assistant message opens calls, as in the TUI: a tool call block of a user message is part of that message.
- A result with no open call of its id, or with no `tool_call_id` (the schema has it optional), is an orphan row in its place, drawn as a result with no call.
- The pairing is derived on read (`transcript::rows`) from the messages of the state: the fold stores no open calls.

The TUI does the same (`Helyx.TUI.ViewModel`): an orphan result is a cell `{:tool, nil, "a tool result with no call", result}`. Before #860 it crashed on an orphan (#407), and its decoder broke on a `tool_execution_end` result with no `tool_call_id`. The fixtures hold both cases: `server_frames.json`, "tool_execution_end: a result with no call id", and `folds.json`, "a tool result with no call before it is an orphan in its place".

## Ownership

The core holds no socket, file, timer, or process; `Client::closed` tells the host whether to open another socket. The network layer (`net`) holds the socket, its watchdog, and the thread of one server; a host holds the layer's state and its channel, which the app's `ui` and the bindings' `Connection` start.

| Resource | Created by | Held by | Released on normal end | Released when the holder crashes | Released on abort |
| -------- | ---------- | ------- | ---------------------- | -------------------------------- | ----------------- |
| TCP socket and WebSocket of the network layer | `net::open` | the network thread | the close of the server; a break (the thread sends a close frame); a wait over its bound (the watchdog shuts the socket down, with no close frame); or a lost connection | a panic of the thread drops the socket with its stack; the host takes the poisoned lock and shows the last state, with the last line, which can still say `connected`: open, accepted, no ticket | the quit of the app ends the process; the drop of the `Connection` of the bindings ends the thread, and its socket closes then (a drop during a connect or an upgrade waits their bound) |
| the watchdog thread of a connection | `net::open` | its own thread, with a clone of the socket | the drop of its `Watchdog` at the end of the connection: it ends at its next check, one poll of 100 ms and the time of its wake-up (a probe measured 102 ms; the test `net/tests/watchdog.rs` allows a margin for load) | it ends at its shutdown of the socket, or at the drop | the quit of the app, or the drop of its `Connection` |
| the network thread | `ui::run` of the app, or `Connection::new` of the bindings | the process | `net::run` returns at `Next::Stop`; the drop of a `Connection` sends the wake-up and closes its channel, so the loop ends within a poll, the pause, or the wait of a connect or an upgrade | n/a | the quit of the app, or the drop of its `Connection`, which does not wait for itself when it runs on that thread |

## Accepted

Decided by the orchestrator on 2026-11-08, for the owner:

- The TUI cuts a message by its blocks, not by its bytes: a tool result keeps its first 1,024 blocks, each text of at most 65,536 bytes (`Helyx.Message.cut_result/1`), so a collapsed tool cell joins and splits up to 1,024 × 64 KiB in each frame that shows it. Core bounds a result the same way.
- The streaming message of the TUI is reversed, split, and cut in each frame: O(blocks) for each frame, so a long stream of deltas costs O(n²) in all. A live partial of Core has at most 1,024 blocks.
- The block cut of a user message and of a tool result counts no tool call, as a call of an assistant message has a cell of its own; in a user message or a tool result a call shows as a placeholder, so a call past the first 1,024 blocks there is lost with no count, and the recall of a cut prompt gives a shorter text. Only a server of another build sends such a message: a user message of Core has one block, and a tool result has no tool call.

Decided while building #920, for the owner:

- The core checks the deadline of an op as the larger bound of a Hub (`sessions.saved`: 15,000 ms, not 10,000 ms), because a client cannot know whether its server is under a Hub. The deadline is information for the host only: the core holds no timer, as before, and the server answers `timeout` at its own deadline.
- The core checks the `cwd` of a `start` and of a `resume` at 1,024 bytes (`PATH_MAX` of macOS). The wire has no bound; the window's field would otherwise grow with a paste. The check can refuse a folder that a Linux server would take (its paths are longer), which the app does not reach on macOS.
- A form asks one question at a time, as the TUI does: Enter takes the question and moves on, and the Other line of a question shows while it is current. A click answers a single pick and marks a multiple one, rather than requiring Enter after each mark.
- The composer follows the TUI's keys: Enter steers a running turn, Option+Enter follows it up, and Escape and Cmd+. abort it. The `follow up` / `steer` toggle is not built, because the keys replace it.

Decided while building #931, for the owner:

- The bindings report one snapshot on each change: the whole state that the window draws, not a difference. A host redraws from it, and the copy is the one that the desktop window makes at each redraw, under the lock of the network thread. The callback runs on the network thread, so a host that draws with it hands the snapshot to its own thread.
- The bindings resume a session by its id only, and a `start` carries no model: the desktop app sends no other form of either, and the surface holds no more than the app uses.
- The window shows the last four request lines and counts the older ones; the list keeps 12. A line whose op is `sessions.live` or `sessions.saved` shows too, because every request of the window has a line; `sessions.live` goes at each welcome, and the first `sessions.saved` at the first welcome of the run, so a reconnect storm does not scan the folder of sessions again. A click on `refresh saved sessions`, or `more sessions…`, asks again.
- The saved list keeps 200 bytes of each prompt, cut at a character boundary, and no time: the window draws the prompt and the folder that identify a session, and a date needs a formatting crate or a hand-written calendar. A page of at most 256 items is at most 52 KiB.
- The window draws its caret as one more character (`▏`) in the text, because GPUI 0.2 has no text layout that the view can read back, and a text of more than 8 lines shows its last 8, where the cursor is when a person types.
- The composer, the form, and the folder field take the keys at the root of the window, and a click only chooses the field: GPUI dispatches a key to the root when no node holds the focus, and one handler keeps the ask and the composer from both acting on a key. Accepted: no IME composition, and no Tab to move between fields.
- `sessions.saved` with no folder lists every folder, as the wire says; the app does not offer a filter by folder.
- A start or a resume follows the session that its reply names, and the window keeps the cwd field after that. A follow that the server refuses shows on the connection line, and the request line shows the error.
