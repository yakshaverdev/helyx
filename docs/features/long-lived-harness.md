# Long-lived harness

One harness program serves the provider process of a session, not one turn: `claude` for `Helyx.Provider.ClaudeCode` and `codex app-server` for `Helyx.Provider.Codex`. Both share `Helyx.HarnessIO`. This doc gives what the harness plugins own: the program lifecycle, the idle close answer, the replay, and the plugin bounds. The Core turn contract (turn states, turn end, deadlines, steer, provider death) is in `docs/features/session-lifecycle.md`, and the provider protocol in `docs/features/one-provider-path.md`.

The protocol facts are in `docs/research/claude-code-stream-json.md` and `docs/research/codex-app-server.md`.

## Program lifecycle

- **Start.** `init/3` finds the program on `PATH` (`HarnessIO.find/1`). Codex starts it there; Claude starts it at the first turn, because the launch takes the turn's prompt (`docs/features/provider-parity.md`). It runs in the session's working directory, in its own process group under `Helyx.Watchdog`, with open input. The provider process holds the groups with `Helyx.Tool.hold/1`, and the hands release them with `release/3` (ADR 0004). By default the program has the trust of the bash tool: Claude runs with `--permission-mode bypassPermissions`, and Codex threads run with the approval policy `never` and the sandbox `danger-full-access`. A Codex session can pick other values ("Sandbox and approvals" in "Codex").
- **Close.** `:close` ends the program's input (`HarnessIO.close/2`) and answers `:ok` at the exit. A program exit at any other time stops the provider process.
- **Stop.** Any stop of the provider process closes its port. The watchdog sends TERM to the program group, waits the TERM grace, and sends KILL. A stop never sends end of input first: Claude runs its queued turns after end of input, and a stop must not run them.
- **Idle close.** `:idle_close` closes as `:close` when the program has no work of its own, and answers `:busy` otherwise; the program then stays. Claude has work of its own while the `tasks` list of the last `background_tasks_changed` line is not exactly `[]`, while a program turn runs, and once after a `task_notification` line. Codex has work of its own while a child thread has open work.
- **Shell.** Each program runs with its shell off, and the model runs its commands with the Helyx `bash`. The hands then give each command its abort, its output bound, and its tool events; a command that the program ran with its own shell had none of them, and a background command outlived an abort. Every Helyx tool goes to it, and Claude has none of its own tools (`docs/features/provider-parity.md`). The observed runs are in `docs/research/harness-shell-off.md`.
- **Background work.** A Claude background task, such as a background sub-agent, and a Codex child thread with open work after a normal turn end, belong to the program, not to a turn. They outlive the turn end. An interrupt ends every Claude sub-agent.
- **No stored state.** With the provider option `persist: false` (`:provider_opts` of the session; default `true`), the program keeps no conversation file: Claude Code launches with `--no-session-persistence`, and Codex starts the thread with `ephemeral: true`. Such a harness session cannot be resumed: the provider gives no `:resume_id` event, a later program and a prompt change start a fresh harness session with the replay, an `init/3` with a `:resume_id` fails with `:no_state_resume`, and a Claude Code compaction fails at once. The rule and its reasons are in `docs/features/harness-no-state.md`.
- **Environment.** With the provider option `env` (`:provider_opts` of the session), a map of string to string with the default `%{}`, each entry is set on every launch of the program, on top of the environment of the BEAM. `init/3` refuses the names that the launch shell or the OS is known to set itself; another name that a shell or an OS sets is a stated hole. The text of a start that fails before the watchdog marker has each value masked as `<env>`. The state folder of the program is one use of it (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`). The check, the bounds, and why Helyx logs no value are in `docs/features/harness-no-state.md`, "The environment of the program".
- **Errors.** stderr is dropped: the Claude `result` line and the Codex error answers carry the errors. An error result of a turn (a Claude `result` that is not a success, `is_error: true` with the subtype `success` too, and a Codex `turn/completed` that is not `completed`) fails the turn with `%Helyx.ProviderError{provider: id, kind: subtype_or_status, text: text}`, whose message is `<id>: <text>` (#746). The text is the program's error text, cut at 2,000 bytes. A result with no text fails it with `{:claude_code, subtype, ""}` or `{:codex, status, ""}`. A Codex error answer to a request that fails the request or the turn (`Turn.failure/2`) is the same exception with the method as `kind` and the error `message` as the text, or `unexpected response` when it has none; a Claude Code error answer to `initialize` or to an interrupt has the `kind` `:initialize` or `:interrupt`, and with no text it is `{:initialize, ""}` or `{:interrupt, ""}` (#760). An error answer to `thread/resume` other than a lost thread keeps `{:malformed, "thread/resume"}` (see "Connect").

## Claude Code

- The program runs as `claude --output-format stream-json --verbose --include-partial-messages --input-format stream-json --permission-mode bypassPermissions --tools= --setting-sources= --strict-mcp-config --system-prompt= --system-prompt-snapshot=off --disable-slash-commands --model=<model> --session-id=<uuid> --mcp-config <helyx server>`, with no `-p`. The first line on stdin is the control request `initialize` with the turn's prompt. A resume passes `--resume=<id>` in place of `--session-id`. The program of a compaction has no `--disable-slash-commands`, because the flag also takes out `/compact` (`docs/features/harness-compaction.md`, #754). The model ref is `claude-code/<model>`, where `<model>` is what `claude --model` takes.
- **Shell off.** `--tools=` takes out every tool of the program: the shell, `Monitor`, the file tools, web fetch and search, and sub-agents.
- **Commands off.** With `--disable-slash-commands`, a user line runs no program command or skill. A line whose first word is the name of a built-in command (`/init`, `/help`) gets the program's answer `/<name> isn't available in this environment.` with no model call and no text delta, so the turn ends `done` with no text; a line with a skill name such as `/code-review` reached the model after a program reminder that no command ran. A named limit (ADR 0002).
- **Capabilities.** Each `init` line must list `interrupt_cancel_queued_v1` and `msg_lifecycle_v1`. An `init` without both stops the provider process with `{:missing_capabilities, missing}`.
- **Turn phases.** A turn is one user line with a `uuid`, answered `:ok` at the write. The provider holds it in one `phase` (`Helyx.Provider.ClaudeCode.Turn`): `:idle` has no turn; `{:queued, messages, chunks, replay?}` is a turn whose line the program did not start yet, with its transcript, the replay chunks not written yet, and whether it wrote a replay; `:started` has its line started, and only from there do its lines and its `result` count; `{:steer_wait, ref}` waits for the start of an unresolved steer; `:program` is a turn that the program started by itself. A pending interrupt is `{:pending, from, seen}` before its write, and `{:sent, from, request_id, seen}` after it; `seen` holds `:response` and `:result` when they came. `compact` is nil for a model turn; in a compaction turn it is `:asked`, then `:compacted` at its `compact_boundary`, or the `compact_error` of a failed compaction.

| State | Event | Next state |
| --- | --- | --- |
| `:idle` | `{:turn, ...}` or `{:compact, ...}` | `{:queued, ...}`: the first replay chunk, then the turn's line |
| `:idle` | `init` line | `:program`: `{:turn_start, id}`, with one new UUID |
| `:idle` | steer, interrupt | `:idle`: `:rejected`, `:ok` |
| `{:queued, ...}` | `started` of the turn's `uuid` | `:started`: a held interrupt goes out |
| `{:queued, ...}` | steer | `{:queued, ...}`: the line goes out, or waits for the turn's line during a held replay |
| `{:queued, ...}` | interrupt | `{:queued, ...}`: held for the `init` line, and after a replay for the start of the turn's line |
| `{:queued, ...}` | `result` with `num_turns` 0 | `{:queued, ...}`: the next held replay chunk goes out |
| `:started` | `started` of the steer's `uuid` | `:started`: `{:user_message, steer_id}` |
| `:started` | steer | `:started`: the line goes out, and the steer waits for its own start |
| `:started` | interrupt | `:started`: the control request goes out |
| `:started` | `result` with `queued_turn_count` 0 | `:idle`: the terminal, or `{:steer_wait, ref}` |
| `{:steer_wait, ref}` | `started` of the steer's `uuid` | `:started`: the timer is cancelled |
| `{:steer_wait, ref}` | `result` with `queued_turn_count` 0 | `{:steer_wait, ref}`: the wait goes on |
| `{:steer_wait, ref}` | the timer | the provider process stops with `:steer_not_started` |
| `:program` | `{:turn, ...}` or `{:compact, ...}` | `{:queued, ...}`: the new turn replaces the program turn |
| `:program` | steer, interrupt | `:program`: the line, or the control request, goes out |
| `:program` | `result` with `queued_turn_count` 0 | `:idle`: the terminal, or `{:steer_wait, ref}` |

- **The turn end.** Only a `result` with `queued_turn_count` exactly 0 ends the turn; a count above 0 keeps it open, and a missing count, or one that is not a non-negative integer, stops the provider process with `:no_queued_turn_count` (ADR 0007). A result before the start of the turn's line is not its turn's: that of a replayed line, of a program turn, or of the turn's own line (#246).
- **The steer.** A steer is a user line with a `uuid` of its own, mapped to the `steer_id`. After the terminal of the turn, the provider answers `:rejected` and writes nothing. A `result` that could not end the turn because a steer was unresolved gives no event: the turn waits for the steer's start, then for the next `result`, and the provider process stops with `:steer_not_started` over the wait ("Bounds"). `claude` reads a line that came before a `result` after it and runs it as a turn of its own, and its start comes 0 to 10 ms after that `result` (research note). After a lost-session relaunch the steers of the turn are dropped, not written again.
- **The interrupt.** It waits for the `init` line of a fresh program, which lists its capabilities only there, after the start of the turn's line; and after a replay it waits for the start of the turn's line too, because `cancel_queued` could drop replay lines (inferred) and leave a harness session with part of the history (research note for one replay line; inferred for more). A success response answers `:ok` with the turn's `result` (any `terminal_reason`), or at once when its `cancelled` list holds the turn's `uuid`: no `result` comes for a cancelled line (research note). A `still_queued` that is not exactly `[]` answers `{:error, :still_queued}` (ADR 0007); a `cancelled` that is not a list is a contract break, and the provider process stops. A turn that already ended answers `:ok`, and nothing is written.
- **Program turns.** An `init` line with no open turn starts a program turn, with a new UUID as its turn id, and the event `{:turn_start, id}` (#240); it has no `command_lifecycle`. A steer and an interrupt of it work as for any turn. A `{:turn, ...}` while a program turn runs replaces it: the program runs the new line after the program turn, and the rest of the program turn is dropped.
- **Lost session.** A resumed program that no longer has the session writes one `result` with the lost text before any `init`, and exits. The provider starts a fresh program with a new id, and a turn that was already written goes to it with the replay. A close during that waits for the lost program's exit.
- **Helyx tools.** An SDK MCP server named `helyx`, the only MCP server; the model sees each tool as `mcp__helyx__<name>`. A `tools/call` gives `{:tool_request, id, name, arguments}` when its `_meta["claudecode/toolUseId"]` is a string, its name is one of the tools that the program was given, its arguments are an object or absent, and a turn is started (a Helyx turn after its `started`, or a program turn). Any other call gets the error result `the call does not map to a tool use` at once. `notifications/cancelled` for an open call removes the call from the open calls and gives no action, so the later result of its run is not written. `initialize` gets a result that echoes `params.protocolVersion`, and `tools/list` gets the Helyx tool specs. The transcript has the Helyx name, without the `mcp__helyx__` prefix. A notification gets the ack `{"jsonrpc":"2.0","result":{}}`, and a request of another method gets the JSON-RPC error -32601.
- **Control requests.** Every control request gets an error answer, `can_use_tool` too: the launch flags make it impossible (ADR 0007, update of 2026-10-16). An unknown line, `control_cancel_request` included, is ignored.
- **Output.** Text and thinking stream as deltas. Tool calls and results arrive whole. The provider sends no `message_end`: the session closes the message.

## Codex

- The program runs as `codex app-server --disable shell_tool --disable unified_exec`. With these flags, the tool list of the model request has no command tool on codex 0.144.1 and 0.162.1, for the thread and for a sub-agent, also when the user's `config.toml` turns `unified_exec` on. On both versions `--disable shell_tool` takes out every command tool (`exec_command`, `write_stdin`, `shell_command`). `--disable unified_exec` alone changes `exec_command` into `shell_command` on 0.144.1 and has no effect on 0.162.1, where `codex features list` still shows `unified_exec` on (see the research note). `apply_patch` stays for file changes. The model ref is `codex/<model>`.
- **Own tools.** `apply_patch`, `request_user_input`, the `multi_agent_v1__*` tools, the MCP resource tools, and the tools of the user's MCP servers stay: a named limit (ADR 0002). The probe of #754 found no option, feature, or thread parameter of 0.163.0 that removes them; the config key `model_catalog_json` was not tried (`docs/research/provider-parity.md`).
- **Connect.** `initialize` (with `experimentalApi` when the program gets Helyx tools) in `init/3`. The first turn opens the thread with its prompt as `baseInstructions`: `thread/resume` with the stored id and the values of "Sandbox and approvals", or `thread/start` (with the Helyx tools as `dynamicTools`). A resume error with code -32600 and the exact message `no rollout found for thread id <id>` starts a fresh thread on the same program. Any other resume error fails the turn with `{:malformed, "thread/resume"}`. An error answer to `initialize` fails the connect, and one to `thread/start` fails the turn, with the program's error. A later turn with other tools starts a new program with a fresh thread and the replay (`docs/features/provider-parity.md`, "The prompt").
- **Thread id.** The stored id is the thread id, `#`, and the digest of the flags and the `dynamicTools` (`HarnessIO.session_id/2`; `docs/features/provider-parity.md`, "Resume eligibility"). A stored id with another digest starts a new thread with the replay.
- **Request phases.** The provider holds the turn in one `phase` (`Helyx.Provider.Codex.State`): `:idle` has no turn; `{:opening, id, from, prompt, history}` opens the thread for a model turn, with the turn's prompt and the rest of its transcript for a replay; `{:injecting, id, from, prompt}` waits for `thread/inject_items`; `{:starting, id, from}` waits for the answer to `turn/start`; `{:running, id, turn, mode}` has the program's turn `turn` running, with `mode` `:model` or `:compact`; and `{:compacting, id, from}` is a compaction before its `turn/started`. `id` is the Helyx turn and `from` the request that waits for an answer, nil once it has one. A compaction is marked only by its phase. A pending interrupt is `{:pending, from}` before the program turn id is known, and `{:sent, from, request_id}` after its `turn/interrupt`.

| State | Event | Next state |
| --- | --- | --- |
| `:idle` | `{:turn, ...}` | `{:opening, ...}`: `thread/start` or `thread/resume`, or nothing when the thread is already open |
| `:idle` | `{:compact, ...}` | `{:compacting, ...}`: `thread/compact/start`; a fresh thread fails with `:no_history` |
| `:idle` | steer, interrupt | `:idle`: `:rejected`, `:ok` |
| `{:opening, ...}` | the thread's answer | `{:injecting, ...}` for a fresh thread, else `{:starting, ...}`; a compaction on a fresh thread fails with `:no_history` |
| `{:injecting, ...}` | the `thread/inject_items` answer | `{:starting, ...}` |
| `{:starting, ...}` | the answer to `turn/start` | `{:running, ..., :model}`: `:ok`, and a pending interrupt goes out |
| `{:compacting, ...}` | the answer to `thread/compact/start` | `{:compacting, ...}`: `:ok` |
| `{:compacting, ...}` | `turn/started` | `{:running, ..., :compact}`: a pending interrupt goes out |
| `{:running, ...}` | steer | `{:running, ...}`: `turn/steer` |
| `{:running, ...}` | interrupt | `{:running, ...}`: `turn/interrupt`, or the error of an open command or child thread |
| `{:running, ...}` | `turn/completed` | `:idle`: the terminal, and a pending interrupt gets `:ok` |

- **The turn.** `turn/start` carries the prompt; its answer carries the program's turn id, and a pending interrupt goes out then. An error answer to `turn/start` or `thread/inject_items` is the reply `{:error, %Helyx.ProviderError{kind: method, text: message}}` (see "Errors"), and the provider process stops.
- **The steer.** `turn/steer` carries `expectedTurnId`, the running program turn id, and `clientUserMessageId`, the `steer_id`. The `item/started` of a `userMessage` item of the running turn with a string `clientId` gives `{:user_message, clientId}`. After `turn/completed` the provider answers `:rejected` and sends nothing. The `from` of a `turn/steer` without an answer outlives the turn, because the answer can come after `turn/completed`. A success answer gives `:ok`. The exact error `no active turn to steer` with code -32600 gives `:rejected`; any other error gives `{:error, reason}` (research note).
- **The interrupt.** With an open `commandExecution` item of the turn, `{:error, :command_running}` at once; with a child thread of the turn that has open work, `{:error, :agent_running}`. Both write nothing, and Core then stops the program. Otherwise the provider sends `turn/interrupt` and answers at `turn/completed`, or with its error answer. An interrupt of an ended turn answers `:ok`.
- **Open work at a turn end.** A `turn/completed` with an open tool item stops the provider process with `:command_running` for a command and `:tool_running` for another type: `turn/interrupt` does not stop a running command, and its late `item/completed` must not reach the next turn. A `turn/completed` while an interrupt waits and a child thread of the turn has open work stops it with `:agent_running`.
- **Child threads.** A `subAgentActivity` item on the program's own thread changes `agents`: kind `completed` removes the child (any turn id); any other kind moves it to the running turn. The notifications of a child thread are dropped. A server request of any thread gets its answer as below, and an `item/tool/call` of a child thread does not map.
- **Unasked turns.** A `turn/started` that is neither the running turn's nor the compaction's, or a `turn/completed` of an unknown turn, stops the provider process with `:turn_not_asked`: the thread does not start a turn by itself (#240). An item of another turn stops it with `:item_of_ended_turn`.
- **Line check.** `Helyx.Provider.Codex.Check.malformed/2` checks the full shape of every line that changes turn or thread state before any state changes. Any other shape, and a turn or item line with no string `threadId`, stops the provider process with `{:malformed, method}`; in the connect, the connect fails with it.
- **Request ids.** Each request has a new integer id; `due` maps each id without an answer to its method. An answer with an id that is not due is dropped. The turn end settles a sent `turn/interrupt`.
- **Helyx tools.** An `item/tool/call` of the running turn whose `callId` is an open `dynamicToolCall` item, with a `tool` that the thread was given and object `arguments`, gives `{:tool_request, call_id, tool, arguments}`. Any other call gets `the call does not map to a tool use` at once. A result goes back as one `inputText` content item with `success`.
- **Sandbox and approvals** (#753). The provider options `codex_sandbox` and `codex_approval_policy` (`:provider_opts` of the session) are the `sandbox` and the `approvalPolicy` of the thread. `codex_sandbox` is one of the strings `read-only`, `workspace-write`, and `danger-full-access`, default `danger-full-access`. `codex_approval_policy` is one of the strings `untrusted`, `on-request`, and `never`, default `never`. These are the string values of `SandboxMode` and `AskForApproval` in the schema of codex 0.163.0 (research note, "Sandbox and approval values"). Any other value, an atom or the `granular` object of `AskForApproval` too, fails `init/3` with `{:invalid_option, :codex_sandbox}` or `{:invalid_option, :codex_approval_policy}`, and the turn fails. `Helyx.Provider.Codex.Program.options/1` checks both. `thread/start` and every `thread/resume` send both values and `approvalsReviewer: "user"`, also after a prompt change in a new program. Reasons: the program does not keep the sandbox and the policy over a resume (research note, "Long-lived use"); and a user's config can name another reviewer (`approvals_reviewer`), which would get an approval request in place of Helyx and can accept it. A live program has not run with `approvalsReviewer` (research note, "Not run"). The stored id has no digest of them, so a resume with other values runs the thread with the new ones. The sandbox is meant for the program's own tools ("Own tools"). On codex 0.166.0, a `read-only` thread with the policy `untrusted` asked for an approval of an `apply_patch` of a stub model, and wrote the file after an `accept` (research note, "An `apply_patch` approval under `untrusted` and `read-only`"). A Helyx tool runs in the session, outside the sandbox, with the trust of the bash tool. Claude Code ignores both options. The `codex_` prefix names the provider that reads the option, as the `openai_` app env keys of `helyx_plugins` do, because the session gives `:provider_opts` to every provider. Not checked: the values that the answer to `thread/start` or `thread/resume` reports (`approvalPolicy`, `sandbox`); the provider trusts the program to apply what it sent.
- **Server requests** (#881). An `item/commandExecution/requestApproval` or `item/fileChange/requestApproval` with an integer or string id, whose `threadId` is the provider's thread, whose `turnId` is the program turn of the running Helyx turn, and whose `itemId` names an open item of the type that the method names (`commandExecution` or `fileChange`), gives the event `{:approval, approval_id, item_id}`: the approval id is the JSON of the JSON-RPC id, so the integer `0` and the string `"0"` give two ids. An id whose JSON is over 256 bytes fails the stream check, and the provider process stops (the generic path; the program sent the integer `0` in every observed run). The session runs the `before_tool` chain of the item's call and answers; the provider sends `{"decision": "accept"}` for an allow and `{"decision": "decline"}` for a deny, which carries no reason (`Helyx.Provider.Codex.Approvals`, `docs/features/hooks.md`, "Harness approvals"). Any other request of these two methods with an integer or string id gets `decline` at once, with no chain: one of a child thread, of an earlier turn, outside a Helyx turn, for an item that is not open or of another type (a Helyx tool call is a `dynamicToolCall`), or with no `params`. Its `itemId` could name another call of the current turn, whose hooks would then decide another item. The research runs saw the `item/started` of the item before its approval request (research note). Every other server request gets the JSON-RPC error -32601: the v1 `applyPatchApproval` and `execCommandApproval`, `item/permissions/requestApproval`, `item/tool/requestUserInput`, and `mcpServer/elicitation/request`. On 0.166.0 the program ends the item of an approval with an error answer as `declined` (research note, "An `apply_patch` approval under `untrusted` and `read-only`"). With the default policy `never` no approval request comes (ADR 0007, update of 2026-10-16). The answer of the program to an error for `item/permissions/requestApproval`, `item/tool/requestUserInput`, and `mcpServer/elicitation/request` was not run.
- **Output.** Text and reasoning stream as deltas. A tool item is a tool call when it starts and a tool result when it completes. The provider sends no `message_end`.

## Replay

A fresh harness session (no resume id, a lost session, or a changed Codex tool set) gets the rest of the transcript before the first turn's prompt, and the turn gives `{:resume_id, id, cut}` with the number of messages left out. The prompt is the user messages at the end of the context. The replay keeps the newest messages within `@replay_max_bytes` of `Helyx.HarnessIO` and never starts at a tool result. The cut applies to closed history only: the last assistant message, its calls, and their results stay, and the oldest messages before it are left out. An open turn that alone passes the bound fails the turn with a typed error (`docs/adr/0014-hole-proofing-invariants.md`, invariant 3).

- Claude Code writes the replay as lines that start no model call (`shouldQuery: false`), in chunks. Each chunk ends at a replayed user line, and the next chunk goes out at that line's `result` with `num_turns` 0. So the model gets the transcript in its order. A steer while chunks are held goes after the turn's line.
- Codex sends the replay with `thread/inject_items`, then `turn/start`.

## Bounds

| What | Bound | Over the bound | Owner |
| --- | --- | --- | --- |
| stdout line | 16 MiB (`@line_max_bytes` in `Helyx.HarnessIO`) | the provider process stops | provider |
| JSON in a stdout line | a JSON object, with each integer up to the largest integer of the BEAM: on OTP 28 every integer of 1,262,592 digits or fewer decodes, and 1,262,593 nines do not (`docs/features/wire-protocol.md`, "Bounds"); a line of 16 MiB can hold a larger one (#786) | the line is skipped, as perl's own text and any other line that does not decode to a JSON object | provider (`Helyx.HarnessIO.lines/3`) |
| bytes written to the program and not yet read | 16 MiB (`@stdin_max_bytes` in `Helyx.Watchdog`) | the watchdog stops the program group and exits with a status; the provider process stops on that exit | watchdog |
| TERM grace | 5,000 ms (`@term_grace_ms` in `Helyx.HarnessIO`) | KILL. The program's own command groups can stay after a KILL | watchdog |
| replay | 400,000 bytes (`@replay_max_bytes` in `Helyx.HarnessIO`) | the oldest messages are left out; `cut` counts them. The last assistant message and its results stay, or the turn fails with a `:replay_over_limit` error when they alone pass the bound | provider |
| replay: tool call id | 1 to 64 characters of `[a-zA-Z0-9_-]` (`Helyx.HarnessIO.wire_id/1`) | the id becomes `h_` and 62 hex digits of its SHA-256 | provider |
| Codex replay: tool name | `[a-zA-Z0-9_-]` (`tool_name/1` in `Helyx.Provider.Codex.Replay`); no length limit, because none is known for `thread/inject_items`. ## Replaced mechanism

The Helyx `bash` replaces the program's own shell (#478).

| Old | New |
| --- | --- |
| Claude `Bash`, with `run_in_background`, and `Monitor` | off with every other tool of the program (`--tools=`); the model calls `mcp__helyx__bash`, which the hands run, abort, and bound |
| Codex `shell_tool` and `unified_exec` (`commandExecution` items) | disabled by the launch flags; the model calls the `bash` dynamic tool. The `command_running` check stays for a command that the program runs by itself |
| Helyx `read`, `edit`, and `write` next to the program's file tools | sent; Claude has no tools of its own, and Codex keeps the few that no flag removes (`docs/features/provider-parity.md`) |
| Real test: a background `Bash` task outlives an abort, a foreground one ends, the program stays | `claude_code_real_test.exs`: the model's command is a Helyx `bash` call, the hands release it on abort, and the program stays. No model background shell is left to test |

Users see each command as a Helyx `bash` tool cell, and Esc aborts it: the hands release it. A Codex thread stored with the file tools in its set starts fresh with the replay.

## Out of scope

- Approvals in the UI: the approval gate (#882).
- The `granular` approval policy of Codex, and a sandbox or a permission mode option of Claude Code.
- A product option that gives a harness its own shell. It comes when a product needs it.
- Showing the Claude background tasks in the TUI.
- The MCP servers of the user's own Claude or Codex config. They stay. A tool of such a server that starts a process gives it no Helyx abort, output bound, or tool event. The Codex tool lists of the probe had one named `mcp__node_repl__js` (`docs/research/harness-shell-off.md`, "The tool list of the model request").
- `thread/fork`, `thread/revert`, `rewind_files`, and branching.
- Compaction inside the harness: `docs/features/harness-compaction.md` (#552).
- A model switch inside one program: a switch closes the program.

## Current limits

The session end bounds each one.

- A session stop during a wait for an interrupt or an idle close answer can kill the provider process before its close answers (`docs/features/session-lifecycle.md`, "Current limits"). The program then gets TERM from the watchdog before it exits by itself. When the kill fires before the provider process reads the close, the program gets no end of input.
- Claude: a `result` of the turn's own line before its `started` is skipped, so the turn ends only by an abort.
- Claude: an interrupt during a program turn was not run. When the control response does not name the line in `cancelled`, the interrupt waits for a `result`, and its armed kill stops the program.
- Claude: a program turn that starts while a Helyx turn waits for an unresolved steer counts for the Helyx turn.
- Claude: the `started` clause of a steer does not check the start of the turn's line.
- Claude: a prompt that is preparing when a program turn starts makes the session drop the program turn, and its text is lost.
- Claude: an idle close between `background_tasks_changed []` and `task_notification`, when the two lines come in separate reads, ends the program's input. What the program then does was not observed (`docs/research/claude-code-stream-json.md`, "End of input during a program turn").
- Claude: a `task_notification` that starts no program turn gives one more `:busy`.
- Claude: a `tools/call` of a sub-agent runs, but the transcript does not show it: the provider drops sub-agent lines.
- Claude: an interrupt sent while the program is idle can end a background sub-agent of an earlier turn.
- Codex: a child thread whose `completed` item never comes stays in `agents`, so the idle close answers `:busy` until the session ends, and an abort of its turn stops the program.
- Codex: a sub-agent of a sub-agent is not tracked, and an `interacted` child whose earlier turn completes leaves `agents` while its new work runs. A later abort then interrupts and does not stop the program.
- Codex: the transcript names a Helyx call `dynamicToolCall`, as every tool item is named by its type.
- Codex: the digest is taken over the JSON of the specs; a spec with more than 32 parameter keys encodes in hash order, which can change between OTP releases and starts a new thread with the replay.
