# helyx serve

Ticket #661. Decisions of the orchestrator, 2026-10-18 (owner away), in the comment of the ticket.

## Goal

`helyx serve` runs the coding agent as a headless server: Core with the plugins of the agent, and `Helyx.Transport.WebSocket` (`docs/features/wire-protocol.md`). It stays up until the stop of its VM: through the launcher of the release, any signal that ends a process but a fault signal or a signal that was ignored at its start, such as SIGINT, SIGTERM, or SIGHUP; with no launcher, SIGTERM. Clients connect over the wire. This is the step to the end state of ADR 0008: one long-running server owns the sessions.

User stories:

- A user runs `helyx serve` on a home machine and connects from the laptop and the phone, through an SSH tunnel or a TLS proxy.
- Two terminals start `helyx serve` in one data folder at the same moment. One server starts. The other exits 1 with a line that names the address of the first.

Decisions:

1. **The command.** `helyx serve [--host ip] [--port n] [--model provider/model]`. `serve` is the first argument; a folder with the name `serve` is `./serve`. The server starts Core and the transport and prints one line on stdout when it is ready: `helyx: serving on ws://<host>:<port>`. No output holds the token. When that line cannot be printed (a closed output), the server stops with the stop of decision 2 and exits 1. `--model` is the default model of the server (the Core option `:model`), default the default model of the agent. A product owns its daemon: the server is in `apps/coding_agent`, not in Core and not in the transport.
2. **The stop is a Core stop, in the stop of the VM.** The server runs under the supervisor `CodingAgent.Servers` of the `coding_agent` application. SIGTERM to the VM gets the OTP default answer, `init:stop/0`, which stops the applications, and with `coding_agent` the server: its serve process gets the stop of its supervisor and stops, in this order, the transport, which closes every connection, Core, then has the holder of the lock remove the server file, and releases the lock. Then `helyx serve` exits 0. No handler of the server is in `:erl_signal_server`. The OTP handler logs `[notice] SIGTERM received - shutting down` on stdout. The serve process traps exits, so a stop that comes while the server starts waits for the end of the start (Bounds), and then runs: the ready line, if the start printed it, comes before the stop. Each step has the bound of its own stop and no kill, so Core stops only after the last connection, and the supervisor gives the serve process no kill of its own (`shutdown: :infinity`): the ordered stop always runs. The stop of the transport takes at most 20,000 ms: a connection that has not finished its upgrade, such as one inside its HTTP headers, closes at once, and the WebSocket connections stop together, each within 15,000 ms; after a crash of its gate or listener, every connection stops within 15,000 ms (Bounds, #793). A SIGTERM that comes while the stop runs calls `init:stop/0` again, and that does not cut the stop short (the probe of 2026-10-19 in `docs/reviews/2026-10-18-serve.md`). A Core stop ends each session in its `terminate/2`: the session file stays, and a running turn ends as a Core stop ends it (`docs/features/server-management.md`, Out of scope: no aborted results in the file; a resume gives the open calls interrupted results). Reason: the sessions are the state of the user; a stop of the server must not change them more than a crash does. A client that reads the server file while the stop runs finds no listener: the transport stops first.
3. **SIGINT.** The BEAM cannot handle SIGINT (`os:set_signal/2` refuses it, OTP 28), and its break handler stops the VM with no Core stop. So the launcher of the release (`docs/features/local-release.md`) runs `serve` under a perl supervisor: the launcher `exec`s perl, which forks the VM, puts it in a process group of its own (`setpgrp`), and execs the release command with its stdin on `/dev/null`, so the SIGINT of a terminal reaches only the supervisor. Before the fork, the supervisor catches every signal whose default ends a process, by the names that perl knows for its OS: all but the ones that are ignored or stop by default (CHLD, CONT, STOP, TSTP, TTIN, TTOU, URG, WINCH, INFO, and IO on macOS), the two that glibc keeps for itself, and the fault signals (ILL, TRAP, ABRT, BUS, FPE, SEGV, SYS, EMT), whose real delivery a handler would make repeat; perl ignores SIGFPE itself. A signal that was ignored at the start of the supervisor, as under `nohup`, stays ignored by it. So the signals that only Linux has (STKFLT, PWR, IO, the realtime signals) are caught too. A handler only counts the signal. Each one ends the server as SIGTERM does: the loop of the supervisor wakes at a signal or each 0.25 s, sends SIGTERM for each new signal, and then sends it again at a tick each second while the VM lives, at most 20 ticks, since a VM drops a SIGTERM that comes before its signal handler, in its boot. Only the ticks count toward the 20. After them, a new signal still sends one SIGTERM. The supervisor reads the end of the VM with `waitpid` and exits with its status at once: the exit code, or 128 plus the number of the signal that ended it. It sends nothing to the pid after its reap. Every other command keeps the `exec` of before. `mix helyx serve` has no launcher: SIGTERM stops it in order, and SIGINT and SIGHUP keep the BEAM default (Accepted holes).
4. **One lock per data folder.** The data folder is the sessions folder, the storage root of Core (`:sessions_dir`, default `~/.helyx/sessions`). The lock is the `flock` of the session lock (`docs/features/session-lock.md`), on `<data folder>/server.lock`, taken with `Helyx.Session.Lock.take/1`. The serve process owns the port of the lock. No second lock mechanism. The server makes the data folder with `Helyx.Session.File.mkdir/1`, so a folder that it makes gets mode 0700, as at the start of a session (#683). It refuses a data folder that its group or other users can write (`helyx: other users can write the data folder <data folder>; run chmod go-w on it`, exit 1), before it takes the lock: such a user could replace the server file or its temporary file (decision 8). The parent folders of the data folder are the trust boundary of the user, as for the session files. The lock is taken before Core starts, so two starts cannot make two servers.
5. **A second start.** When the lock is held, `helyx serve` reads the server file, connects to its address, and passes the handshake with its token (`Helyx.TUI.Wire.connect/4`, the connect of `CodingAgent.Attach`). Only after `welcome` does it close the connection and exit 1 with `helyx: a server runs for <data folder> at ws://<host>:<port>`. The server file is a hint and the handshake is the proof (#777): from the `flock` of a new server to its remove of a stale file, the file names a server that was killed, and its port can be closed or in use by another program. Only the server that wrote the file has its token. A missing or invalid file, a file with no string token, and any failure of the connect up to `welcome` mean that the server is starting: a refused connection, a failed proof, and also a `refused` of another protocol, which the transport sends before it checks the proof. The holder writes the file after its listener is up, so the second start reads the file and connects again every 100 ms, and starts no attempt after 5,000 ms. Then it exits 1 with `helyx: a server holds the lock of <data folder> and gave no address in 5000 ms`.
6. **Listen.** `127.0.0.1` and a port that the OS picks, by default. `--host` takes an IPv4 or IPv6 address, not a host name; a name would need a resolve that can wait. `--port` takes 0 to 65535; 0 lets the OS pick. A host that is not loopback needs the explicit `--host`. No TLS: for another machine, use an SSH tunnel or a TLS proxy (ADR 0008 §6).
7. **Token.** Each start makes a new token: the base64url of 32 random bytes, with no padding, 43 characters. The token is the text of those 43 characters: a client computes the proof with the key `SHA-256(token)` over these bytes (`wire-protocol.md`, Connection). The transport needs the proof from every connection, also on loopback.
8. **The server file.** `<data folder>/server.json` holds `{"address", "port", "token", "protocol", "pid"}`: the listen address as text, the port that the listener has, the token, `Helyx.Transport.WebSocket.protocol/0`, and the OS pid of the VM. **The holder of the lock owns the file**: the perl process that holds the `flock` does every operation on it, on commands of the serve process (`Helyx.Session.Lock.write_file/3` and `remove_file/2`). Perl holds the `flock` for its whole life, so the operations run only while the lock is held, and a server whose perl ended can do none of them: its commands find a closed port. The server removes a `server.json` that it finds as soon as it holds the lock: the file of a server that was killed must not pass for this one while it starts. When the remove fails, the start releases the lock and exits 1 with `helyx: could not remove the stale server file: <reason>`. It writes the new file after the listener is up: perl removes `server.json.tmp`, makes it again with `O_EXCL|O_NOFOLLOW` and mode 0600, writes it, and renames it to `server.json`. No file or link that is there is written through, no other user can open the file, and a reader sees no file or the whole new one. When the write fails, the start stops with exit 1 and `helyx: could not write the server file: <reason>`. The file is the readiness signal: a client that finds it while the lock is held can connect, but in a stop, which removes the file after the transport and Core, its connect is refused, and a second start names no address (decision 5). A clean stop removes it. A file with no lock holder is stale: the next start replaces it, and a client takes it as no server (#662). The token is made in a closure: the transport gets the closure, and the text of the file is made in the one call that sends it to perl, so no frame, argument, log, or crash report of the serve process holds it (`docs/agents/review-checklist.md`, the secret in data that a dependency can log).
9. **Handshake.** The `challenge` and `hello` of #763 is the version check. A client that gets `refused` shows its protocol number and the `server_protocol` of the frame (#662).
10. **The end of a part.** A crash of Core or of the transport, or the end of the perl process of the lock, stops the server by the same steps, and `helyx serve` exits 1 with one line. After the end of the lock, the stop removes nothing: its command finds a closed port (decision 8). Another server can hold the lock by then, and the file can be its file. A file that this server left is stale, and the next start replaces it. Reason: with no lock, a second server can start; with no Core or no listener, the server serves nothing.

## Interface changes

- `CodingAgent.CLI`: the command `serve` with the new switches `--host ip` and `--port n`, and `--model`. `--host` and `--port` without `serve` give `--host needs serve`. `serve` with a directory argument or with another switch gives one error line; `--help` and `--version` keep their rule and win over `serve`. The usage, the switch lines, and the exit statuses in `--help` name it.
- `CodingAgent.Serve.run/1` (new): runs the server until the stop of the VM, and returns `:ok`, or `{:error, text}`. It starts the serve process as a `:temporary` child of `CodingAgent.Servers`, with `shutdown: :infinity` (decision 2), and waits for its result; the serve process prints where the caller prints. A VM runs one server: the serve process takes the name `CodingAgent.Serve` before any other step and holds it until it ends, after its stop, so a second `run/1` while a server runs returns `{:error, "a server runs in this VM already"}` before it makes the data folder or takes a lock. A caller that ends leaves its server running: the supervisor owns it.
- `CodingAgent.Application` (new): the application of `coding_agent`, with the `Task.Supervisor` `CodingAgent.Servers`.
- `Helyx.Session.File.mkdir/1` (new): makes the sessions folder alone, with the mode rule of `mkdir/3`, which now calls it.
- The serve process reads the server file with `Helyx.Session.File.Scan.read_up_to/2`, a public `@doc false` function of Core, as `Helyx.Session.File` does.
- `Helyx.Session.Lock.take/1` is public: the lock of `<path without extension>.lock`. The serve process calls it and `release/1`. New: `write_file/3` (a file with mode 0600 through `<path>.tmp` and a rename; the data comes in a closure) and `remove_file/2`, which the perl process that holds the lock does (`docs/features/session-lock.md`). The module stays `@moduledoc false` in Core: a product of this repository uses it, and no new interface is made.
- The launcher of `mix helyx.install`: a branch for `serve`, which `exec`s the perl supervisor (decision 3).
- `CodingAgent.error_text/1`: `{:invalid_option, :model}` gives `the model ref is not valid; use provider/model`.

## Replaced mechanism

1. **The launcher `exec` for every command.** The launcher ran `exec <release script> eval ... "$@"` for every argument list. For `serve` it now `exec`s a perl supervisor, which forks the VM into a new process group, waits for it, and ends it with SIGTERM at a signal. Every other command keeps the `exec`. Test: "installs the build under its commit and the launcher passes arguments and folder" keeps its property for a command that is not `serve`; a new test checks the serve branch with a fake release script.
2. **A directory argument named `serve`.** `helyx serve` ran the TUI in the folder `serve`. It now runs the server. `helyx ./serve` keeps the old meaning.
3. `CodingAgent.run/1` is not changed: it still stops Core at its end and aborts its session. The server does not call it.
4. **The address of a second start from the file alone** (#777). A second start named the address of the first valid server file that it read. It now names it only after `welcome` (decision 5). Tests: "a second start names an address only after the handshake with its token", "a second start reads a server file of 4096 bytes", and the slow tests "a second start with no valid server file gives up after the wait" and "a real SIGTERM stops a serve VM with 0; a start in another VM names its address".

## Accepted holes

- A SIGKILL of the VM leaves `server.json`. The kernel frees the lock at the exit of perl, so the file is stale, and the next start replaces it.
- A SIGKILL of the supervisor of the launcher, or a fault signal (ILL, TRAP, ABRT, BUS, SEGV, SYS, EMT) sent to it with `kill`, ends it and leaves the VM running in its own process group (Ownership). The supervisor does not catch the fault signals: a handler would make a real fault repeat.
- `mix helyx serve`, with no launcher: SIGTERM stops it in order; SIGINT (the break handler of the BEAM) and SIGHUP (its OS default) stop the VM with no Core stop, the server file stays, and the next start replaces it.
- A signal other than SIGTERM sent to the VM itself, whose pid the server file holds, keeps the BEAM or OTP default: SIGINT, SIGHUP, SIGUSR1, and SIGQUIT halt the VM with no Core stop (SIGUSR1 writes a crash dump). The launcher never sends them.
- The OTP handler logs its notice of a SIGTERM on stdout, so stdout holds a second line at a stop, after the ready line when the start printed it (decision 2).
- The read of the server file by a second start checks the type of the path, then opens it: it is `Helyx.Session.File.Scan.read_up_to/2`, and `Helyx.ModelInfo.Catalog` reads with the same pattern. A FIFO put in place between the two blocks the open past the wait. Only the owner of the data folder can make it. Open, ticket #777.
- A server that runs and gives no `welcome` gets no address from a second start, which waits 5,000 ms and exits 1 with the line of no address, as before with no file (decision 5): a server of another build, whose `refused` comes before the check of the proof and so proves no token; a server at its cap of 64 connections, which answers the upgrade with HTTP 503 (`wire-protocol.md`); and a server in its stop, whose transport stopped first.
- The `flock` is on the file `server.lock`. A user who removes that file while a server runs lets a second server lock a new file, as for the lock of a session file.

## Out of scope

- The attach of the TUI to a server, and the start of a server in the background (#662).
- A service unit of the OS, and TLS.
