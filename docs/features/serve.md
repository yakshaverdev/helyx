# helyx serve

Ticket #661. Decisions of the orchestrator, 2026-10-18 (owner away), in the comment of the ticket.

## Goal

`helyx serve` runs the coding agent as a headless server: Core with the plugins of the agent, and `Helyx.Transport.WebSocket` (`docs/features/wire-protocol.md`). It stays up until SIGINT, SIGTERM, or SIGHUP. Clients connect over the wire. This is the step to the end state of ADR 0008: one long-running server owns the sessions.

User stories:

- A user runs `helyx serve` on a home machine and connects from the laptop and the phone, through an SSH tunnel or a TLS proxy.
- Two terminals start `helyx serve` in one data folder at the same moment. One server starts. The other exits 1 with a line that names the address of the first.

Decisions:

1. **The command.** `helyx serve [--host ip] [--port n] [--model provider/model]`. `serve` is the first argument; a folder with the name `serve` is `./serve`. The server starts Core and the transport and prints one line on stdout when it is ready: `helyx: serving on ws://<host>:<port>`. No output holds the token. `--model` is the default model of the server (the Core option `:model`), default the default model of the agent. A product owns its daemon: the server is in `apps/coding_agent`, not in Core and not in the transport.
2. **The stop is a Core stop.** SIGTERM, and SIGHUP, start the stop: the server removes the server file, stops the transport, which closes every connection, stops Core, and releases the lock. Then `helyx serve` exits 0. A Core stop ends each session in its `terminate/2`: the session file stays, and a running turn ends as a Core stop ends it (`docs/features/server-management.md`, Out of scope: no aborted results in the file; a resume gives the open calls interrupted results). Reason: the sessions are the state of the user; a stop of the server must not change them more than a crash does.
3. **SIGINT.** The BEAM cannot handle SIGINT (`os:set_signal/2` refuses it, OTP 28), and its break handler stops the VM with no Core stop. So the launcher of the release (`docs/features/local-release.md`) runs `serve` under a perl supervisor: the launcher `exec`s perl, which forks the VM, puts it in a process group of its own (`setpgrp`), and execs the release command, so the SIGINT of a terminal reaches only the supervisor. Before the fork, the supervisor catches every signal whose default ends a process, by the names that perl knows for its OS: all but the ones that are ignored or stop by default (CHLD, CONT, STOP, TSTP, TTIN, TTOU, URG, WINCH, INFO, and IO on macOS) and the two that glibc keeps for itself. So the signals that only Linux has (STKFLT, PWR, IO, the realtime signals) and EMT on macOS are caught too. A handler only counts the signal. A fault signal (ILL, TRAP, BUS, FPE, SEGV, SYS, EMT) goes back to its default at its first delivery, so a real fault in perl ends perl and does not repeat. Each one ends the server as SIGTERM does: the loop of the supervisor wakes at a signal or each 0.25 s, sends SIGTERM for each new signal, and then sends it again at a tick each second while the VM lives, at most 20 ticks, since a VM drops a SIGTERM that comes before its signal handler, in its boot. Only the ticks count toward the 20. After them, a new signal still sends one SIGTERM. The supervisor reads the end of the VM with `waitpid` and exits with its status at once: the exit code, or 128 plus the number of the signal that ended it. It sends nothing to the pid after its reap. Every other command keeps the `exec` of before. `mix helyx serve` has no launcher: SIGINT there keeps the BEAM default, as in print mode.
4. **One lock per data folder.** The data folder is the sessions folder, the storage root of Core (`:sessions_dir`, default `~/.helyx/sessions`). The lock is the `flock` of the session lock (`docs/features/session-lock.md`), on `<data folder>/server.lock`, taken with `Helyx.Session.Lock.take/1`. The serve process owns the port of the lock. No second lock mechanism. The server makes the data folder with `Helyx.Session.File.mkdir/1`, so a folder that it makes gets mode 0700, as at the start of a session (#683). It refuses a data folder that its group or other users can write (`helyx: other users can write the data folder <data folder>; run chmod go-w on it`, exit 1), before it takes the lock: such a user could replace the server file or its temporary file (decision 8). The parent folders of the data folder are the trust boundary of the user, as for the session files. The lock is taken before Core starts, so two starts cannot make two servers.
5. **A second start.** When the lock is held, `helyx serve` reads the server file and exits 1 with `helyx: a server runs for <data folder> at ws://<host>:<port>`. The holder writes the file after its listener is up, so the second start reads the file again every 100 ms, at most 5,000 ms. With no valid file in that time, it exits 1 with `helyx: a server holds the lock of <data folder> and gave no address in 5000 ms`.
6. **Listen.** `127.0.0.1` and a port that the OS picks, by default. `--host` takes an IPv4 or IPv6 address, not a host name; a name would need a resolve that can wait. `--port` takes 0 to 65535; 0 lets the OS pick. A host that is not loopback needs the explicit `--host`. No TLS: for another machine, use an SSH tunnel or a TLS proxy (ADR 0008 §6).
7. **Token.** Each start makes a new token: the base64url of 32 random bytes, with no padding, 43 characters. The token is the text of those 43 characters: a client computes the proof with the key `SHA-256(token)` over these bytes (`wire-protocol.md`, Connection). The transport needs the proof from every connection, also on loopback.
8. **The server file.** `<data folder>/server.json` holds `{"address", "port", "token", "protocol", "pid"}`: the listen address as text, the port that the listener has, the token, `Helyx.Transport.WebSocket.protocol/0`, and the OS pid of the VM. **The holder of the lock owns the file**: the perl process that holds the `flock` does every operation on it, on commands of the serve process (`Helyx.Session.Lock.write_file/3` and `remove_file/2`). Perl holds the `flock` for its whole life, so the operations run only while the lock is held, and a server whose perl ended can do none of them: its commands find a closed port. The server removes a `server.json` that it finds as soon as it holds the lock: the file of a server that was killed must not pass for this one while it starts. When the remove fails, the start releases the lock and exits 1 with `helyx: could not remove the stale server file: <reason>`. It writes the new file after the listener is up: perl removes `server.json.tmp`, makes it again with `O_EXCL|O_NOFOLLOW` and mode 0600, writes it, and renames it to `server.json`. No file or link that is there is written through, no other user can open the file, and a reader sees no file or the whole new one. When the write fails, the start stops with exit 1 and `helyx: could not write the server file: <reason>`. The file is the readiness signal: a client that finds it while the lock is held can connect. A clean stop removes it. A file with no lock holder is stale: the next start replaces it, and a client takes it as no server (#662). The token is made in a closure: the transport gets the closure, and the text of the file is made in the one call that sends it to perl, so no frame, argument, log, or crash report of the serve process holds it (`docs/agents/review-checklist.md`, the secret in data that a dependency can log).
9. **Handshake.** The `challenge` and `hello` of #763 is the version check. A client that gets `refused` shows its protocol number and the `server_protocol` of the frame (#662).
10. **The end of a part.** A crash of Core or of the transport, or the end of the perl process of the lock, stops the server by the same stop, and `helyx serve` exits 1 with one line. After the end of the lock, the stop removes nothing: its command finds a closed port (decision 8). Another server can hold the lock by then, and the file can be its file. A file that this server left is stale, and the next start replaces it. Reason: with no lock, a second server can start; with no Core or no listener, the server serves nothing.

## Interface changes

- `CodingAgent.CLI`: the command `serve` with the new switches `--host ip` and `--port n`, and `--model`. `--host` and `--port` without `serve` give `--host needs serve`. `serve` with a directory argument or with another switch gives one error line; `--help` and `--version` keep their rule and win over `serve`. The usage, the switch lines, and the exit statuses in `--help` name it.
- `CodingAgent.Serve.run/1` (new): runs the server until a stop, and returns `:ok` after a stop by a signal, or `{:error, text}`. The handler in `:erl_signal_server` is global, so a VM runs one server, and the state of the signal server is the guard: the handler of a server takes the place of the OTP handler only (its `init/1` accepts only the handover of the OTP handler), so a second `run/1` while a server runs returns `{:error, "a server runs in this VM already"}` after the lock of its own data folder, which it releases, and before any other step. The serve process supervises its handler (`swap_sup_handler`): the server gives it back after its stop, and when the serve process ends in another way, the signal server removes it and the OTP handler comes back from a process of its own. A caller that ends leaves its server running; the guard stays with the server.
- `Helyx.Session.File.mkdir/1` (new): makes the sessions folder alone, with the mode rule of `mkdir/3`, which now calls it.
- The serve process reads the server file with `Helyx.Session.File.Scan.read_up_to/2`, a public `@doc false` function of Core, as `Helyx.Session.File` does.
- `Helyx.Session.Lock.take/1` is public: the lock of `<path without extension>.lock`. The serve process calls it and `release/1`. New: `write_file/3` (a file with mode 0600 through `<path>.tmp` and a rename; the data comes in a closure) and `remove_file/2`, which the perl process that holds the lock does (`docs/features/session-lock.md`). The module stays `@moduledoc false` in Core: a product of this repository uses it, and no new interface is made.
- The launcher of `mix helyx.install`: a branch for `serve`, which `exec`s the perl supervisor (decision 3).
- `CodingAgent.error_text/1`: `{:invalid_option, :model}` gives `the model ref is not valid; use provider/model`.

## Replaced mechanism

1. **The launcher `exec` for every command.** The launcher ran `exec <release script> eval ... "$@"` for every argument list. For `serve` it now `exec`s a perl supervisor, which forks the VM into a new process group, waits for it, and ends it with SIGTERM at a signal. Every other command keeps the `exec`. Test: "installs the build under its commit and the launcher passes arguments and folder" keeps its property for a command that is not `serve`; a new test checks the serve branch with a fake release script.
2. **A directory argument named `serve`.** `helyx serve` ran the TUI in the folder `serve`. It now runs the server. `helyx ./serve` keeps the old meaning.
3. `CodingAgent.run/1` is not changed: it still stops Core at its end and aborts its session. The server does not call it.

## Accepted holes

- A SIGKILL of the VM leaves `server.json`. The kernel frees the lock at the exit of perl, so the file is stale, and the next start replaces it.
- A SIGKILL of the supervisor of the launcher, or a real fault in its perl, leaves the VM running in its own process group (Ownership).
- `mix helyx serve` keeps the BEAM default for SIGINT (decision 3).
- The read of the server file by a second start checks the type of the path, then opens it: it is `Helyx.Session.File.Scan.read_up_to/2`, and `Helyx.ModelInfo.Catalog` reads with the same pattern. A FIFO put in place between the two blocks the open past the wait. Only the owner of the data folder can make it. Open, ticket #777.
- From the `flock` of perl to the remove of a stale `server.json`, a second start can read that file and name the address of the server that was killed. Open, ticket #777.
- The `flock` is on the file `server.lock`. A user who removes that file while a server runs lets a second server lock a new file, as for the lock of a session file.

## Out of scope

- The attach of the TUI to a server, and the start of a server in the background (#662).
- A service unit of the OS, and TLS.
