# Coding agent (checkpoint one)

A terminal coding agent built on Helyx. It is the first product and it proves the substrate.

## Goal

From the TUI, prompt the agent about a repository. It reads, edits, and runs shell commands in a loop. Output streams. Abort, steer, and follow-up work during a turn. The session resumes after a restart. One user: the author, on this repository.

## Shape

- Root `helyx` Mix project. All bundled plugins live in one Mix project, `plugins/bundled` (app `helyx_plugins`), and the product lives in `apps/coding_agent`. Both depend on Helyx by path, and the product depends on `helyx_plugins` and on `ex_ratatui`, which is optional there (ADR 0005). No umbrella.
- Elixir 1.19 and OTP 28, pinned in `.tool-versions`. Started with a Mix task.

## Runtime

- One session process per conversation, started under a DynamicSupervisor and found by id through Registry.
- Each turn has a turn id and runs in a Task under Core's task supervisor. The session monitors the Task and ignores messages from a Task that is no longer current.
- One hands process per session runs tool calls as Tasks and spawns harness programs. See ADR 0003. Each tool call runs in a Task under Core's task supervisor (row "tool Task" of the ownership table).
- Core starts as a child spec that takes the plugin list. No application config.
- Interface modes: Provider, Tool, and Event are `multi`. ModelContext, Compaction, and Transport are `single`.

### Turn

A local turn runs the provider stream in a Task under Core's task supervisor (row "provider stream Task" of the ownership table). The Task sends each stream event to the session and returns the terminal stream event, `done` or `error`. The session builds the assistant message from the stream events and closes the provider call on the Task's reply. A stream that ends without a terminal event, or a Task that crashes, fails the turn. The tool calls of an assistant message run on the hands one at a time, in call order, so two calls never touch the working directory at once. Each result joins the transcript as it arrives, and the provider is called again after the last one. The turn ends on an assistant message with no tool calls. A connected turn is in `docs/features/long-lived-harness.md`.

### Abort

Abort ends the current turn by id. The session kills the turn Task and tells the hands to cancel that turn id. The hands kill every tool Task for that turn and call the `release/3` of each tool with the handles its Tasks held, with the mode `:cancel` (`docs/features/tool-resource-release.md`). Closing a port does not stop the command behind it, so the bash tool starts each shell command in its own process group and holds it with the hands. Its release sends `SIGTERM` to the group on abort and `SIGKILL` after a short grace period. The hands reply to the session only after every release has returned or passed its deadline, and the session starts the next turn only after that reply, because the hands cannot take a tool call during the release. The session does not wait in a call for that reply. It ends the turn and sends the abort events at once. The reply arrives as a message, and `Helyx.Session.abort/1` returns then. Until the reply, the session answers every client call (#93). A prompt, a steer, or a follow-up in that time queues. One turn starts with the queue after the reply. A second abort in that time drops the queue, and it returns with the first. An abort that the session reads after the reply finds the turn that the queue started. It aborts that turn like any running turn, so the user messages of that turn stay in the transcript, as they do for a prompt and an abort with no release. In both orders, nothing that was sent before an abort runs or waits in a queue when that abort returns. Every tool result and harness event carries its turn id, and the session drops any that arrive for a turn that is no longer current. A shell command killed mid-write can leave a half-written file. That is accepted.

When a turn is aborted, by the user or by a restart, every tool call in it that has no result gets a tool result entry with `is_error` true and the text `aborted`, so the next provider call sees a complete call and result pair. A live abort appends the entry to the transcript and the file. After a restart, the resume adds it on read and writes nothing (#269, see Persistence). Providers reject a tool call without a result, so removing the call is not an option.

### Steer and follow-up queues

Queued steers join the transcript as user messages, in order, before the next provider call inside the turn. Queued follow-ups start a new turn after the current turn ends normally; anything still queued at that point, steers included, becomes that one new turn's prompt, steers first, so no typed message is lost. A steer or follow-up sent with no turn running starts a turn at once, like a prompt, so the client never races the end of a turn. Abort and turn failure drop both queues. The queues live in the session process only and are not persisted. Every change emits a `queue_update` event with the counts; the drain at a normal turn end goes out between turns with a nil turn id. Each queue holds at most 32 entries; past the cap the call returns `{:error, :queue_full}` and the TUI keeps the text in the composer and shows the reason in the status bar (#46).

A model is named by one string, `provider/model`. A session parses it once per start, resume, and switch.

### Model switching

`Helyx.Session.set_model/2` switches the model of a running session. The ref goes through the same parse and the same provider lookup as the `:model` of `Session.start`. These are the errors (`t:Helyx.Session.model_error/0`):

- A bad ref returns `{:error, {:invalid_model_ref, ref}}`.
- An unknown prefix returns `{:error, {:unknown_provider, id}}`.

A bad or a shared provider id never reaches a session: Core checks every `id/0` once, at start, and does not start (the Provider id row, #169).

In every case the model, the file, and the event stream stay as they were. An accepted switch does three things inside one session call: it appends a `model_change` entry to the session file, it replaces the session's model ref and provider module, and it emits a `model_change` event with the new ref. A switch to the current model is accepted and recorded like any other.

A turn fixes its model and provider when it starts. A switch during a turn is accepted at once, but every provider call of the running turn, and the `model` of its assistant messages, stay on the old model. The next turn, a queued follow-up too, uses the new one. The switch belongs to no turn, so its event carries a nil turn id, during a turn too.

A `model_change` append that fails on disk is treated like a message append that fails: a warning, one `:notice` event (#262), persistence off for the session, and the switch still holds in memory.

Both directions between a model provider and a harness provider go through this one path, because the session sees only a provider module. A switch to a provider with an external turn starts a fresh harness session that gets the transcript (see Harness turns).

### Harness turns

> Since ADR 0007 and its amendment (#265), both harness providers are connected: the program lives for the session (`docs/features/long-lived-harness.md`), and a provider is connected when it exports `harness_init/3`. The Steer and Turn items below describe the removed per-turn mode; the Stream and Resume items still hold for the events of a connected turn.

A harness runs its own loop and its own tools. Helyx starts the program for the turn, translates its output into messages and events, and records them in the transcript. Helyx tools are not visible to the harness (ADR 0002).

- Steer: a harness does not accept a message inside a turn. On an external turn, a steer queues and aborts the turn, and when the hands have released the program, a new turn starts with the queued messages. The provider's prompt is every user message at the end of the transcript, so a prompt the harness did not answer is sent again with the steer. The transcript keeps whatever the harness completed before the abort.
- Turn: a provider's optional `turn/0` returns `:external`; the default is `:local`. The session calls `Helyx.Provider.turn/1` once, in the caller of a start, a resume, or a switch, and keeps the result; a `turn/0` that raises, throws, exits, or returns any other value fails that call with `{:bad_provider_turn, id}`, so no session runs plugin code for the turn. The stream of an external turn runs as a Task of the hands with the provider module in the place of the tool, so the provider holds the process groups of its program with `Helyx.Tool.hold/1` and implements `release/3` (ADR 0004). Its terminal reaches the session as `{:stream_end, turn_id, terminal}` after the release. While a handle is unconfirmed, the hands refuse the stream of an external turn like a tool call; the stream of a local turn is not a Task of the hands and is never refused.
- Stream: besides the deltas and tool calls, a harness stream sends `{:tool_result, call_id, {status, text}}` for each result. The first result of a call of the open assistant message closes that message (#385; before, the harness sent `message_end`). The session appends each message and each result as it arrives, with the events of a model turn: `message_end`, `tool_execution_start` for each call, `tool_execution_end` for each result. No message goes between a call and its result: before the session appends a message, each call of an earlier message with no result gets an `aborted` error result. A result for a call of no completed message, or for a call that got its `aborted` result, is dropped. So is a result whose id matches no open call, for example an id that is not valid UTF-8: the session uses the id only to find the call. At the end of the call, when the turn fails, and on an abort or a steer, each call with no result gets an `aborted` error result. A result that arrives, or is aborted, after the next message has started to stream has its `tool_execution_end` event after that message's `message_start` and the deltas sent before it; the transcript order is as stated. The session never runs the tool calls of an external turn on the hands.
- Resume: each harness issues its own session id. The provider reports the id of each fresh harness session as `{:harness_session, id, cut}` when its first turn is written (Claude Code) or at the first turn on a thread that `thread/start` made (Codex). The session writes it to the transcript as a `harness_session` entry, keeps the last id of each provider (restored on resume), and emits a `harness_session` event, `%{provider, harness_session_id, lost, cut}`. A turn passes the stored id as `:harness_session_id` only when the last assistant message of the transcript came from this provider after that harness session's entry; otherwise it passes nil. A message of the harness session shows that it read the whole replay and the prompt. A fresh session that ends before its first message (an abort, a steer, a failure, or a restart) is not resumed, and the next turn replays again. The session keeps the number of messages before each provider's last entry. On resume, the file gives this number back, and drops every label at or above a fork of the file at or below a harness session entry (#282, "Session file"). If the harness no longer has the session, the provider starts a fresh one in the same call, and `lost` is true. The TUI shows a notice that the harness lost its own context.
- Replay: a fresh harness session (the first harness turn, a lost session, or a switch from another provider) gets the transcript before the prompt. For Claude Code, the provider sends the history over stdin as stream-json lines: one `assistant` line per assistant message (text and tool calls; thinking is not replayed), and one `user` line with `shouldQuery: false` for each run of user messages and tool results, so no replayed line starts a model call. A tool call id that is not 1 to 64 characters of `[a-zA-Z0-9_-]` becomes `h_` and 62 hex digits of its SHA-256, the same for the call and its result (`HarnessIO.wire_id/1`, shared with Codex), so two ids stay two except through a SHA-256 collision. The prompt is the user messages at the end of the transcript. The replay keeps the newest lines within 400,000 bytes and starts at a line with no tool result, so every kept result keeps its call; `cut` counts the messages left out, and the TUI shows a notice when it is above 0. The facts are in `docs/research/claude-code-stream-json.md`. For Codex, the provider sends the history with one `thread/inject_items` request before `turn/start`; it makes no model call. Each message gives Responses API items: a user message an `input_text` message, an assistant message an `output_text` message per text and a `function_call` per tool call (thinking is not replayed), and a tool result a `function_call_output`. A call id gets the same `HarnessIO.wire_id/1` as for Claude Code; a tool name gets every other character replaced with `_` and is cut at 64, the function name limit of the Chat Completions API; that limit is not verified for `thread/inject_items` (research note). The same 400,000-byte cap and start rule apply, counted on the JSON of the items (`HarnessIO.cap_replay/3` in `plugins/bundled/lib/helyx/harness_io.ex`, shared by both providers).
- Claude Code is a connected provider (ADR 0007, #200). `harness_init/3` runs one `claude` from `PATH` for the session, with `--output-format stream-json --verbose --include-partial-messages --input-format stream-json --permission-mode bypassPermissions --model=<model>` and no `-p`, and with `--session-id=<new uuid>`, or `--resume=<id>` for a resume, under `Helyx.Watchdog` with open input in the session's working directory. A turn is one user line; an interrupt is the control request `interrupt` with `cancel_queued: true`. The details are in `docs/features/long-lived-harness.md`, sections "Claude Code" and "Built in #200". Its stderr is dropped; the `result` line carries the errors.
- Codex runs `codex app-server` from `PATH` under `Helyx.Watchdog` in the session's working directory, with open input (row "watchdog input on stdin"), and speaks JSON-RPC lines (#11). Since #201 one program serves the session's harness process (`docs/features/long-lived-harness.md`, section "Codex", and ADR 0007): its connect sends `initialize`, then `thread/resume` with the stored id, or `thread/start`, and each turn is a `turn/start` with the prompt. A resume error `no rollout found` is a lost thread: the same run starts a fresh thread. Threads run with the approval policy `never` and the sandbox `danger-full-access`, the trust of the bash tool. A command or file change approval request that still arrives is answered `accept`; every other server request gets the JSON-RPC error -32601. The program's input ends only at a close: the session end or a provider switch. A tool item (a command, a file change, an MCP tool call, and the other item types in the research note) is a tool call when it starts and a tool result when it completes; only the notifications of the run's own thread count. The session closes the message at the first result of one of its calls. A call of a closed message that still runs at the next close gets `aborted`, and its later result is dropped (#385, `docs/features/long-lived-harness.md`, section "Built in #385"). `Helyx.Provider` states the rule for every harness provider. An abort sends `turn/interrupt` when no `commandExecution` item of the turn is open, and stops the program when one is; a turn that ends with an open `commandExecution` item also stops the program, so no next turn starts while the command runs (row "Codex program"). The facts are in `docs/research/codex-app-server.md`.
- Stream Task shutdown (#11): removed with the per-turn mode (#265). The cancel of the hands brutal-kills every Task of the turn, then releases its handles. The Claude Code harness process does not trap exits (#167), so it dies at once in every phase, also behind queued stdout. Codex has no stream Task since #201: its harness process does not trap exits.

## Ownership

When anything above a command dies, the command stops. Two rules cover every path (ADR 0004): inside the VM, work is linked to its owner, and the owner traps exits so a crash below it stays a message; at the OS boundary, a command's life is tied to its port through the perl watchdog. perl is required; the bash tool's `check/0` reports a system without it at session start and resume, before any file or process is created, and the session fails to start with a clear error (row "Tool checks at session start"). The Claude Code and Codex providers check for perl next to their program lookup, in `harness_init/3` (Claude Code) or `stream/3` (Codex) (`Helyx.HarnessIO.find/1`); without it the turn fails with an error that names perl, and the session lives. A watchdog that ends with no marker gives a result that names perl. perl removed after the check makes `Port.open` raise in the caller (#367 removed the rescue of #141, which no observed run needed). The no-marker text names the perl watchdog, not a cause: an argv over the OS limit also ends there.

## Transcript and events

- Message shape and session file format: see ADR 0001 and the section below.
- Session files live under `~/.helyx/sessions/<project>/<session>.jsonl`.
- Twelve events: `agent_start`, `agent_end`, `turn_start`, `turn_end`, `message_start`, `message_update`, `message_end`, `tool_execution_start`, `tool_execution_end`, `queue_update`, `model_change`, `harness_session`. Each carries the session id, the session instance id (#204), the turn id (nil on the queue drain between turns and on every `model_change`), and a sequence number.

### Session file

One JSON object per line. Every entry has `id`, `parent_id`, `ts`, and `type`. The first entry is the header and its `parent_id` is null. Example entries, one per kind:

```json
{"id":"01J...","parent_id":null,"ts":"2026-09-17T10:00:00Z","type":"session","version":1,"cwd":"/path/to/repo","model":"opencode-go/kimi-k2"}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"message","role":"user","content":[{"type":"text","text":"List the tests."}]}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"message","role":"assistant","model":"opencode-go/kimi-k2","stop_reason":"tool_use","usage":{"input":120,"output":40},"content":[{"type":"text","text":"Listing."},{"type":"tool_call","id":"call_1","name":"bash","arguments":{"command":"ls test"}}]}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"message","role":"tool_result","tool_call_id":"call_1","tool_name":"bash","is_error":false,"content":[{"type":"text","text":"core_test.exs"}]}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"model_change","model":"claude-code/opus"}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"harness_session","provider":"claude-code","harness_session_id":"..."}
```

Content blocks: `text` has `text`. `thinking` has `thinking` and an optional `signature`. `tool_call` has `id`, `name`, and `arguments`. `image` has `mime_type` and base64 `data`.

Rules:

- The header carries `version`. A reader rejects a version it does not know.
- `Helyx.Message.stop_reasons/0` owns the closed `stop_reason` set, and the format encodes it: `end_turn`, `tool_use`, `max_tokens`. A reader decodes them without touching the atom table's history, so a fresh VM resumes a saved file. A terminal event with a stop reason outside the set, or a usage the file cannot encode, fails the turn as a malformed stream event before the message exists. A new stop reason is a format change.
- A tool result links to its call by `tool_call_id`. A tool call with no result after the turn ended gets an `aborted` error result on read, never on write (#269). A tool result that answers no open call at its place (no call with its id, a second result for one call, or a result after a later message) is dropped on read, and the file keeps it (#417). User story: I resume a session that stopped in the middle of a tool call. The model gets valid call and result pairs. Nothing is written to the file until I do something. The resume reads the branch. For each call with no result among the tool results right after its message, it inserts one `aborted` result after those results (`Helyx.Session.Transcript.abort_unanswered/2`). The file keeps the open call, and the next turn appends after it. So every resume inserts the same results at the same place. A file that already has its `aborted` results (written before #269) resumes unchanged. The provider request, the Claude Code replay, and the snapshot all read this one transcript. The file counts the messages before a harness session without the inserted results. So the resume adds the results inserted at or before each count and subtracts the results dropped before it, and `resumable/3` drops the same messages as in the live session. A count exactly at an insert point can come from an entry written before the crash, and then the live count was lower. An inserted or a dropped result is never an assistant message, so `resumable/3` gives the same answer for both counts. The resume still appends a newline when the last line has none (#266), because the next entry must start on a line of its own. It writes no entry.
- Streamed partial messages are not written. Only the completed message is appended, after the provider finishes it.
- The file is a tree (#266, ADR 0001). Two writers that append to one file, two Cores that resumed one session, make two branches: the `parent_id` of each entry is the leaf of its own writer. User story: I have one session open in two Helyx servers on one disk, and both write to it. Neither conversation is mixed with the other, no byte of either is cut off, and a later resume gives me the branch I wrote last. Moving between a laptop and a phone uses one server with a second client (ADR 0006) and does not reach this path.
- **One write per entry.** Each entry and its newline go to the file in one append write. `File.write/3` makes one binary of them (`file:write_file/3`), opens the file with `append` (`O_APPEND`), and writes the binary with one `writev` (`prim_file:write/2`, OTP 28). POSIX `write()`: with `O_APPEND`, no other change of the file comes between the move of the offset to the end and the write. On a local filesystem the entries of two writers thus do not interleave. A short write (a full disk, a signal) makes `prim_file` write the rest with a second `writev`, which another writer can come between: the line is then torn, and the rule below skips it. A network filesystem is out of scope: `open(2)` on Linux states that `O_APPEND` can corrupt a file on NFS when more than one process appends at once.
- **Read as a tree.** The file is read line by line. A line that does not decode to a JSON object with a `type` is skipped wherever it is: a torn write, or a torn write that the next append of another writer was glued to. The reader indexes the entries by `id` in file order and builds the transcript by walking `parent_id` from a leaf to the header. The header, the first entry, is the root whatever its own `parent_id` says.
- **The newest leaf.** A resume takes the branch of the last entry in file order whose chain of parents reaches the header and whose id is not repeated (see the damage rule). In a file with no damage, that is the last complete entry. The model is the last model change on that branch, and the harness session labels and the message counts before them are those of that branch, without the labels that a fork drops (below).
- **Damage from the disk, one rule each.** An entry whose `parent_id` does not name an earlier entry of the file (a missing parent, a `null` parent on an entry that is not the header, a parent later in the file, and so every cycle) is on no branch, and neither is any entry below it. It stays in the file, and the resume takes the newest entry that reaches the header. This is the smallest unit: the other entries of the file are known good. It also covers a glued line: the entries that its writer appends below it lose their parent. An entry whose `id` is missing or not a string has no identity: no entry can name it as a parent, so it is on no branch, nor any entry below it. A repeated `id` is kept to the smallest unit. Before the repeat, a child can only mean the first entry, because a parent is always earlier in the file, so the branch through the first entry stands. The repeat itself is on no branch, and so is every later entry that names that id as its parent: it cannot tell the two apart. The header keeps its place as the root when a later entry repeats its id. A repeated id is never the leaf: the next append names the leaf as its parent, so a repeated leaf would put all new work on no branch. The resume takes the newest entry that reaches the header and whose id is not repeated, and the transcript ends at that entry. When no such entry exists (the header id is repeated, and so is the id of every other entry that reaches the header), no entry can take a child, and the resume fails with `{:invalid_file, _}` and changes nothing: this is the stated larger failure. The writer makes ids of 72 random bits, so two writers do not make one id by chance; a repeat comes from a hand edit. Only the entries on the branch get the shape checks and the decode of the next rule. An entry on no branch is never read, so a bad shape there does not stop the resume.
- **Repair never truncates.** Nothing is ever removed from the file: a truncate could cut bytes that another writer appended. When a resume finds that the file does not end in a newline, it appends one before the session appends anything. A whole last entry is kept that way; a torn one stays a line of its own that every read skips, and the next entry starts on a new line. A running writer that did not resume does not add the newline: its next entry is glued to the torn line (see the damage rule). A skip sends no signal: when damage cuts a branch, the resume goes back to the newest entry that still reaches the header, and the log and the clients are not told. Accepted: the ticket asks for the skip, and a notice needs a snapshot field (see the write failure rule below).
- **A fork drops every harness session label at or above it (#282).** User story: I have one session open in two Helyx servers, both on Claude Code or Codex, and the conversation forks into two branches. When I resume one branch, the harness gets that branch replayed and holds none of the turns of the other. Two Cores that resume one session with a label both continue that harness session, so its external conversation holds the turns of both branches. So on resume, when an entry of the file that is not on the branch names a branch entry at or below a harness session entry as its parent, every label at or above that fork point is dropped, of every provider, and each harness starts fresh and gets the branch replayed. A label written below the last fork is kept: only its own branch has it. The rule is derived on read in `Session.File.Branch` (`last_fork/2`): no lock between servers and no write at resume. Every entry that names a branch entry counts, also one on no branch (the damage rule), because the reader cannot tell another writer's work from damage. The exceptions are an entry that repeats the id of a branch entry at or below the first harness session entry, and a header whose `parent_id` names a branch entry at or below a harness session entry (it drops the labels at or above that entry with no fork). A line with no `type` is skipped as a line that does not decode, so it names no parent. Only a hand edit makes any of these. Accepted holes, each of which costs at most one replay or keeps the state before #282: two Cores that are live at the same time continue the one harness session until their next resume, because each resumed before the fork existed; a fork whose other branch never used that harness, or started its own fresh harness session, still drops the label; a label of a provider that the other branch never continued is dropped with the rest; and a fork whose child lines do not decode (a short write that another writer's line splits) is not seen, because a skipped line names no parent, so the label stays. The writer appends each entry in one write, so that last case needs a torn write.
- A file written before #266 is one chain, because its one writer set each `parent_id` to the entry before it, so it resumes with the same transcript.
- A reader never raises at the caller. A header with an unknown or missing version, and an entry on the branch with a shape the writer never produces, come back as `{:error, reason}`. An optional value is the exception: it is not needed to resume, so a bad one does not lose the chat. On a message, a `usage` that is not a map reads as `%{}`, and a `model` that is not a string or a `stop_reason` outside the set of `Helyx.Message.stop_reasons/0` reads as nil, as a missing one does. The role, the content, `tool_call_id`, `tool_name`, and `is_error` keep their checks. A bad harness session label is dropped (see the harness session row). A line that does not decode is skipped (see above). A repair that cannot write, and a sessions directory that cannot be written on create, are their own error classes.
- Provider deltas that are not valid UTF-8, and tool calls whose fields the file cannot encode, fail the turn as malformed stream events; prompts that are not valid UTF-8 are rejected at the client. Transcript text is valid, and every value in it survives the round trip to the file, from the moment it exists.
- Tool output is repaired to valid UTF-8 at its two boundaries, before it enters the transcript (row "tool result text validity"). So every consumer of the transcript, the file, the providers, and the TUI, sees valid text.
- A write failure mid-session logs a warning, sends one `:notice` event with a fixed text (#262), turns persistence off for that session, and the turn continues on the in-memory transcript. The notice carries the id of the running turn, or none between turns. Persistence stays off, so the notice goes out once per session. A resume writes no entry (#269), so no write can fail before a client subscribes.

The open message also has at most 1,024 blocks (`@max_message_blocks`, #439), a safety budget and not a provider limit: a delta that merges into the last block, when that block is of its kind, makes no new block, a tool call is one, and the count starts again at 0 with the byte count; without it, alternating 1-byte text and thinking deltas make about 8 million blocks within 8 MiB | The delta or call is a contract break: the provider process stops and the turn fails with `{:message_too_large, bytes, 8_388_608}`, or with `{:too_many_blocks, 1025, 1024}` for the 1,025th block, through the usual failure path (`TurnLoop.stop_provider/2`). The delta or call is not added and nothing is cut |
| Harness tool result text, as the provider sends it | 65,536 bytes (`@max_tool_result_bytes` in `Helyx.Session.Stream`), checked on the text as sent, before the UTF-8 repair; the stdout line cap bounds it before that. Every output of the provider cut fits: at most 51,201 bytes of lines and a notice of less than 200 bytes. Core counts bytes, not lines: a provider that breaks the contract can send up to 65,537 lines within the limit (65,536 newlines), and the TUI wraps that one cell whole (row "Transcript scrollback"). The TUI shows the text after the UTF-8 repair, so that cell is at most three times the limit, 196,608 bytes (row "tool result text validity") | the turn fails with `{:tool_result_too_large, actual_bytes, 65_536}` through the usual failure path, and every open call gets its aborted result; the error does not hold the text |
| Harness tool result text, after the provider cut | 2000 lines or 51,200 bytes of line content, on whole lines, by `Helyx.Text.truncate/2`, `:tail`, in `Helyx.Provider.ClaudeCode.Turn` and `Helyx.Provider.Codex.Items` before they send the event | See the row "tool result text" |
| SSE line from the model gateway | 1 MiB, terminated or not; a partial line counts its trailing `\r`. The buffer overshoots by at most one transport chunk. `Helyx.Provider.OpenAI` decodes each `data:` payload with `JSON.decode/1` in the provider Task, so this cap bounds the decode; there is no heap cap, accepted (#106) | One `{:error, {:line_over_limit, limit}}` event ends the stream |
| Tool call bytes per response (arguments, ids, and names that the calls hold) | 10 MiB across all calls, overshooting by at most one line; a call holds its arguments as one binary, so the count is what the parser holds. A call index is an integer from 0 to 10,000, which bounds the number of calls. The shape check follows the OpenAI streaming format: `choices` is a list, null, or missing, its first choice and its `delta` are maps, `tool_calls` is a list, every field but the index can be missing or null (`false` is a value of the wrong type), and every call delta has an integer index, a string or missing `id`, and a map or missing `function` with a string or missing `name` and `arguments`. A call takes its id and name from the first delta that has them, and each delta appends its argument fragment. A chunk that fails the check, an index out of the range, or a missing or null index included, ends the stream with `{:error, {:bad_chunk, payload}}` (#368). The text and thinking deltas go to Core as they are, and Core fails the turn on one that is not a string (`Helyx.Session.Stream`). `finish_reason` is a string and `usage` a map whose `prompt_tokens` and `completion_tokens` are integers; each can be missing or null, and a finish reason that the provider does not name is `end_turn`. An `error` that is not null is an API error, `{:error, {:api_error, error}}`, which holds the value as it came and fails the turn. The index range is a safety bound with no outside source: the byte count does not see a call that holds no bytes. The arguments of each call are decoded with `JSON.decode/1` at the end of the message, so this cap bounds the decode; there is no heap cap, accepted (#106) | One `{:error, {:tool_call_bytes_over_limit, limit}}` event ends the stream; no partial call is emitted |
| Tool call arguments of the OpenAI provider (#146) | A JSON object, or no bytes for `%{}` | Other arguments go on as their raw text in a `tool_call` (#380). `Helyx.Session.Stream` gives the call `%{}` and a rejection reason, and the session gives it the error result `tool call not run: the arguments are not a valid JSON object`; the text and the other calls of the message stay, and the model can correct the call. A call with no id cannot get a paired result: `Helyx.Session.Stream` rejects a tool call with an empty id as a malformed event, so it fails the turn with `{:bad_stream_event, {:tool_call, call}}`, with valid arguments or not (#345). The raw text is dropped at the Core check in the provider process, so no transcript entry, session file entry, or tool result holds it. Core's error for a malformed call or request and the helper's error for a repeated call id name the call with `%{}`. An error that holds a provider value as sent can hold the raw text: the `{:bad_chunk, payload}` error of the parser (row above) holds the chunk, at most one SSE line of 1 MiB. Accepted: an error is bounded like every provider value, and the raw text is the model's own output. Before the check the raw text is within the 10 MiB limit on tool call bytes |
| Integer in tool call arguments and in the usage of a provider call | 100 digits, for each integer at any depth, map keys and struct fields included, because the JSON encode of an integer is quadratic in its digits (#79). `Helyx.Session.Stream` checks the arguments and the usage with `Helyx.Message.big_integer?/1` before the first encode, in the provider process. An error reason and the reason of a Task exit get `Helyx.Message.cap_integers/1`, which replaces such an integer with a marker string. On resume, the session file applies `cap_integers/1` to the arguments of a tool call block and to the usage of a message. Not covered, and accepted: a provider that raises or exits with such an integer in the reason, because the crash report of the Task makes the digit text; and an integer over the integer size limit of the BEAM in the JSON decode of a provider, which raises, so the provider Task exits and the turn fails | A tool call or tool request with such an integer goes on with arguments `%{}` and gets an error tool result, `tool call not run: an integer in the arguments has more than 100 digits`; the other calls of the message run. A usage with such an integer is a malformed stream event, which fails the turn, as are arguments or a usage that are a struct, not a plain map. A float is not changed: its encode is short |
| HTTP error response body | 16 KiB; the accumulator overshoots by at most one transport chunk | The body is cut by `Helyx.Text.cap/3` to valid UTF-8 at the limit and marked `[truncated at the N-byte limit]`; the rest of the response is cancelled. A transport error while the body is read fails the turn as a Task exit |
| Wait for bytes from the model gateway (`@chunk_idle_ms` in `plugins/bundled/lib/helyx/provider/openai.ex`) | 120,000 ms between two chunks of the response, the first chunk included. Req applies it to each chunk, so it is not a limit on the full response. The total time of a response is unbounded, and accepted with no ticket, because the abort of the user is the bound: a gateway that sends one chunk in each 120 s holds the turn until the abort | Before the response starts, the stream gives one `{:error, reason}` event with the transport error. During the body, the timeout raises in the turn Task, and the turn fails as `{:task_exit, reason}`. The session accepts the next prompt |

The three provider limits carry no research citation: `docs/research/coding-tools.md` covers tool output truncation, not gateway input, so the values are set here.

Ownership:

| Resource | Holder | Release |
|---|---|---|
| Session file append (#266) | One entry and its newline in one binary, one `File.write/3` with `:append` (`O_APPEND`), one `writev` on a local filesystem; the entry size is bounded by what the session puts into it, and the file by the 64 MiB limit on resume | A short write (a full disk, a signal) takes a second `writev` that another writer can come between: the line tears and every read skips it (rule "Read as a tree"). A network filesystem is out of scope |
| Session file handle | The calling process; every read and append opens and closes inside one `Session.File` call | On return; no handle outlives a call |

A `Session.start` that fails after the file is created (a supervisor or hands failure) can leave a header-only session that a later resume restores as an empty transcript with the right model. Open, accepted for checkpoint one; the window is narrowed by creating the file only after the plugins resolve.

Nothing locks a session file: two runtimes that resume the same file each write their own branch (#266, rules above), and a resume reads one branch. A UI to list or switch branches is out of scope. One more hole is open and accepted for checkpoint one. A resumed session starts a new event stream: sequence numbers restart at one, and no client API reads the restored transcript. The TUI starts empty after a resume, and the model keeps the full context. Ticket #163 adds the session history to the TUI (#105).

## TUI

- ex_ratatui, alternate screen. The TUI is `Helyx.TUI` in `plugins/bundled`, defined only when `ex_ratatui` is loaded (ADR 0005). `Helyx.TUI` owns the terminal loop and the key dispatch. `Helyx.TUI.Composer` owns the composer and its paste markers, and `Helyx.TUI.Transcript` owns the transcript rows and the scroll position rule; both have the same guard. `Helyx.TUI.Wrap` (the width rule) and `Helyx.TUI.ViewModel` need nothing from `ex_ratatui` and have no guard. `Helyx.TUI` implements no Core interface and is not in Core's plugin list: it is a client that subscribes to one session. Local delivery is OTP messages from `Helyx.Session.subscribe/1`; a Transport interface arrives with the first remote client.
- The view model is a pure fold over events, `Helyx.TUI.ViewModel`, tested with scripted event lists. It grows with the conversation, bounded by the session. A tool result attaches to the oldest open tool cell with the same `tool_call_id`, wherever the cell is (#83). That is the rule of the session: an external turn can start two calls with one id, and the first result answers the first call (#163). A notice can arrive while the tool runs. The session runs tool calls one at a time. The fold does not depend on that order. Core makes every event from checked data, so the fold trusts the shapes of `Helyx.Event`: an event of another shape is a bug in Core and crashes the TUI. The fold ignores `:turn_start`, `:turn_end`, and the `:message_start` of a user message on purpose. The composer is human input; its size is accepted as unbounded, like a queue entry's text (#29). Tool results render at most four content lines each, plus one truncation row naming the hidden line count. Transcript lines wrap by terminal display width, not by grapheme count; the bounds table has the rule and its exceptions (#40).
- The TUI mounts from the snapshot that `Helyx.Session.subscribe/1` returns, so a resumed session shows its history and a late client shows the running turn. `mix helyx --resume` passes `resumed: true` to `Helyx.TUI.run/1`, and a notice "resumed session" follows the history. The design is in `docs/features/session-snapshot.md` (#163).
- PgUp and PgDn scroll the transcript by one screen (#39). While the view is scrolled, new output does not move it, and the status bar says that the view is scrolled. Ctrl+End, a PgDn at the end, or a sent prompt returns the view to the newest output. The position is client state of the TUI process. It is not in the view model, because it depends on the terminal size, and the fold knows no terminal. The bounds table has the costs and the exceptions.
- Escape aborts. Enter sends a steer during a turn and a prompt when idle. Alt plus Enter queues a follow-up: most terminals cannot tell Shift+Enter from Enter without the kitty keyboard protocol, so Alt is the modifier. Ctrl+J adds a new line; the composer and the paste rules are in `docs/features/multiline-composer.md` (#44). The status bar shows the model, the run state, and the queue counts. When the client rejects input, the status bar also shows the reason in red, as ` ✕ <reason> ` at the start of the line: `not sent: the queue is full` or `not sent: the session ended` for a steer or a follow-up. The rejected text stays in the composer. The reason is the `reason` field of the view model. It is client-local, like a notice: `ViewModel.reject/2` sets it, and no event changes it. Each reason is a fixed text of `Helyx.TUI`, so it holds no input and its longest text is 27 bytes. The reason comes first because the line does not wrap and a model ref can be 256 bytes; the reason is at most 31 columns with its mark, so it shows in full at 31 columns or more. The next key press or paste clears the reason before the TUI handles that input, so the same input can set a new reason. A new reject replaces the reason, also when it comes from a key repeat, because the newest reject is the one the user must see. The release and the repeat of a key do not clear it, because those of the rejected Enter come immediately after the reject. There is no terminal bell. A rejected `/model` switch stays a notice cell, because its text must stay visible while the user corrects the ref.
- `/model provider/model` in the composer switches the model through `Session.set_model/2`, idle or during a turn. It is the only command. The rule is on bytes, not on looks: a line that starts with `/model`, after whitespace, is never sent as a message, and any other text is a message; see the bounds table for the exact rule and its limit. The status bar changes when the `model_change` event arrives, not when the call returns, so the view model stays a fold over events. A rejected switch adds a notice cell (`ViewModel.notice/2`, client-local like the composer) and keeps the text in the composer.
- Queued steers are delivered together at the next provider call. On an external turn, a steer aborts and resends (see Harness turns).
- The `helyx` Mix task lives in `apps/coding_agent`. `mix helyx [directory] [--model provider/model] [--resume]` starts Core with the bundled plugins, one session in `directory` (default: the current one), and the TUI, and quitting restores the terminal. The session is written under `~/.helyx/sessions`; `--resume` continues the most recent session for the directory with its saved model, so it does not combine with `--model`. The scan for that session reads only the 256 files with the newest modification time in the project directory, and an append sets that time. A session older than those files is not found, and the task prints the `:not_found` sentence, `no saved session for this directory; start one without --resume`, although the file exists. A start or a resume that fails prints one line on stderr, `could not start the agent: <sentence>`, and the task exits with a non-zero status. `CodingAgent.error_text/1` is the one place that makes the sentence. It has a clause for each shape of `Helyx.Session.File.error/0`, for the model ref and provider errors, for `{:tool_unavailable, name, reason}`, and for `{:terminal_init_failed, text}`. The `:too_large` text prints as it is. An invalid model ref stays out of the sentence, as in the TUI notice. A value from the file (`:unknown_version`, the type of a bad entry, a provider id) prints through `inspect/1` with its default limits, so a JSON object shows as a map. A bare atom prints as its POSIX text when it is a POSIX code. An error with no clause prints through `inspect/1`, so it can show as a tuple: a duplicate tool name, a bad tool spec (`{:bad_tool_spec, label}`, #142), a bad or a shared provider id at Core start (the Provider id row, #169), a supervisor error, a session that died. Every sentence gets one clean pass: a whitespace run becomes one space, and a control character or a byte that is not UTF-8 becomes `?`. The `:invalid_file` text can be an exception message of many lines, and the clean pass puts it on one line. The task reads the sessions directory from the `:sessions_dir` application env key of `:coding_agent`, so that a test uses its own directory. The default stays `~/.helyx/sessions`.
