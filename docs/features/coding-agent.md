# Coding agent (checkpoint one)

A terminal coding agent built on Helyx. It is the first product and it proves the substrate.

## Goal

From the TUI, prompt the agent about a repository. It reads, edits, and runs shell commands in a loop. Output streams. Abort, steer, and follow-up work during a turn. The session resumes after a restart. One user: the author, on this repository.

## Shape

- Root `helyx` Mix project. All bundled plugins live in one Mix project, `plugins/bundled` (app `helyx_plugins`), and the product lives in `apps/coding_agent`. Both depend on Helyx by path, and the product depends on `helyx_plugins`, which depends on `ex_ratatui` (ADR 0005). No umbrella.
- Elixir 1.19 and OTP 28, pinned in `.tool-versions`. Started with a Mix task.

## Runtime

- Core starts as a child spec that takes the plugin list (`Helyx.Core.child_spec/1`). Each session process runs under Core's DynamicSupervisor and is found by id through Core's Registry.
- Each session has one hands process (`Helyx.Session.Hands`, ADR 0003). It runs each Helyx tool call and the provider process as Tasks.
- Each session has one provider process (`Helyx.Session.ProviderProcess`), a Task of the hands. Its protocol is in `docs/features/one-provider-path.md`.
- `Helyx.Session.Server.TurnLoop` owns the turn lifecycle in the session process: the turn states, the turn end, abort, steer, and the queues. The contract is in `docs/features/session-lifecycle.md`. The harness programs are in `docs/features/long-lived-harness.md`.

## Ownership

When anything above a command dies, the command stops (ADR 0004). Inside the VM, work is linked to its owner, and the owner traps exits. At the OS boundary, the perl watchdog ties the life of a command to its port. perl is required: without it the bash tool's `check/0` fails the session start or resume, and `Helyx.HarnessIO.find/1` fails the `init/3` of a harness provider. Core needs perl too when `:sessions_dir` is given: the writer lock of the session file (#579, `docs/features/session-lock.md`). Recorded risk: a future macOS may ship without perl; the watchdog is small enough to rewrite in sh with job control if that happens. The provider process and the prepare Task are in the Ownership table of `docs/features/session-lifecycle.md`, and the harness programs in that of `docs/features/long-lived-harness.md`.

| Resource | Created by | Held by | Released on normal end | Released when the holder crashes | Released on abort |
| -------- | ---------- | ------- | ---------------------- | -------------------------------- | ----------------- |
| tool Task | hands | hands, linked | the result goes to the session | the link ends it with the hands | the cleanup request of the hands kills it (`Helyx.Session.Hands.request_cancel/2`) |
| command port | `Helyx.Watchdog.start/4`, in the tool Task | the Task, linked | closes when the watchdog exits | closes when the Task dies | closes when the Task is killed |
| command process group | the watchdog's fork, held with the hands as `{:command, group}` before it runs | hands (the handle) and watchdog (the life) | `release/3` with `:deliver` | the closed port ends the watchdog's stdin: TERM, grace, KILL, reap | `release/3` with `:cancel` |
| watchdog process | `Port.open` in `Helyx.Watchdog.start/4`; `{:watchdog, os_pid}` is held with the hands | the port | exits after it reaps the command | the closed port is its signal | after the command groups, the release waits for it, then KILLs it |
| the `:default` log handler on `tui.log` | `CodingAgent.log_to_file/2`, before the TUI starts | the VM | the earlier handler comes back when the TUI ends | an `after` puts the earlier handler back when the TUI raises or exits; a kill of the process of `CodingAgent.run/1` leaves the file handler until the VM ends | not changed by an abort |

## Transcript and events

- Message shape and session file format: see ADR 0001 and the section below.
- Session files live under `~/.helyx/sessions/<project>/<session>.jsonl`.
- Events: see `Helyx.Event`.

### Session file

One JSON object per line. Every entry has `id`, `parent_id`, `ts`, and `type`. The first entry is the header and its `parent_id` is null. Example entries, one per kind:

```json
{"id":"01J...","parent_id":null,"ts":"2026-09-17T10:00:00Z","type":"session","version":1,"cwd":"/path/to/repo","model":"opencode-go/kimi-k2"}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"message","role":"user","content":[{"type":"text","text":"List the tests."}]}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"message","role":"assistant","model":"opencode-go/kimi-k2","stop_reason":"tool_use","usage":{"input":120,"output":40},"content":[{"type":"text","text":"Listing."},{"type":"tool_call","id":"call_1","name":"bash","arguments":{"command":"ls test"}}]}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"message","role":"tool_result","tool_call_id":"call_1","tool_name":"bash","is_error":false,"content":[{"type":"text","text":"core_test.exs"}]}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"model_change","model":"claude-code/opus"}
{"id":"01J...","parent_id":"01J...","ts":"...","type":"harness_session","provider":"claude-code","harness_session_id":"..."}
```

Content blocks: `text` has `text`. `thinking` has `thinking`. `tool_call` has `id`, `name`, and `arguments`. A block of another type, or a `thinking` block with a `signature`, makes the file invalid (#634). So does a message with more blocks than the live path allows (#673, the bounds row "content blocks of one message in the session file").

Rules:

- The header carries `version`. A reader rejects a version it does not know (`check_version/1` in `Helyx.Session.File`).
- The header of a child session that the agent tool started has `"parent": {"session_id": "...", "call_id": "..."}`, the parent session and its call. The list and the newest-session resume leave such a file out; `--session <id>` opens it (`docs/features/agent-tool.md`). The format keeps version 1: an older reader lists a child as a session and loses nothing.
- `Helyx.Message.stop_reasons/0` owns the closed `stop_reason` set, and the format encodes it: `end_turn`, `tool_use`, `max_tokens`, `refused`, `aborted`, `error`. `refused` is an answer that the provider filtered or the model refused (#539); `docs/research/stop-reasons.md` has the wire values that map to it. A reader decodes them without touching the atom table's history, so a fresh VM resumes a saved file. A terminal event with a stop reason outside the set, or a usage the file cannot encode, fails the turn as a malformed stream event before the message exists (`Helyx.Session.Stream.check/1`). A stop reason that an older reader must not lose is a format change. The format keeps version 1 for `aborted` and `error` (#432) and for `refused` (#539): an older reader reads them as no stop reason, and the message keeps its content.
- A tool result links to its call by `tool_call_id`. A tool call with no result after the turn ended gets an error result on read, never on write (#269). Its text says that the session stopped while the call ran, that the call may have run, and that the model must check before it repeats it (#584, `docs/features/interrupted-calls.md`); a user abort writes `aborted` and keeps it. A tool result that answers no open call at its place (no call with its id, a second result for one call, or a result after a later message) is dropped on read, and the file keeps it (#417). User story: I resume a session that stopped in the middle of a tool call. The model gets valid call and result pairs. Nothing is written to the file until I do something. The resume reads the chain. For each call with no result among the tool results right after its message, it inserts one interrupted result after those results (`Helyx.Session.Transcript.repair/1`). The file keeps the open call, and the next turn appends after it. So every resume inserts the same results at the same place. A file that already has its results (`aborted` results written before #269) resumes unchanged. The provider request, the Claude Code replay, and the snapshot all read this one transcript. A harness session label counts the assistant messages before it (#511). The repair inserts and drops only tool results, so that count is the same in the file, in the repaired transcript, and in the live session, and the resume changes no count. The resume still appends a newline when the last line has none (#266), because the next entry must start on a line of its own. It writes no entry.
- Streamed partial messages are not written. Only a closed message is appended; the close at a turn end is in `docs/features/session-lifecycle.md`, section "Turn end".
- The file is one chain (#629, ADR 0001). The writer sets the `parent_id` of each entry to the id of the entry before it. The writer lock (#579) makes one writer for each file, and a session that loses its lock stops saving once it handles the exit of the lock port (`docs/features/session-lock.md`, decision 5). Accepted: a client call that is in the mailbox before that exit runs first, and its write can still append after the port closed. From #266 to #629 the file was a tree with one branch for each writer; the update of 2026-10-16 in ADR 0001 gives the reasons for the change.
- **One write per entry.** Each entry and its newline go to the file in one append write. `File.write/3` makes one binary of them (`file:write_file/3`), opens the file with `append` (`O_APPEND`), and writes the binary with one `writev` (`prim_file:write/2`, OTP 28). POSIX `write()`: with `O_APPEND`, no other change of the file comes between the move of the offset to the end and the write. On a local filesystem the entries of two writers thus do not interleave. A short write (a full disk, a signal) makes `prim_file` write the rest with a second `writev`, which another writer can come between: the line is then torn, and the rule below skips it. A network filesystem is out of scope: `open(2)` on Linux states that `O_APPEND` can corrupt a file on NFS when more than one process appends at once.
- **The sessions folder.** A session start creates the sessions folder with mode 0700, and leaves the mode of a folder that exists (#683, bounds row "sessions folder mode").
- **Durability.** The session file survives a crash of the process or of the VM, not a power loss: Helyx does not call fsync, so an append is in the file once the OS has it, and not yet on the disk. A crash can leave a torn last line (the rules below) and tool calls with no result, which a resume reads as interrupted (#584).
- **Read as one chain.** The file is read line by line (`Helyx.Session.File.Reader`). A line that does not decode to a JSON object with a `type` is skipped wherever it is: a torn write. The first entry is the header, with a string `id` and `model`, a known version, and the `cwd` of the resume; its own `parent_id` is not read. Each later entry must have a string `id` and, as its `parent_id`, the id of the entry before it. An entry that breaks the chain fails the resume with `{:invalid_file, text}`, where the text names its line; the line number counts the skipped lines too, so it is the line in an editor. The resume writes nothing then. This is the stated larger failure: an entry that breaks the chain comes from a hand edit or a second writer, and the reader cannot tell which entries after it are good. A file of a tree that two writers made from #266 to #629 is rejected in the same way, at the first entry of the second branch. The model is the last model change, and the harness session labels and the assistant message counts before them come from the chain.
- **Repair never truncates.** Nothing is ever removed from the file. When a resume finds that the file does not end in a newline, it appends one before the session appends anything. A whole last entry is kept that way; a torn one stays a line of its own that every read skips, and the next entry starts on a new line and continues the chain of the last whole entry. A skip sends no signal to the log or the clients.
- A file written before #266 is one chain, because its one writer set each `parent_id` to the entry before it, so it resumes with the same transcript.
- A reader never raises at the caller. A header with an unknown or missing version, and an entry with a shape the writer never produces, come back as `{:error, reason}`. An optional value is the exception: it is not needed to resume, so a bad one does not lose the chat. On a message, a `usage` that is not a map reads as `%{}`, and a `model` that is not a string or a `stop_reason` outside the set of `Helyx.Message.stop_reasons/0` reads as nil, as a missing one does. The role, the content, `tool_call_id`, `tool_name`, and `is_error` keep their checks. A bad harness session label is dropped (see the resume id row). A line that does not decode is skipped (see above). A repair that cannot write, and a sessions directory that cannot be written on create, are their own error classes.
- Provider deltas that are not valid UTF-8, and tool calls whose fields the file cannot encode, fail the turn as malformed stream events (`Helyx.Session.Stream.check/1`); prompts that are not valid UTF-8 or are over 4 MiB are rejected at the client (`Helyx.Session.Input.text/1`). Transcript text is valid, and every value in it survives the round trip to the file, from the moment it exists.
- Tool output is repaired to valid UTF-8 at its two boundaries, before it enters the transcript (row "tool result text validity"). So every consumer of the transcript, the file, the providers, and the TUI, sees valid text.
- A write failure mid-session logs a warning, sends one `:notice` event with a fixed text (#262), turns persistence off for that session, and the turn continues on the in-memory transcript. The notice carries the id of the running turn, or none between turns. Persistence stays off, so the notice goes out once per session. The loss of the writer lock takes the same path with its own notice text (`docs/features/session-lock.md`, decision 5), and the snapshot field `persisting` is false after either. A resume writes no entry (#269), so no write can fail before a client subscribes.

A `Session.start` that fails after the file is created (a supervisor or hands failure) can leave a header-only session that a later resume restores as an empty transcript with the right model. Open, accepted for checkpoint one.

A session file has a writer lock (#579, `docs/features/session-lock.md`): a second open of a session fails while one process holds it. Two writers on one file remain possible only through two sessions folders that share it (a hard link). The second writer breaks the chain, and a later resume rejects the file with `{:invalid_file, text}` (#629, rules above). Branches are out of scope.

## TUI

- ex_ratatui, alternate screen. The TUI is `Helyx.TUI` in `plugins/bundled/clients/tui` (ADR 0005). `Helyx.TUI` owns the terminal loop and the key dispatch. `Helyx.TUI.Composer` owns the composer and its paste markers, `Helyx.TUI.Transcript` owns the transcript rows and the scroll position rule, and `Helyx.TUI.Selection` owns the mouse: the wheel, the selection, and its copy. `Helyx.TUI.Wrap` (the width rule), `Helyx.TUI.Markdown` (the rows of a reply), and `Helyx.TUI.ViewModel` are pure. `Helyx.TUI` implements no Core interface and is not in Core's plugin list: it is a client that subscribes to one session. Local delivery is OTP messages from `Helyx.Session.subscribe/1`; with #662 the TUI attaches to the server over the wire of ADR 0008, and Core gets no Transport interface.
- The view model is a pure fold over events, `Helyx.TUI.ViewModel`, tested with scripted event lists. It grows with the conversation, bounded by the session. A tool result attaches to the oldest open tool cell with the same `tool_call_id`, wherever the cell is (#83). The first result answers the first of two calls with one id, as in the session. A notice can arrive while the tool runs. The session runs the calls of concurrent tools together (`docs/features/concurrent-tool-calls.md`). The fold does not depend on the order of the results. The fold ignores the `:message_start` of a user message on purpose. The composer is human input; its size is accepted as unbounded, like a queue entry's text (#29). A tool result has two forms. The short form, which the TUI shows from its mount, shows at most four content lines and a truncation line with the hidden line count and the key Ctrl+O. Ctrl+O shows the full form, all lines of every tool result, until the next Ctrl+O (`docs/features/tui-tool-output-toggle.md`, #666). Transcript lines wrap by terminal display width, not by grapheme count; the bounds table has the bound, and `Helyx.TUI.Wrap` has the rule.
- The TUI mounts from the snapshot that `Helyx.Session.subscribe/1` returns, so a resumed session shows its history and a late client shows the running turn. `mix helyx --resume` passes `resumed: true` to `Helyx.TUI.run/1`, and an information cell "resumed session" follows the history. The transcript has two kinds of client cell (#467): a notice, drawn red as `✕ <text>`, for an abort, a failed turn, an unconfirmed steer, a lost provider session, a session notice, or a rejected command; and an information cell, drawn dim as `· <text>`, for the resume and a model change. An assistant message that stopped at the token limit or was refused is followed, after its tool cells, by a stop line drawn as a notice: `the answer stopped at the token limit`, or `the answer stopped: the provider refused or filtered it` (#539). It is not a client cell: the fold makes it from the stop reason of the message, so a snapshot and a late client show it too. In two cases a stop reason that arrives while a steer waits is lost, and that answer shows no stop line (`docs/features/session-lifecycle.md`, "Current limits"). A run of information lines joins into one cell and one dim row, so no empty row stands between them; the run is one item of the scroll position (#483, #667). Error notices keep one row each. The model cell joins the cells when the `model_change` event arrives, so a switch during a turn shows it above the reply that the old model still writes. Accepted: the view model stays a fold over events, as a notice does. The design is in `docs/features/session-snapshot.md` (#163).
- The layout (#483): the transcript, the composer, and the footer have an empty margin of 2 columns on the left and on the right. A transcript row breaks at a space (`Helyx.TUI.Wrap`), so a word and the quote after it stay together. An empty row follows each item. A user message has a blue bar `▌` and a white-on-black tint on every row, filled with spaces to the edge; a row that holds one glyph wider than the text width has no bar. The composer box has rounded corners in dark gray, no title, and a blue `›` mark on its top row, drawn only when the box is at least 4 columns wide and 3 rows high; the follow view ends with the empty row of the last item, so one empty row stands above the box. All colors are palette colors, so the layout follows the terminal theme; white on black reads in light and dark themes alike.
- The text of an assistant message renders as Markdown (#487), by `Helyx.TUI.Markdown`; user messages, thinking, and tool output stay plain text. A heading is bold without its leading signs; a closing run of `#` stays. A bullet item gets `•`, and a numbered item keeps its number; the rows of an item hang under its text. Bold, italic, inline code, and fenced code lose their signs; code is yellow, and a fenced line is indented by 2 columns. A link shows its text underlined and its address after it in parentheses, or once when the text is the address. A backslash escapes a sign, but not inside a code span; before a run of backticks it makes the whole run text. A sign with no partner stays text, and a line break is a row, as before. Each grapheme has one style, because ExRatatui drops a mark that starts a span. A fence that has no closing line shows as plain text from its opening line to the end, so a code block in stream shows as code when its closing fence arrives. `ExRatatui.Widgets.Markdown` is not used: it draws into an area with its own wrap and gives the transcript no rows to count, so the scroll position and the width rule could not hold. The text of each row is the text of a row of `Helyx.TUI.Wrap.line_slices/2` on the sanitized text, and a row that does not fit with its bullet, number, or code indent has none, so the width and scrollback bounds stay as they are. A line costs time linear in its length (code spans and emphasis pair with one pass each), but more than the wrap alone: measured on 2026-10-04, a reply of 5,000 lines with bold, code, and links at 76 columns takes about 300 ms against 110 ms for the wrap, and 5,000 lines with no sign take 13 ms against 1 ms. The rows are not cached, as before, so a frame parses each item it shows. Accepted: no syntax colors; no block quotes, tables, or rules (`* * *` shows as a bullet); emphasis does not cross a line; a link text shows as it is written, and a link text with a code span is no link; an unclosed fence is plain text also in a finished reply.
- PgUp and PgDn scroll the transcript by one screen (#39). While the view is scrolled, new output does not move it, and row 2 of the footer says `scrolled`. With an empty composer, Home goes to the first row of the oldest item, held by `Transcript.hold/4`, so a transcript that fits the screen stays in the follow view; End, a PgDn at the end, or a sent prompt returns the view to the newest output. With text in the composer, Home and End move its cursor. There is no Ctrl+End: on a MacBook, macOS takes fn+Ctrl+Right for window tiling (#484). The position is client state of the TUI process. It is not in the view model, because it depends on the terminal size, and the fold knows no terminal. The bounds table has the cost bound. Ctrl+F finds text in the loaded transcript; the rules and the bounds are in `docs/features/tui-search.md` (#668).
- The TUI turns on mouse capture (#485), and ExRatatui turns it off with the raw mode on every exit. A wheel or trackpad step scrolls the transcript by three rows, by the rule of PgUp and PgDn; a step that does not move the view draws no frame. Mouse capture stops the selection of the terminal, so the TUI has its own: a left press in the transcript starts it, a drag moves its end, and the selected cells show in reverse video until the next left press. The ends are a transcript address and a column, so a wheel step during the drag keeps the selected text and the drag can reach into the scrollback. A drag past an edge of the transcript selects to that edge. A press outside the transcript, a click with no drag, a new size, or Ctrl+O (`docs/features/tui-tool-output-toggle.md`) selects nothing. A mouse event that changes nothing draws no frame. The release copies the text with OSC 52, written to standard output in the event handler, between two frames: one line for each row, with no bar and no space at the end, so a wrapped line copies as several lines. A frame that the terminal draws at the same moment can show broken cells until the next frame. A mouse event neither arms nor disarms the quit of Ctrl+C. Accepted: a cell that changes its rows under a selection changes the selected text, as the scroll position does; and the copy counts columns by the width rule of `Helyx.TUI.Wrap`, not by the cells ExRatatui draws (ticket #90), so where the two differ the copied text differs from the highlighted cells: after an emoji sequence or a zero-width code point that the rule does not list, such as U+2060, the columns move, and a glyph wider than the whole transcript, which ExRatatui does not draw, is copied. Selection inside the composer is out of scope.
- Escape aborts. The steers and follow-ups that the abort or a failed turn takes off the queue come back to the composer (`queue_dropped`); the rule is in `docs/features/multiline-composer.md`. Enter sends a steer during a turn and a prompt when idle. Alt plus Enter queues a follow-up: most terminals cannot tell Shift+Enter from Enter without the kitty keyboard protocol, so Alt is the modifier. Ctrl+J adds a new line; the composer and the paste rules are in `docs/features/multiline-composer.md` (#44). Up on the first row and Down on the last row recall earlier prompts; the rules are in the same doc (#469). The footer (#484) has two dim rows and no key hints, except the Ctrl+C hint below (#486); the keys are in `apps/coding_agent/README.md`. Row 1 is the working directory, with the home directory as `~`, and the git branch in parentheses. The TUI gets the directory from the `:cwd` option of `Helyx.TUI.run/1`, which `CodingAgent` sets to the session directory, because the snapshot has no cwd. It asks git for the branch with `git branch --show-current`, in a task, so git decides what the branch is and a slow git does not hold a frame. git runs on the machine of the TUI, which is the machine of the session in local mode. A branch change between turns shows after the next turn ends. Row 2 is the model, the run state, the usage values of the session, `queued <steers>+<follow-ups>` only when a count is not zero, `<n> running`, `<n> held`, and `<n> waiting` for the background runs and their ends (`Helyx.Session.Queue`, `counts/1`), each only when it is not zero (#695), and `scrolled` while the view is scrolled; the hint `Ctrl+C again to quit` comes before them while it shows. The usage values (#558) are `in <n> out <n>`, `cache <p>%`, the cost (`$1.23`, `≥$1.23`, `$?`, or no field, with `list` after a sum when any cost in it is a list price), and the context %, yellow over 70 and red over 90. The tokens, the cache share, and the cost are session totals over every assistant message of the transcript, live and after a resume; the context % is the estimate from the last usage with `context_tokens`. Each value has a bound; the rules and the bounds are in `docs/features/usage-and-limits.md`, "The footer" and "Bounds". While a turn runs, the run state is an animated braille spinner and the whole seconds since the turn started, in place of a static word, so a slow model looks different from a stuck one (#468). A tick every 100 ms draws the next frame. The timer is an `ExRatatui.Subscription.interval/3` that `Helyx.TUI.subscriptions/1` declares while a turn runs. ExRatatui keeps one timer per subscription id, cancels it when the list drops it, and drops a tick of a cancelled timer. So `turn_start` starts the one timer, `turn_end` stops it, and no timer runs while idle. Each tick renders the whole frame, the transcript included; the transcript widget wraps only the cells on the screen. A client that sees the `turn_start` event starts the time there. A client that joins a running turn takes the start from the snapshot: the session gives the time since the turn started as `elapsed_ms` in the snapshot `turn`, and the mount sets the start to that many milliseconds before now. So every client shows the time since the turn started, not since its own mount; a delay of the snapshot on its way to the client is not counted. When the client rejects input, row 2 of the footer also shows the reason in red, as `✕ <reason> ` at the start of the row: `not sent: the queue is full`, `not sent: over 4 MiB`, or `not sent: the session ended` for a steer or a follow-up, and `not copied: over 75 KB` for a copy over the bound. The rejected text stays in the composer. The reason is the `reason` field of the view model. It is client-local, like a notice: `ViewModel.reject/2` sets it, and no event changes it. Each reason is a fixed text of the TUI, so it holds no input and its longest text is 27 bytes. The reason comes first because the row does not wrap and a model ref can be 256 bytes; the reason is at most 30 columns with its mark, so it shows in full at a terminal of 34 columns or more, with the margins. The next key press, paste, or mouse press of any button clears the reason before the TUI handles that input, so the same input can set a new reason. A new reject replaces the reason, also when it comes from a key repeat, because the newest reject is the one the user must see. The release and the repeat of a key do not clear it, because those of the rejected Enter come immediately after the reject. There is no terminal bell. A rejected `/model` switch stays a notice cell, because its text must stay visible while the user corrects the ref.
- Ctrl+C does not quit at once (#486). The first Ctrl+C press clears the composer. When the composer is already empty, with no draft that Down brings back, row 2 of the footer shows the hint `Ctrl+C again to quit` instead, after the reason of a rejected input. A second Ctrl+C press within 500 ms quits and restores the terminal. Any other key press, or a paste, between the two disarms the quit, and so does the end of the window. The release and the repeat of a key do not disarm it. `Helyx.TUI.Quit` holds the armed state and decides each answer; `Helyx.TUI` has one clause that hands it the key. The window is a timer message with the ref of its arm, so the end of an earlier window does not disarm a later arm. A timer that arrives late under load makes the window longer than 500 ms, never shorter. Esc stays the abort key.
- `/model provider/model` in the composer switches the model through `Session.set_model/2`, idle or during a turn. `/compact [instructions]` is the other session command (`docs/features/harness-compaction.md`). The rule is on bytes, not on looks: a line that starts with `/model`, `/compact`, `/new`, `/resume`, or `/help`, after whitespace, is never sent as a message, and any other text is a message. The footer changes, and an information cell `model: <ref>` joins the transcript, when the `model_change` event arrives, not when the call returns, so the view model stays a fold over events and a switch from any client shows. The ref is checked by `Helyx.ModelRef` (at most 256 bytes, no control characters), and the cell is drawn through `Helyx.TUI.Wrap` as every cell is. A rejected switch adds a notice cell (`ViewModel.notice/2`, client-local like the composer) and keeps the text in the composer. `/new` and `/resume` switch the session of the TUI (`docs/features/tui-session-switch.md`, #551). `/help` (#696) adds one information cell (`ViewModel.info/2`, dim, client-local) that lists the usage of each slash command on one line, then the keys, one line each, and clears the composer; no turn starts and nothing goes to the session. `/help` with an argument, as `/new` with one, shows its usage. The command names and their usage are one list in `Helyx.TUI.Command`, which `parse/1` and `/help` both read. The keys are one module attribute, `@keys` in `Helyx.TUI`, the module of the key dispatch, which its moduledoc and `/help` both show. The attribute comes before the moduledoc, which reads it. The help is fixed text of the TUI with no input, drawn through `Helyx.TUI.Wrap` as every cell is.
- The log does not draw on the terminal of the TUI. A log line on the terminal writes over the screen, and stderr is the same terminal in the usual setup. So while the TUI runs, `CodingAgent` replaces the `:default` log handler with a file handler that writes to `tui.log` in the sessions directory (`~/.helyx/sessions/tui.log`), and puts the earlier handler back when the TUI ends, also when it raises. The log keeps every diagnostic line, such as a tool crash with its stack frames. The lines from before the TUI starts and after it ends go to the terminal as before. Print mode sends its log to stderr (`docs/features/print-mode.md`).
- The command line is `CodingAgent.CLI.main/1`, which the `helyx` release (`docs/features/local-release.md`, #506) and the `helyx` Mix task in `apps/coding_agent` call. `helyx [directory] [--model provider/model] [--resume]` starts Core with the bundled plugins, one session in `directory` (default: the current one), and the TUI, and quitting restores the terminal. `helyx --help` prints the usage, the switches, and the exit statuses, and starts nothing (`docs/features/local-release.md`). The session is written under `~/.helyx/sessions`; `--resume` continues the most recent session for the directory with its saved model, so it does not combine with `--model`. The scan for that session reads only the 256 files with the newest modification time in the project directory, and an append sets that time. A session older than those files is not found, and the command line prints the `:not_found` sentence, `no saved session for this directory; start one without --resume`, although the file exists. The scan skips a file whose header this build does not read, such as a newer version, so a folder whose only session has such a header gets the same sentence (#585). A start or a resume that fails prints one line on stderr, `helyx: could not start the agent: <sentence>`, and the exit status is 1. A session that ends while the TUI runs ends the TUI with `{:session_down, reason}` (`Helyx.TUI.run/1`), and the line is `helyx: the session stopped`, or `helyx: the session crashed and stopped` when `Helyx.Session.end_reason/1` gives `:crashed`; the exit status is 1. `CodingAgent.error_text/1` is the one place that makes the line after `helyx: `, the prefix included. It has a clause for each shape of `Helyx.Session.File.error/0`, for the model ref and provider errors, for `{:tool_unavailable, name, reason}`, and for `{:terminal_init_failed, text}`. The `:too_large` text prints as it is. An invalid model ref stays out of the sentence, as in the TUI notice. A value from the file (`:unknown_version`, the type of a bad entry, a provider id) prints through `inspect/1` with its default limits, so a JSON object shows as a map. A bare atom prints as its POSIX text when it is a POSIX code. An error with no clause prints through `Helyx.Reason.text/1`, so it can show as a tuple with no stacktrace: a duplicate tool name, a bad tool spec (`{:bad_tool_spec, label}`, #142), a bad or a shared provider id at Core start (the Provider id row, #169), a supervisor error. A bare string reason shows with no quotes. Every sentence gets one clean pass: a whitespace run becomes one space, and a control character or a byte that is not UTF-8 becomes `?`. The `:invalid_file` text can be an exception message of many lines, and the clean pass puts it on one line. After the clean pass, the whole line has at most 4000 bytes of valid UTF-8, the prefix included, so plugin text such as the reason of a tool check and a value from the file have the bound too; a character cut in half is dropped. `CodingAgent.CLI` reads the sessions directory from the `:sessions_dir` application env key of `:coding_agent`, so that a test uses its own directory. The default stays `~/.helyx/sessions`.

## Out of scope

MCP, sub-agents, permission prompts, plan mode, todos, branching, editing queued messages, queue persistence, remote hands, packaging, Anthropic API key provider, dedicated grep, find, and ls tools, skills discovery.
