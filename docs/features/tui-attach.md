# TUI attach

Ticket #662. Decisions of the orchestrator, 2026-10-19 (owner away), in the comments of the ticket.

## Goal

The TUI becomes a wire client. `helyx` attaches to the server of its data folder, or starts one in the background, as tmux does. Quitting the TUI leaves the sessions running. This is the end state of ADR 0008: one long-running server owns the sessions, and every client is on one wire contract (`docs/features/wire-protocol.md`). The server is `helyx serve` (`docs/features/serve.md`).

User stories:

- A user quits the TUI during a long turn, opens it again, and sees the turn still running.
- A user who never ran `helyx serve` types `helyx`, and it works as today.

Decisions:

1. **Find the server.** The client finds the server of its data folder by `<data folder>/server.json`, while the lock `<data folder>/server.lock` is held (serve.md, decision 8). It refuses a data folder that its group or other users can write, with the line of `helyx serve`: such a user could write a server file that sends the prompts of the user to another server. A data folder that is not there is no server. A path that is not a directory gives `helyx: the data folder <dir> is not a directory`, and a failed stat `helyx: could not read the data folder <dir>: <reason>`. The client tests the lock with a non-blocking take (`Helyx.Session.Lock.take/1` on `<data folder>/server`). When it gets the lock, no server runs: it releases the lock at once and takes the folder as no server. It never removes the file: the next `helyx serve` replaces it. The take runs in a Task of its own, which traps exits as `Lock.take/1` needs and ends after the take, so no message of the port stays in the mailbox of the caller.
2. **Read the file as `helyx serve` reads it.** The client and a second start read the file with one function, `CodingAgent.Serve.read_file/1`: a regular file, at most 4,096 bytes, a JSON object with `address` a parsed IP address and `port` an integer from 1 to 65535. The client also needs `token`, a string. A file that fails a check is no valid file.
3. **The server is starting.** With the lock held, a missing or invalid file, a file with no string token, a refused TCP connection, any other failure up to the `101` reply of the upgrade, a close of the server before `welcome` (such as `4401`, a refused proof, or a close inside a frame), and the timeout of the connect mean that the server is starting: from the `flock` of a new server to its remove of the stale file, the file can name a dead server, and its port can be in use by another program. A second `helyx serve` names an address by the same proof (serve.md, decision 5; #777). The client tests the lock, reads the file, and connects again every 100 ms, as a second `helyx serve` does, and starts no attempt after 5,000 ms (`CodingAgent.Serve.wait_ms/0`). Then it shows one line, `helyx: could not attach to the server of <dir> in 5000 ms: <reason>`, with the reason of the last attempt, and exits 1. A lock that is free at a later attempt is no server. The comment of the orchestrator names the refused connection and the refused proof; the other failures before `welcome` join them, so one rule covers every failure that a server in its start or its stop can give.
4. **The handshake.** The client connects over TCP to the address of the file, sends the upgrade, checks `101` and `Sec-WebSocket-Accept` (RFC 6455), waits for `challenge`, sends `hello` with its protocol number (`Helyx.Transport.WebSocket.protocol/0`) and the proof of the token (wire-protocol.md, O1), and waits for `welcome`. The token is the secret of the server: it stays in a closure, and no error, line, or crash report holds it.
5. **Refused.** On `refused` the client shows `helyx: the server speaks protocol <server_protocol>, this client speaks <n>; install the same build` and exits 1. It does not retry and starts no second server: the lock of the data folder is held, so a second `helyx serve` exits 1 anyway. `server_protocol` is checked as a JSON integer of 0 or more before it reaches the line.
6. **A contract break.** After a valid `101` reply, any frame or value that the handshake does not allow is a contract break: a text that is not JSON or is over the decode bounds of the transport, a frame over the frame bound, a masked frame, a reserved bit, a binary frame, a control frame that is fragmented (FIN 0) or over 125 bytes, a continuation with no start, a `part`, a frame type that the handshake does not expect or a missing key, a nonce that is not the base64 of 32 bytes, a `welcome` of another protocol number, and a `refused` whose `server_protocol` is not an integer of 0 or more. It gets one generic line, `helyx: could not attach to the server at ws://<address>:<port>: the server broke the wire contract`, at once, with no retry. A real server of this build sends none of these. A ping or a pong is skipped, also between the fragments of a text.
7. **The TUI over the wire** (slices 2 and 3). The TUI keeps its pure fold `Helyx.TUI.ViewModel`. A connection process owns the socket, decodes each frame with the codec of the transport (`Helyx.Transport.WebSocket.Frame`), turns each wire event into the Core event that the fold takes (the message shape is the message entry of the session file, `Helyx.Session.File.Codec`), and acks it. The operations of the TUI become requests: `steer`, `follow_up`, `abort`, `set_model`, `compact`, `answer`, `start`, `resume`, `sessions.saved`. The TUI subscribes with `answers: true`.
8. **Quit leaves the sessions running** (slice 3). Over the wire, a quit closes the connection and sends no `abort`: the session runs on in the server.
9. **The log** (slice 3). The TUI writes its log to `<data folder>/tui.log` (`CodingAgent.log_to_file/2`); a server that the client starts writes its output to `<data folder>/server.log`. The two run in two OS processes, so their logs do not mix. The process-global handler change of `log_to_file/2` then holds only the client.
10. **Auto-start** (slice 4). With no server, `helyx` starts `helyx serve` in the background through the launcher: a new process group, stdin on `/dev/null`, stdout and stderr to `server.log`. Then it waits for the server as decision 3 does. Two clients that start a server at the same moment start two `helyx serve`; the lock keeps one, and both clients attach to it. A second start then tries the lock again at each poll, so the short lock take of a client test (decision 1) does not end a start. With no launcher (`mix helyx`), slice 4 decides.
11. **Reconnect** (slice 4). The TUI records the `instance_id` and the `seq` of the last event that it applied. After a lost connection, it connects again and subscribes with `after`; the replay ring gives the events it missed, or a new tail snapshot replaces its state (wire-protocol.md, "Join, pages, and replay"). The rule of the TUI that it has no seq guard changes: the fold applies an event only once, by its `seq`.
12. **The in-node path goes** (slice 5). The TUI uses only the wire; `CodingAgent.run/1` keeps print mode.
13. **The client bounds** (#814, decision of the orchestrator in the ticket). After `welcome`, the client reads each server frame with the decode bounds of an outbound frame (`Helyx.Transport.WebSocket.Frame.decode/3` with `:outbound`). They derive from the bounds of what the server sends, not from the inbound bounds of a client frame:
    - **Bytes.** 1,611,661,312 bytes of a frame joined from parts. The largest frame is a `queue_dropped` of 64 texts of 4,194,304 bytes in their worst JSON form, six bytes for each byte (`\u0001`): 1,610,612,736 bytes, and 1,048,576 bytes for the other fields (64 origin ids of 256 bytes are 98,304 bytes in that form). The next largest is a snapshot: a live newest group of 8 MiB and 1,024 tool results of 64 KiB, and a partial of 8 MiB, at most 481 MiB in that form; a newest group read from the file is at most the 64 MiB of the file.
    - **Values.** 38,797,312 values (2^25 + 2^22 + 2^20). The most values are in a tail snapshot whose messages are the newest group alone, read from the file: the file reader bounds a message only by its 1,024 blocks and the 64 MiB of the file (`Helyx.Session.File`, `Codec.decode/1`), not by the 8 MiB of the live path, and each JSON value after the first takes at least two bytes of the file, as `,0` does. That is 33,554,432 for the messages, and 18,432 for the results that the resume adds to calls with none (`Helyx.Session.Transcript.repair/1`, 1,024 short results of 18 values). A tail that is not the newest group alone has fewer: 16,777,216 (16 MiB of external size, and each JSON value takes at least one byte of it, as `[]` does). Then 4,203,520 for the partial (8 MiB, at least two bytes for each value, and 9 values for each of 1,024 blocks); and 262,216 for 8 asks (one for each running call of `Helyx.Session.ToolQueue`, a request of at most 65,536 bytes of JSON). That is 38,038,600, and the bound leaves 758,712 for the other fields. A frame of 22,020,095 integers took a heap of 606 MiB (below), so a frame at the bound takes about 1 GiB: an estimate by that rate, not measured at the bound.
    - **Integers.** At most 1,024 characters, as inbound: the server sends no integer of more than 100 digits in a tool call or an ask (`Helyx.Session.Stream`, `Helyx.Message.cap_integers/1`, `Helyx.Session.Input.json_object/2`), and its other integers are counts.

    Measured (2026-10-20, OTP 28, Elixir 1.19.5, the dev machine, one probe run with `Helyx.Transport.WebSocket.Wire` and a copy of the decoder of `Frame` with the outbound bounds): a tail of 200 assistant messages of 64 tool calls is 1,383,506 bytes of JSON and 170,603 values, over the inbound bound of 65,536. A `queue_dropped` of 64 plain texts of 4 MiB is 268,458,462 bytes of JSON in 342 parts of 357,960,237 bytes; the server encodes it in 681 ms and the client decodes it in 180 ms, its strings off the heap. One text of 4 MiB of `\u0001` is 25,165,849 bytes of JSON. 100,288 bytes of external size of `[]` hold 100,018 values. A frame of 22,020,095 integers decodes in 1,742 ms with a heap of 606 MiB at its end, a decode with a bound one value lower refuses it after 1,199 ms with 518 MiB, and 4,000,000 nested arrays decode in 733 ms with 117 MiB: the decode of a frame at the bounds takes about the memory of its term in the server.

    The other option of the ticket, a snapshot in pages, is not taken. An event is one frame: a `queue_dropped` or a `message_end` of 8 MiB (48 MiB of JSON) passes any fixed bound of a snapshot page. The client folds the whole snapshot into its state, so pages bound a frame, not the memory of the client. And pages need protocol 4 in the server and in every client. A frame over the outbound bounds is a contract break.
14. **The strict check of wire data** (#814). A wire value is checked against the schema of protocol 3 before it becomes a Core value (`Helyx.TUI.Wire.Decode`): each known field has its type, `content` is a list of at most 1,024 blocks, a usage is a `Helyx.Usage` that `valid?/1` takes, an origin is on a user message only, a stop reason is of the set, an integer in the arguments of a tool call has at most 100 digits, and each text block of a tool result is at most 65,536 bytes. A missing key is null or false, as the codec of wire-protocol.md says: a user message with no `origin` has the origin nil, as Core holds it, for the server leaves out a nil origin. The tolerant decoder of the session file (`Helyx.Session.File.Codec.decode/1`) is never the check of wire data: it reads a bad usage as the unknown usage, a bad stop reason as none, and a content of `{}` as no blocks, so that a file keeps its chat. A server of protocol 3 sends none of these, so on the wire each is a contract break.
15. **The connection reads while it writes** (#821, decisions of the orchestrator in the ticket and on 2026-10-20). The connection process never waits on a write: a writer process (`Helyx.TUI.Wire.Writer`), linked to it, encodes and sends each frame of the connection in order, and the connection reads the frames of the server and gives them to the owner while a frame goes out. The server reads no frame while it writes one (Bandit), so a client that does not read while it writes waits for the server as the server waits for it. Traced (2026-10-20, the dev machine): with the write in the connection process, a steer of 4 MiB of `\u0001` and then a follow-up left both processes in `prim_inet:send/4`, the client with 1,338,500 bytes pending and the server with 345,204, until a send timeout ended the connection with `{:shutdown, {:closed, nil}}`: after 11,110 ms in the trace, and after 31.3 s in the first run of the test of #821, before the fix (the send timeout of the client is 5,000 ms for each WebSocket frame, that of the server 30,000 ms). The rules of the writer:
    - **Its own descriptor.** The writer sends on a `:socket` of the descriptor of the socket (`:inet.getfd/1`), and the connection reads with `gen_tcp`. At a failed send, `gen_tcp` drops the bytes that wait to be read, with both of its backends, and the kernel keeps them (probe of 2026-10-20 on the dev machine, macOS; not probed on Linux: a peer that sends `HELLO` and resets the connection; after a failed send, `gen_tcp` read `{:error, :closed}`, `:socket` read `HELLO`). The descriptor needs a socket of the `inet` backend (`:inet.getfd/1`).
    - **A failed write.** The writer tells the connection and ends. The connection then reads the bytes that the socket holds, at most its receive buffer, with no wait, and ends with `{:shutdown, {:closed, code}}`: the code of a close frame that came before the failure, else nil. A frame among those bytes that the contract does not allow ends it with `{:shutdown, :broken}`. A write past the send timeout is a failed write.
    - **Bounded queue.** At most 16 request frames of the callers wait for the writer: a request holds its place among the 16 until its reply has come and its frame is written, and one more gives `{:error, :busy}`. The `unsubscribe` of a late `subscribe` reply goes to the writer at once, with no check of the 16: a server that replies to a `subscribe` before it reads it can make up to 32 request frames wait (open, see the accepted holes). At most one batch of control frames waits for it; pings and acks that come meanwhile go in the next batch, which holds the latest ping (RFC 6455, section 5.5.3) and the latest seq of each live subscription (the server takes an ack as the highest seq so far).
    - **Its end.** The connection kills the writer at its end (`terminate/2`), and the link ends it at a kill of the connection, so the second descriptor closes with the connection.

## Slices

Each slice is one change of `/ship` size. A later slice is its own ticket, ready for an agent, blocked by the slice before it.

1. **The attach client** (#662). Decisions 1 to 6: `CodingAgent.Attach.connect/1` and `Helyx.TUI.Wire.connect/4`. Nothing calls them yet; `helyx` is not changed.
2. **The wire session of the TUI** (#806). Decision 7: the connection process with requests, replies, the subscription, the acks, the parts, and the pings; the events decoded to Core events. Nothing in the TUI uses it yet.
3. **`helyx` attaches** (#807). When a server runs for the data folder, `helyx` runs the TUI over the wire (decisions 8 and 9). With no server, it runs in the node as today.
4. **Auto-start and reconnect** (#808). Decisions 10 and 11.
5. **The in-node path goes** (#809). Decision 12.

## Interface changes

Slice 1:

- `CodingAgent.Attach.connect/1` (new): `connect(dir)` with the data folder. Returns `{:ok, socket}` with the socket after `welcome`, owned by the caller, `:none` when no server runs, or `{:error, text}` with the line without its `helyx: ` prefix.
- `Helyx.TUI.Wire.connect/4` (new, client code in `plugins/bundled/clients/tui`): `connect(ip, port, token, timeout)` with the token in a closure. Returns `{:ok, socket}` after `welcome`, passive and owned by the caller; `{:error, {:refused, server_protocol}}`; `{:error, :broken}` for a contract break; or `{:error, text}` for the failures of decision 3. It closes the socket on every error.
- `CodingAgent.Serve.read_file/1` and `CodingAgent.Serve.url/2` (new, `@doc false`): the read of the server file of decision 2 and the URL of a parsed address, which a second start used privately. `read_file/1` gives the token in a closure, or nil when the file holds no string token.
- `Helyx.Test.WireClient` gets a fake server for the tests of a client (`fake_server/1` and its steps).

Slice 2:

- `Helyx.TUI.Wire.Connection` (new): `open(socket)` with the socket of `connect/4`, owned by the caller, starts the connection process, which takes the socket; it returns `{:ok, conn, ref}` with the caller's monitor of it. The caller is the owner: the connection ends with it, and it gets `{:helyx_event, event}` for each event of its subscriptions and `{:helyx_end, sub, :stopped | :crashed}` at `session_end`, as a client in the node gets them from `Helyx.Session.subscribe/2`. The connection ends with `{:shutdown, :broken}` at a contract break and with `{:shutdown, {:closed, code}}` at a close of the server, `code` nil for a close with no code: a close of TCP, a close frame with no code, or a failed read or write.
- The operations: `subscribe(conn, session)` with `answers: true`, which gives `{:ok, snapshot, sub}` (a replay answers only a `subscribe` with `after`, which this client sends from slice 4: from slice 3 a replay is a contract break); `ack(conn, sub, event)` for each event that the owner applied, which sends an `ack` for each 1,024th `seq`, as `Helyx.Session.ack/2` does with an event; `start(conn, cwd: cwd)`, with `model:` as an optional key (a nil value is `bad_params`), and `resume(conn, id: id)` or `resume(conn, cwd: cwd)`, which give `{:ok, session_id}`; `list_saved(conn, opts)`, which gives `{:ok, [Scan.Summary.t()], next}` as `Helyx.Sessions.list_saved/2`; and `steer/3`, `follow_up/3`, `compact/3`, `abort/2`, `set_model/3`, and `answer/4`, which give `:ok`. An error of the wire is `{:error, code}` with the code as an atom; `invalid_model_ref`, `unknown_provider`, and `start_failed` give `{:error, {code, text}}`. A request over the frame bound goes as parts (`Helyx.Transport.WebSocket.Frame.encode/1`).
- An event is the `Helyx.Event` of Core: a message is checked and built by `Helyx.TUI.Wire.Decode` (decision 14), a user message of origin `unknown` with the origin `%{kind: :unknown, id: nil}` that Core holds for it. A message has the role that the fold takes for its event: a tool result for `tool_execution_end`, a user message for `queue_dropped` and `steer_unconfirmed`, and an assistant message for the partial of a turn. The arguments of a tool call hold no integer of more than 100 digits, as the server sends them (`Helyx.Message.cap_integers/1`). The two fields that the wire leaves out come back from the messages: `texts` of `queue_dropped` and `text` of `steer_unconfirmed` (`Helyx.Message.text/1`). An event of a type that the client does not know is dropped; a key that it does not know is ignored.
- `Helyx.TUI.Wire.check/4` and `Helyx.TUI.Wire.masked/2` (`send_frame/3` before #821) become public with `@doc false`: the connection checks each frame header with the rule of the handshake, and the writer masks its pongs and texts as the handshake does.

Slice 3 (#807). Decisions of the worker, the owner away, where the ticket does not decide:

- `CodingAgent.CLI`: without `-p`, `helyx` calls `CodingAgent.Attach.connect/1` on the data folder first. `:none` runs in the node as before. `{:ok, socket}` runs `CodingAgent.attach/2`. `{:error, text}` prints `helyx: <text>` (after the clean pass, as every line) and exits 1. Print mode stays in the node (decision 12). The lock test needs perl, so with no perl on the PATH `helyx` prints the lock line before the tool check of a start in the node.
- `CodingAgent.attach/2` (new): opens the connection (`Connection.open/1`), starts or resumes the session over the wire (`start` with `cwd` and the `--model` of the command line, or none, so that the server gives its default model, serve.md decision 1; `resume` with `cwd` for `--resume` or `id` for `--session`), and runs the TUI with the log in `tui.log`. For `--session` it finds the file of the id in the data folder first, as the node does (`Helyx.Session.File.Scan.find/2`), so `not a session id`, `no session`, and the other errors of the find are the lines of the node, and the TUI runs in the folder of the header, where the server resumes the session. The folder is checked before the open, with the checks of the node (UTF-8, no NUL byte, an absolute path to a directory), so no session starts in the server for a folder that the TUI refuses, and a folder that is not UTF-8, which has no JSON form, gets `invalid_cwd`. The session opens before the TUI starts, so its errors are lines on the plain terminal. The quit aborts nothing. The user story: the user opens the running session again with `helyx --resume` or `/resume`; `helyx` alone starts a new session, as in the node.
- `Helyx.TUI.Wire.Connection.take/1` (new): makes the caller the owner. The TUI process starts in `start_link`, after the caller opened the connection, so it takes it at its mount; the connection then ends with the TUI.
- `Helyx.TUI.Wire.Connection.stop/2` (new): the `stop` operation of the wire, which decision 7 does not list. A switch over the wire stops the session that it leaves, as in the node (`docs/features/tui-session-switch.md`): else its subscription stays and its unacked events end the connection with `4408` after 16,384 events. A stop that the wire refuses (`timeout`, `busy`, `closed`, `failed`) fails the switch: the TUI stays on the old session, whose events it acks, with `could not switch: <text>`, and the new session runs on in the server. A `subscribe` reply with a replay is a contract break: this client sends no `after`.
- `Helyx.TUI.Link` (new, `@moduledoc false`): the session of the TUI, a `Helyx.Session` or `%Link{conn, id}`. Every operation of the TUI on its session goes through it: the subscribe, the ack, steer and follow-up, abort, `/model`, `/compact`, the answer of a question, the open and the stop of a switch, and the list of `/resume` (`sessions.saved` with `limit` 256, the scan bound of `Helyx.Session.File.Scan.list/2`). The errors of the wire that Core does not give (`timeout`, `busy`, `closed`, `failed`) have texts of at most 27 bytes, the bound of a reason of the footer (`Link.error_text/1`): a rejected steer or follow-up stays in the composer with the text in the footer, a command or an answer gets it as its notice or reason, a refused abort of Escape as the reason (the abort runs in a Task, which sends the text back), and the `/resume` list shows `could not list the sessions: <text>`. A steer, a follow-up, or a `/compact` text over 4 MiB (`Helyx.Session.max_text_bytes/0`), and a `/model` ref over it, get the answer of Core at the client, `text_too_large` or `invalid_model_ref`, and no request: a frame over the bound of the server closes the connection with `4413`, and 4 MiB of text is at most 24 MiB of JSON, under the 25 MiB of a frame of parts. The id of a `/resume` line gets the clean pass, as the other fields of the line: over the wire it comes from the server.
- `Helyx.TUI`: the `:session` option takes a `%Link{}`. A `session_end` of its sub ends the TUI as the end signal of a session does; the end of the connection ends it with `{:connection_down, reason}`, and a subscribe that the wire refuses too. `CodingAgent.error_text/1` gives the line (`Link.down_text/1`): `the server broke the wire contract`, `the server closed a slow connection` for `4408`, `the server closed the connection`, `could not subscribe to the session: <text>`, or `the connection to the server ended`.

## Replaced mechanism

None in slices 1 and 2. #814 replaces two mechanisms of slice 2: the inbound decode bounds of the transport for a server frame, by the outbound ones (decision 13), and `Helyx.Session.File.Codec.decode/1` for a wire message, by the strict check of `Helyx.TUI.Wire.Decode` (decision 14); the tests of `Codec.decode/1` stay with the session file. #821 replaces the write in the connection process by the writer process, on its own descriptor of the socket (decision 15): the connection stays the one process that gives frames to the writer, so the request frames keep their order and the parts of a frame stay together, and the tests of the order of a pong and an ack and of the 16 waiting requests stay. A request no longer waits for the take while an earlier frame goes out; it waits in the writer, within its deadline. Slice 3 replaces the abort of the session at the quit of the TUI (`Helyx.TUI.terminate/2`, `CodingAgent.run_session/1`) for a TUI over the wire, and the direct calls of `Helyx.Session` in the TUI by `Helyx.TUI.Link`; slice 5 replaces the in-node TUI.

## Accepted holes

- The lock test of a client holds the lock for the few milliseconds of a take and a release. A `helyx serve` that starts in that window waits for a server file and its handshake, and exits 1 after 5,000 ms. Slice 4 (#808) makes a second start try the lock again at each poll (decision 10).
- The read of the server file checks the type of the path, then opens it, as a second start does: a FIFO put in place between the two blocks the open. Only the owner of the data folder can make it. Open, ticket #777.
- The bytes bound of an outbound frame (decision 13) has no test at its size or one over: a frame of 1,611,661,312 bytes is more memory than a test may take on a machine that other worktrees share. The test of the client reads a `queue_dropped` of 64 plain texts of 4 MiB, 268,458,462 bytes, and a frame of 26,214,401 bytes; the join that checks the bound is the one of the inbound bound, which the server tests at 26,214,400 bytes and over it (`web_socket_test.exs`). The value bound has tests at 38,797,312 and one over (`frame_test.exs`).
- A frame at the outbound bounds takes the client up to about 1.5 GiB for the joined bytes, and a heap of about 1 GiB for a decode at the value bound (decision 13): about the memory of the same frame in the server, which holds its term and encodes it whole.
- Slice 2: the client checks each frame against the frame bounds and the schema, not the counts that the server keeps: a page of 256 items, a replay of 1,024 events, a `queue_dropped` of 64 messages, an `ask` request of 65,536 bytes. A frame that breaks them reaches the owner within the frame bounds. A tail snapshot has no count bound of its own: the newest group alone can pass `tail`.
- Slice 2: the decode checks each event alone, and a snapshot with the fold. An event that the fold cannot apply to its state, such as the result of a call that is not open, crashes the fold, as a bug of Core does (`Helyx.TUI.ViewModel.apply/2`).
- Slice 2: an `ask` of the `question` tool whose request the tool did not make crashes `Helyx.TUI.Question`, as in the node: the tool makes its request from the arguments that it checked (`docs/features/question-tool.md`), `Helyx.Tool.ask/1` checks only that the request is a JSON object of valid UTF-8 within its size, and the client checks only that it is a JSON object.
- Slice 2: a block of a kind that protocol 3 does not have ends the connection, as the strict check refuses it (decision 14); the tolerant reader of wire-protocol.md shows a placeholder for it, and a server of protocol 3 sends none.
- Slice 2: a server that reads each WebSocket frame of a large request just within the send timeout makes the write of the request up to 5,000 ms for each frame: 34 frames for a request of 25 MiB. The requests behind it wait in the writer and get `{:error, :timeout}` at their deadlines.
- #821: the worst JSON form of the text bound meets the slow-client policy of the server. A steer of 4 MiB of `\u0001` makes events of about 24 MiB of JSON each; a client that reads them late, by about one second on a loaded machine, passes the outbound queue of the server, 64 MiB, and the server closes it with 4408, which the client gives to the owner (`link_test.exs`). A plain text of 4 MiB with a pause of 3,000 ms passed.
- #821, open (review round 3, reproduced with a fake server that breaks the contract): the `unsubscribe` of a late `subscribe` reply is not held to the 16 request frames of the writer queue. A server that replies to timed-out `subscribe` requests before it reads them, while the writer waits, made 31 request frames wait (Codex: 32). A server of protocol 3 replies only after it reads a request. The fix, an unsubscribe that waits for a free place, is a second finding on the bound of the writer queue and is past the review limit of #821.
- #821, open (review round 3): with `-kernel inet_backend socket`, `:inet.getfd/1` fails and `Connection.open/1` raises in the start of the writer. `helyx` does not set that flag. A fix: `Wire.connect/4` asks for `inet_backend: :inet`.
- #821: a close frame that the server did not send before it reset the connection is lost. The server resets the connection when it closes with bytes of the client that it did not read, such as a request in flight, and its kernel drops what it did not send; the client then ends with no code.
- #821: the deadline of a request counts the frames that the server sends before its reply. After a steer of 4 MiB of `\u0001`, each event of its turn is about 24 MiB of JSON, and on a loaded machine (a precommit run) the follow-up got `{:error, :timeout}`; the follow-up ran, and the connection stayed open.
- Slice 2: the client does not check the `seq` order of the events of a subscription (O4): the fold has no `seq` guard until slice 4 (decision 11). An event of a type that the client does not know is dropped and not acked; a server of protocol 3 sends none.

- Slice 3: the TUI over the wire shows the tail of the snapshot, the newest 200 messages of the default tail of the wire (`docs/features/wire-protocol.md`, "Join, pages, and replay"); decision 7 has no `history` request, so the older messages of a long session do not show. In the node the TUI shows the whole transcript.
- Slice 3: when the old session ends during a switch that fails, the answer of the switch Task can come before the `session_end` of the old sub, from another process. The node checks the session with `Session.pid/1` and starts a new session in its place; over the wire no call tells, and the `session_end` that comes later ends the TUI with `the session stopped`.
- Slice 3: a switch over the wire stops the session that it leaves, so another TUI on the same session ends with `the session stopped`.
- Slice 3: each quit leaves its session running, and `/new` stops only the session that it leaves, so the sessions of a server grow to its cap of 64 (`too_many_sessions`) until the server stops; no request of the TUI stops a session at the quit. Open, ticket #822.
- Slice 3: a request whose Task the TUI ends keeps its place among the 16 requests that wait for a reply (slice 2, "late ones too") until the server replies: Escape on the `/resume` list while the server does not answer, and the quit during a switch. Sixteen of them make each later request `too many requests wait`; a server that answers frees the place at once.
- Slice 3: a switch that the server refuses shows a fixed text for each known reason (`too many sessions on the server`, `the server could not open the session`, and the others of `Helyx.TUI.Switch`), and `the session did not open` for any other, so the notice holds no term; in the node too, so the reason of a failed tool check of a `/new` does not show.
- Slice 3: the lock test of the attach needs perl, so with no perl on the PATH `helyx` prints the line of the lock test, not the tool error of a start in the node.
- Slice 3: an error of a start or a resume that the wire has no code for, such as a session that another process has open, comes as `start_failed` with the text of the server (`Helyx.Transport.WebSocket.Ops`), not as the sentence of the node.
- Slice 3: a session that `attach/2` opened stays in the server when the TUI then does not start (no terminal); in the node `CodingAgent.run/1` aborts it and stops Core.

## Out of scope

- Other clients.
- A server on another machine: the client reads the server file of a local data folder. An SSH tunnel or a TLS proxy serves other clients (serve.md, decision 6).
