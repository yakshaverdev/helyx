# Session lifecycle

## Goal

The Core turn contract: how a session starts, runs, and ends a turn with its provider process, and the wait before the next turn. The provider protocol (requests, actions, replies) is in `docs/features/one-provider-path.md`. The harness programs are in `docs/features/long-lived-harness.md`.

## Owners

- `Helyx.Session.Server.TurnLoop` owns the lifecycle. It matches each input (a client call or a message) to the current activity: `:idle`, a `%Turn{}`, or a `%Wait{}`. A lifecycle message of a turn, a wait, or a provider process that is no longer current is dropped there. Any other message crashes the session. `Helyx.Session.Server` drops a stream event or a tool result of a turn that is not current. A tool request of a turn that is not current gets the answer `aborted`.
- `Helyx.Session.Server.Wait` owns the turn end (`Wait.finish/2`) and the wait after it.
- `Helyx.Session.Server.Records` is the only writer of the transcript and the session file. `Records.finish/2` closes the records of a turn.
- `Helyx.Session.Server.Steering` is the only writer of the steer state (`Helyx.Session.Queue`).
- `Helyx.Session.Server.Events` is the only writer of `seq` and the subscribers.
- The provider process (`Helyx.Session.ProviderProcess`) is a Task of the hands. `init/3`, `request/3`, and `info/2` run only there. Core calls `id/0` when it registers the plugin, and the hands run `release/3` in their own Tasks under the release deadline. The provider process keeps no turn state.

## Turn states

A turn has a `phase` (`Helyx.Session.Turn`). The line between `preparing` and `submitting` is the send of `{:turn, ...}`, not its answer. A context request (`{:need_context, turn_id}`) of a `submitted` turn runs a prepare Task (`Turn.prepare`) until the session answers it. The phase stays `submitted`, so a steer goes to the provider process.

| Phase | From | To | A steer |
| --- | --- | --- | --- |
| `preparing` | the turn starts: `turn_start`, the connect, and the prepare Task | `submitting`, when the provider process is ready and the context is prepared | stays in the local queue. At the send it joins the transcript and the end of the context as a user message: it is part of the prompt |
| `submitting` | `{:turn, ...}` or `{:compact, ...}` sent | `submitted` at the answer `:ok` | stays in the local queue. At `:ok` the session sends the local steers, in order |
| `submitted` | the answer `:ok` | the end of the turn | goes to the provider process with a new `steer_id` |

- A turn that the provider starts by itself (`{:event, id, :turn_start}`) opens a `submitted` turn with no user message, and `turn_start` has `%{origin: :provider}`. It opens only with no turn, no wait, and a ready provider process. At any other time the session drops it and its events.
- A failed prepare Task in `preparing` fails the turn. A failed context build of a context request in `submitted` goes to the provider as `{:error, reason}` (`docs/features/one-provider-path.md`, C3).
- With `Helyx.Provider.Loop`, an assistant message with no tool calls ends the turn, unless the loop holds a steer (`docs/features/one-provider-path.md`).
- An answer other than `:ok` to `{:turn, ...}` stops the provider process (`ProviderRequest.stop_after/2`). Its `provider_down` fails the turn. The same holds for `{:compact, ...}`, except `:unsupported`, which runs the summary path of the Compaction plugin. That path ends the turn `done`, with a notice when no summary is made, or `error` when the plugin returns an error or the summary fails (`docs/features/harness-compaction.md`, `docs/features/summary-compaction.md`).

## Message close

The session owns the boundary of the assistant message. It closes the open message at a `message_end` event, at the first `tool_result` of one of its calls (stop `:tool_use`, usage `%{}`), at a taken steer, and at the turn end. A Helyx tool request does not close it: more calls of the same message can still arrive. A result for no open call is dropped.

## Turn end

Every end of a turn runs one path, `Wait.finish/2`, with an outcome: `{:done, stop_reason, usage}` (the terminal of the provider), `:aborted` (`Session.abort/1`), or `{:error, reason}` (a failure). In order:

1. The session kills the prepare Task of the turn, if one runs.
2. `Records.finish/2` closes the records.
   - At `done` an assistant message always joins with the provider's stop reason and usage: the open one, or an empty one when none is open.
   - At an abort or a failure, an open message with a tool call joins with the stop reason `:tool_use` and usage `%{}`. An open message with text only joins with the stop reason `:aborted` or `:error`, and its `message_end` has `:aborted` or the error text in `error`. An open message with no block gets its `message_end` and is not stored.
   - Then each open tool call (`Transcript.open_calls/1`) gets an `aborted` error result. No message goes between a call and its result.
3. The steers end (`Steering.end_turn/3`). At `done` a steer with no answer stays in the ledger as `{:ended, turn_id}`, and its late answer alone decides what happens to it. An abort or a failure empties both queues (`Queue.abort/1`, the one owner of this rule): a steer with no answer gets its notice, and one `queue_dropped` event gives the queued texts back to the client, steers first, before `turn_end`. The background ends stay, and hold: they wake no turn until the next turn that is not a compaction opens (`docs/features/background-bash.md`).
4. Each open Helyx tool request of the turn gets `aborted` (`ToolRuns.end_turn/2`), while the provider process lives. No answer is awaited.
5. `turn_end` goes out, here or, while a Helyx tool call of the turn runs, after step 6, with `%{outcome: :done}`, `%{outcome: :aborted}`, or `%{outcome: :error, error: text}`, where `text` is the error text that Core writes from the reason, valid UTF-8 of at most 4000 bytes (`Helyx.Reason.text/1`, ADR 0006 §2). The same function writes the text of a tool that crashes, raises, throws, or exits (`Helyx.Session.Hands`) and the sentence of a start error with no clause of its own in the coding agent (`CodingAgent.error_text/1`). A string reason passes as it is, up to the cut: it is plugin text, so a stack that a plugin formats into a string stays. Any other reason is first cleaned by one walk: every stacktrace in it, at any depth inside a tuple, a list, a map key or value, or a struct (an exception too), becomes the atom `:stacktrace`, whatever wrapper holds it. A stacktrace is a list, or the rest of a list, whose first element is a stack frame: `{module, fun, arity_or_args, location}` with two atoms, an integer arity or an argument list, and a list location, or `{fun, args, location}`. A list of other 4-tuples stays, and so does a frame that is not in a list. An integer of more than 100 digits becomes the marker of `Helyx.Message.cap_integers/1`, because `inspect` of a huge integer takes seconds. No boundary caps the integers of a reason before the walk, so the walk is the cap: for a turn error, for the value that a tool raises, throws, or exits with, and for a start error of the coding agent. Revision of 2026-10-16: removed capability, the caps at the `:DOWN` of a provider process in `Helyx.Session.Hands`, at the error terminal of a provider (`Helyx.Session.Stream.check/1`), and at the crash of a prepare Task (`TurnLoop`), which replaced a whole struct that held a huge integer by the marker. The walk replaces only the integer field, so the text keeps the other fields of the struct. The walk visits at most 10,000 terms (`@max_nodes`); past the bound, the rest of each open term becomes `:cut`, so no part that the walk did not see reaches the text. A struct that the walk enters keeps its `__struct__` and `__exception__` pairs when the walk cuts it, and they cost no visit; a struct that the walk reaches with no visit left becomes `:cut`. The text comes from the cleaned reason. An exception gives its message. Every client shows this text of a failed turn and makes no text of its own (#746): the print mode line is `the turn failed: <text>` (`CodingAgent.Print`), and the TUI error cell is `error: <text>` (`Helyx.TUI.ViewModel`). A provider gives an error with a text for the user as an exception whose message is the provider id and that text, `<id>: <text>`; its other fields, such as the subtype of a program result, are in the reason for the log only. The harness providers do this at the error result of a turn (`Helyx.HarnessIO.Error`, `docs/features/long-lived-harness.md`, "Errors"). Every other provider error, one with no text too, keeps its term, which shows as `inspect` output: the OpenAI errors and the Codex error answers to a request are such terms. A crash, `{error, :stacktrace}` bare, under any atom tag such as `:task_exit` or `:provider_stop`, or as the exit of a call `{reason, {GenServer, :call, args}}`, gives the message of the error that `Exception.normalize/3` makes, which is shorter than the term. This unwrap is not a safety step: the cleaning keeps the stacktraces out. An exit signal `{:EXIT, from, reason}` is not unwrapped: no process of the provider path traps exits, and the term shows as `inspect` output. A provider error whose second element is the atom `:stacktrace` reads as a crash, accepted. Core calls the `message/1` of the exception itself: a plugin `message/1` that raises, throws, exits, or gives no string makes the name of the exception. Any other reason shows as `inspect` output of at most 50 items, and a binary in it shows at most 4000 characters of its source, at most 16000 bytes of text, so a large term makes at most about 800 KB of text before the cut. Core inspects with `safe: false` in a catch of every class: a plugin `Inspect` that raises or exits makes the plain term with no struct implementation. Two Elixir fallbacks turn the raise of plugin code into text with the stack of that raise: a safe `inspect` (the `#Inspect.Error<...>` form, for a plugin `Inspect` that raises) and `Exception.message/1` (for a `message/1` that raises). The message of an Elixir error such as `MatchError` or `KeyError` runs a safe `inspect` of its term, and a plugin exception or a plugin `Inspect` can call either fallback. Core does not scan the text for such a stack: a label is not a reliable test, and a valid message can hold the text `Stacktrace:` (#633). A message and an `inspect` output keep their text up to the cut. A string that plugin code put into the reason is plugin text, as a string reason is: a stack in it stays. The message of an exception has no bound before the cut. The log gets the reason with its stacktraces, not cleaned, with the integer cap of `Helyx.Message.cap_integers/1`, as `inspect` output of at most 50 items with strings of at most 160 characters, built to about the 8096 bytes at which the Logger formatter cuts a line by default (`truncate`). That is about 8.5 KB of ASCII text; the limit counts characters and does not cut an atom, so 4-byte characters make at most about 32 KB and long atoms about 51 KB. The text and the log line have a bound. The work of the text has the bound of the walk. Measured on 2026-10-12: a reason that holds a map of a million items takes about 130 ms, most of it the garbage collection of the heap that holds the reason; a tuple of a million items takes 13 ms, and a list under 1 ms. The log line keeps a known ceiling: `inspect` walks a whole map before it applies the item limit, about 210 ms for a map of a million items. No real provider returns an error term of that size, and a handler for plugin output that breaks the contract needs evidence.
6. The hands get the cleanup request (`Hands.request_cancel/2`): always at an abort or a failure, and at `done` when a Helyx tool still runs. They kill the Tasks of the turn and release their handles.
   While a Helyx tool call of the turn runs (`ToolQueue.running` is not empty), `turn_end` of step 5 waits for the answer to this request, and goes out before the notice of a failed cleanup (#595). The hands handle their messages in order, so a start answer of a background run that they took before the request reaches the session first, and the run counts before `turn_end`. A turn with no running call gets `turn_end` at step 5, also at an abort or a failure. The release of the call delays `turn_end` too: the grace of a `bash` process group at an abort, up to the release deadline for a stuck release (`docs/features/tool-resource-release.md`). The run whose start answer came first lives: the call got `aborted`, and the end of the run joins a later turn (`docs/features/background-bash.md`). While `turn_end` waits, the snapshot shows the turn as running with no partial message, and the events of the wait come before it: a `queue_update`, such as the count of a start answer, and the `queue_dropped` of an abort in the wait. Hands that die in the wait, and a stop of the session in it, end the session with no `turn_end`: the client gets the end of the session, as at a stop in a turn.
7. Only an abort of a turn in `submitting` or `submitted` sends `{:interrupt, turn_id}`. It goes after the `aborted` answers of step 4, so the provider process gets them first.

## The wait

`Wait` holds the parts that must end before the next turn: `hands` (the cleanup answer) and `reply` (the answer to an interrupt or an idle close). A provider process that ends also holds the wait: it stays in `State.conn` with `ProviderConn.status` `:ending` until the hands' `provider_down`. A provider start with no answer of the hands yet holds the wait too: a turn that ends in `preparing` ends with an abort or a failure, so its cleanup request goes to the hands after the start, and the hands answer in order. So no idle session has a `conn` with no pid. `TurnLoop` ends the wait when no part is left and no provider process is `:ending`. Then the abort callers get `:ok`, a provider process of another model gets `:close`, and the queue starts the next turn (`Queue.drain/1`): every queued steer together, or with none the first follow-up. Each follow-up is a turn of its own, and each normal turn end starts one more while the queue holds a text. With no queued text, background ends that do not hold open a turn with no user message of its own; they join it at the send.

- While the wait lasts, the session starts no turn. A prompt and a follow-up queue as follow-ups, and a steer queues as a steer. So a new turn never runs tools beside a Task of the old turn.
- An interrupt answer `:ok` keeps the provider process. Any other answer, or its armed kill, stops it, and the wait lasts until its `provider_down`.
- A failed cleanup gives one `notice` with a fixed text. The abort still replies `:ok`.
- An abort in a wait gives the queued texts back in a `queue_dropped` event with a nil turn id, as the abort of a turn does, and its caller gets `:ok` at the end of the wait. An abort with no turn and no wait replies `:ok` at once.
- A resume id of the session's provider process for the turn that the wait ended is recorded as in a turn, with the turn id of that turn (#518). Both bundled providers send it while they handle `{:turn, ...}`, so after an abort it comes before the answer to the interrupt, in the wait. Only the process in `State.conn` with status `:ready` records it: the provider process sends its pid with the event. A resume id at any other time, or of another turn, is dropped. `Transcript.resumable/3` still decides at the next start whether the id is reused.

## Deadlines

Every request of the session to the provider process has a kill armed at the OTP timer server (`ProviderRequest.ask/3`). The loop cancels the kill when the provider replies, and sends the reply after the cancel. A blocked callback blocks the cancel too, so a blocked loop is killed at the bound, whatever the session and the hands do. The OTP timer fires at the bound or later, so a bound is the least wait, not an exact time.

- The connect kill is armed by the hands as the first act of the provider process, and the loop cancels it after `init/3`, before `{:provider_ready, pid}`. The wait for `:start` from the session is inside this bound.
- The prepare Task arms its own kill as its first act, before any plugin code, and cancels it before it sends the context.
- The timer can fire during the cancel, so a reply can still be followed by the kill. Then the `provider_down` decides the end, not the reply.

## Steer

The session gives each sent steer a `steer_id` and keeps it in the ledger of `Helyx.Session.Queue` until its `user_message` and its answer. Delivery is at most once.

| Answer to `{:steer, ...}` | Session |
| --- | --- |
| `:ok` | waits for `{:user_message, steer_id}` |
| `:rejected` | queues the steer for the next turn |
| `{:error, _}`, or the armed kill | the steer is unknown. It is never sent again |

- At `{:user_message, steer_id}` the open assistant message closes, each open call gets `aborted`, and the session appends its own text of the steer. An unknown or repeated id is dropped.
- A steer with `:ok` or an unknown answer and no `user_message` at the end of its turn gets a `steer_unconfirmed` event with its text. At `done` a late `:rejected` still queues it; at an abort or a failure it gets the event at once. A background end gets no event: it goes back to the ends (`docs/features/background-bash.md`).

## Provider death

The session monitors its provider process, and the hands send `{:provider_down, pid, reason}` after they release its handles. The two messages have no order between them. `reason` is `:provider_timeout` after an armed kill, the stop reason after an exit with `{:shutdown, reason}`, `{:task_exit, reason}` after any other exit, or `{:error, text}`, with the fixed text of `Helyx.Session.Hands.Release.error/1`, when the release left handles unconfirmed.

- The session holds its provider process in one place, `State.conn`. Its `status` is `:starting` until `{:provider_ready, pid}`, then `:ready`.
- The start is a request to the hands (`Hands.start_provider/3`), not a call: the hands can be busy with a release, so the session waits for their answer in its loop (#677). Until the answer `{:provider_start, ref, result}`, `conn` has the ref in `start` and no pid; the turn stays `preparing`, and the session takes client calls and an abort. An answer `{:error, text}` fails a turn with `text`; in a wait it only clears `conn`. With `{:ok, pid}`, in the turn or in the wait after it, the session monitors the process and sends it `:start`. So a turn that ends before the answer keeps the process, as one that ends after it does (#726). The process is `:starting` until its `{:provider_ready, pid}`. The next turn of its model takes it; after a model switch it closes (`close_switched/1`). The process waits for `:start` before `init/3`: `{:provider_ready, pid}` comes from the process and the answer from the hands, and two senders have no order. The process of a summary call (`docs/features/summary-compaction.md`) waits for `:start` too, but a call that ended before the answer stops its process at the answer: that process serves only its call.
- The process is `:ending` until its `provider_down`. Four events make it `:ending`: an answer to an interrupt or an idle close that stops it (`Wait.answered/3`), a stop by the session (`TurnLoop.stop_provider/2`), the `:close` of a model switch (`close_switched/1`), and its `:DOWN` outside a sent turn (`monitor_down/1`). In a sent turn, its `:DOWN` and an error answer to `{:turn, ...}` leave it `:ready`.
- Only `provider_down` takes the process out of `conn`. An `:ending` process holds the wait (`TurnLoop.progress/1`), and `TurnLoop.connect/1` never reuses it.
- Outside a turn, the `:DOWN` makes the process `:ending` and starts a wait, so the next turn waits for its `provider_down`.
- In a sent turn (`submitting` or later), the `provider_down` fails the turn with `reason`.
- In `preparing`, the `:DOWN` holds back `{:turn, ...}`. When the process was started by an earlier turn, its `provider_down` makes the turn connect a new one, once, and the queued steers stay for that turn: `Queue.provider_down/2` settles only the steer ledger. A process that this turn started fails the turn.
- At `provider_down` each sent steer with no notice gets `steer_unconfirmed`, except a background end, which goes back to the ends, and the ledger drops every entry of that process.
- Provider output outside the contract (a bad event, a context request outside `submitted` or while one is open (`TurnLoop.handle/2`), a message over a bound) stops the provider process with `{:shutdown, reason}` and fails the turn.

## Idle close

With a ready provider process and no turn and no wait, the session arms one idle timer (`provider_ms.idle`). Each arm has a new ref, and a timer message with an old ref, or during a turn or a wait, is dropped. When it fires, the session sends `:idle_close` with the close bound and waits. `:ok` ends the process, and the wait lasts until its `provider_down`. `:busy` keeps it, and the timer is armed again.

## Subscribers

`Helyx.Session.subscribe/1` returns `{:ok, snapshot, ref}`. The session adds the entry and takes the snapshot in one call, so every later event reaches the caller. `ref` is the caller's monitor of the session: its `:DOWN` ends the stream. The session monitors each subscriber and drops its entry at its `:DOWN`. The rules are in `docs/features/session-subscribers.md`.

## Session stop

`terminate/2` runs `Helyx.Session.Server.Stop.run/1` on the list of `TurnLoop.work/1`. In a turn, the prepare Task is killed, and the provider process ends with the hands. With no turn, the provider process gets `:close`, also when it is `:ending`, with its armed kill. Then the session stops the hands and waits for them, and deletes its background folder.

## Late calls

A client call of `Helyx.Session` with a timeout exits its caller at the timeout, but its message stays in the session's mailbox. A session that is busy past the timeout, in a slow file write for example, takes the message later, when no caller waits (#679).

- `call_pid/3` in `Helyx.Session` is the one path of every session call. A call with a timeout goes as `{:until, deadline_ms, request}`, where `deadline_ms` is the monotonic time in milliseconds at which the caller gives up. A call with `:infinity`, `abort/1`, has no deadline.
- `Helyx.Session.Server.Calls` takes the request only before its deadline. At or past it, the call does not act and gets no reply: a late `prompt` starts no turn, a late `steer`, `follow_up`, or `compact` queues nothing, a late `set_model` changes nothing, and a late `subscribe` adds no subscriber. No event goes out for it. A subscribe that times out still ends an earlier subscription of its caller: the caller cleans up after the timeout (`Helyx.Session.subscribe/1`). The session logs one `Logger.info` line with the op name, never the text.
- A timeout tells the caller that it does not know the result. A call that the session takes before its deadline acts, and its reply can come after the caller's timeout. A subscriber sees the result in the event stream.
- The deadline is a monotonic time of the caller's node. Every caller of the session API runs in the session's node. The wire transport of ADR 0008 also runs in that node.
- Core does not count the calls that wait in the mailbox. One caller process has at most one call in flight, but a caller that catches the timeout and calls again adds one more call for each call timeout. So the count grows with the time that the session stalls, and each call keeps its text of at most 4 MiB until the session takes it. An `abort/1` has no deadline: it waits until the session takes it, and then it acts. The TUI starts one abort for each Esc. The stall itself is out of scope (#677). The wire bounds its remote callers per connection (#660).

## Ownership

| Resource | Created by | Held by | Released on normal end | Released when the holder crashes | Released on abort |
| --- | --- | --- | --- | --- | --- |
| provider process | the hands (`Hands.start_provider/3`), a Task in `tasks` | hands, linked; the session monitors it | `:close` at the session end when no turn runs, or when no turn and no wait runs and its model is not the session's model (after a model switch; a switch away and back during a turn keeps it), or `:ok` to an idle close; then the hands release its handles | the link ends it with the hands; its end is a `:DOWN` and a `provider_down` | kept after an interrupt `:ok`; any other answer or the armed kill stops it. ## Current limits

- A cut with no block stores no message. The last stored assistant message is then an older one, so a later turn can resume an older provider session (`Transcript.resumable/3`).
- An abort with a tool call joins the message with the stop reason `:tool_use`, not `:aborted`. So `Transcript.resumable/3` still resumes the provider session, which may not keep that partial message.
- A stop reason that arrives while a steer waits is lost in two cases (#539). `Helyx.Provider.Loop` drops a `done` with no content while a steer is held, before the stream check, so nothing checks its stop reason and no message joins; a `done` after content keeps its stop reason in the `message_end` it sends. `Helyx.Provider.ClaudeCode` holds a `result` that comes while a steer is unresolved, and drops it when the steer starts; the session closes the open answer with `:end_turn`, or `:tool_use` when it has a tool call (`Records.take_steer/2`). In both cases a `:refused` or `:max_tokens` answer before the steer shows no stop line in the TUI. Accepted: the user already sent new input for the turn, so the missing line does not change the next step.
- An armed kill of a request of the old turn (a steer, a tool result, a context) can fire in the next turn and fail it. Only a provider that did not answer within its bound does that.
- A provider process of an earlier turn that ends after the context is prepared, before the session reads its `:DOWN`, ends in `submitting`, and the turn fails.
- At a session stop during a wait for an interrupt or an idle close answer, the armed kill of that request still runs beside the kill of the close. When it fires first, it kills the provider process before the close answers. The release still runs.
