# Session lifecycle

## Goal

The Core turn contract: how a session starts, runs, and ends a turn with its provider process, and the wait before the next turn. The provider protocol (requests, actions, replies) is in `docs/features/one-provider-path.md`. The harness programs are in `docs/features/long-lived-harness.md`.

## Owners

- `Helyx.Session.Server.TurnLoop` owns the lifecycle. It matches each input (a client call or a message) to the current activity: `:idle`, a `%Turn{}`, or a `%Wait{}`. A lifecycle message of a turn, a wait, or a provider process that is no longer current is dropped there. Any other message crashes the session. `Helyx.Session.Server` drops a stream event or a tool result of a turn that is not current. A tool request of a turn that is not current gets the answer `aborted`.
- `Helyx.Session.Server.Wait` owns the turn end (`Wait.finish/2`) and the wait after it.
- `Helyx.Session.Server.Records` is the only writer of the transcript and the session file. `Records.finish/2` closes the records of a turn.
- `Helyx.Session.Server.Steering` is the only writer of the steer state (`Helyx.Session.Queue`).
- `Helyx.Session.Server.Events` is the only writer of `seq` and the subscribers.
- The provider process (`Helyx.Session.ProviderProcess`) is a Task of the hands. `init/3`, `request/3`, and `info/2` run only there. Core calls `id/0` when it registers the plugin, and the hands run `release/3` in their own Tasks under the release deadline. The provider process keeps no turn state.

## Turn states

A turn has a `phase` (`Helyx.Session.Turn`). The line between `preparing` and `submitting` is the send of `{:turn, ...}`, not its answer. A context request (`{:need_context, turn_id}`) of a `submitted` turn runs a prepare Task (`Turn.prepare`) until the session answers it, and stays open until the provider replies to that `{:context, ...}` request (`Turn.pending`). The phase stays `submitted`, so a steer goes to the provider process.

| Phase | From | To | A steer |
| --- | --- | --- | --- |
| `preparing` | the turn starts: `turn_start`, the connect, and the prepare Task | `submitting`, when the provider process is ready and the context is prepared | stays in the local queue. At the send it joins the transcript and the end of the context as a user message: it is part of the prompt |
| `submitting` | `{:turn, ...}` or `{:compact, ...}` sent | `submitted` at the answer `:ok` | stays in the local queue. At `:ok` the session sends the local steers, in order |
| `submitted` | the answer `:ok` | the end of the turn | goes to the provider process with a new `steer_id` |

- A turn that the provider starts by itself (`{:event, id, :turn_start}`) opens a `submitted` turn with no user message, and `turn_start` has `%{origin: :provider}`. It opens only with no turn, no wait, and a ready provider process. At any other time the session drops it and its events.
- A failed prepare Task in `preparing` fails the turn. A failed context build of a context request in `submitted` goes to the provider as `{:error, reason}` (`docs/features/one-provider-path.md`, C3).
- With `Helyx.Provider.Loop`, an assistant message with no tool calls ends the turn, unless the loop holds a steer (`docs/features/one-provider-path.md`).
- An answer other than `:ok` to `{:turn, ...}` stops the provider process (`ProviderRequest.stop_after/2`). Its `provider_down` fails the turn. The same holds for `{:compact, ...}`, except `:unsupported`, which runs the summary path of the Compaction plugin. That path ends the turn `done`, with a notice when no summary is made, or `error` when the plugin returns an error or the summary fails (`docs/features/harness-compaction.md`, `docs/features/summary-compaction.md`).

## Message close

The session owns the boundary of the assistant message. It closes the open message at a `message_end` event, at the first `tool_result` of one of its calls (stop `:tool_use`, usage `%{}`), at a taken steer, and at the turn end. A Helyx tool request does not close it: more calls of the same message can still arrive. A result for no open call is dropped.

## Turn end

Every end of a turn runs one path, `Wait.finish/2`, with an outcome: `{:done, stop_reason, usage}` (the terminal of the provider), `:aborted` (`Session.abort/1`), or `{:error, reason}` (a failure). In order:

1. The session kills the prepare Task of the turn, if one runs.
2. `Records.finish/2` closes the records.
   - At `done` an assistant message always joins with the provider's stop reason and usage: the open one, or an empty one when none is open.
   - At an abort or a failure, an open message with a tool call joins with the stop reason `:tool_use` and usage `%{}`. An open message with text only joins with the stop reason `:aborted` or `:error`, and its `message_end` has `:aborted` or the error text in `error`. An open message with no block gets its `message_end` and is not stored.
   - Then each open tool call (`Transcript.open_calls/1`) gets an `aborted` error result. No message goes between a call and its result.
3. The steers end (`Steering.end_turn/3`). At `done` a steer with no answer stays in the ledger as `{:ended, turn_id}`, and its late answer alone decides what happens to it. An abort or a failure empties both queues (`Queue.abort/1`, the one owner of this rule): a steer with no answer gets its notice, and one `queue_dropped` event gives the queued texts back to the client, steers first, before `turn_end`. The background ends stay, and hold: they wake no turn until the next turn that is not a compaction opens (`docs/features/background-bash.md`).
4. Each open Helyx tool request of the turn gets `aborted` (`ToolRuns.end_turn/2`), while the provider process lives. No answer is awaited.
5. `turn_end` goes out, here or, while a Helyx tool call of the turn runs, after step 6, with `%{outcome: :done}`, `%{outcome: :aborted}`, or `%{outcome: :error, error: text}`, where `text` is the error text that Core writes from the reason, valid UTF-8 of at most 4000 bytes (`Helyx.Reason.text/1`, ADR 0006 §2). The same function writes the text of a tool that crashes, raises, throws, or exits (`Helyx.Session.Hands`) and the sentence of a start error with no clause of its own in the coding agent (`CodingAgent.error_text/1`). A string reason passes as it is, up to the cut: it is plugin text, so a stack that a plugin formats into a string stays. Any other reason is first cleaned by one walk: every stacktrace in it, at any depth inside a tuple, a list, a map key or value, or a struct (an exception too), becomes the atom `:stacktrace`, whatever wrapper holds it. A stacktrace is a list, or the rest of a list, whose first element is a stack frame: `{module, fun, arity_or_args, location}` with two atoms, an integer arity or an argument list, and a list location, or `{fun, args, location}`. A list of other 4-tuples stays, and so does a frame that is not in a list. An integer of more than 100 digits becomes the marker of `Helyx.Message.cap_integers/1`, because `inspect` of a huge integer takes seconds. No boundary caps the integers of a reason before the walk, so the walk is the cap: for a turn error, for the value that a tool raises, throws, or exits with, and for a start error of the coding agent. Revision of 2026-10-16: removed capability, the caps at the `:DOWN` of a provider process in `Helyx.Session.Hands`, at the error terminal of a provider (`Helyx.Session.Stream.check/1`), and at the crash of a prepare Task (`TurnLoop`), which replaced a whole struct that held a huge integer by the marker. The walk replaces only the integer field, so the text keeps the other fields of the struct. The walk visits at most 10,000 terms (`@max_nodes`); past the bound, the rest of each open term becomes `:cut`, so no part that the walk did not see reaches the text. A struct that the walk enters keeps its `__struct__` and `__exception__` pairs when the walk cuts it, and they cost no visit; a struct that the walk reaches with no visit left becomes `:cut`. The text comes from the cleaned reason. An exception gives its message, bare, under any atom tag such as `{:provider_stop, reason}` or `{:provider_init, reason}`, in `{:provider_error, kind, reason}` (the stop at an error answer, `Helyx.Session.ProviderRequest.stop_after/2`), or as the exit of a call, so the stop of a provider process with an exception shows its message too (#760). Another tuple of three, such as `{:failed_to_start_child, id, reason}`, is not unwrapped. Every client shows this text of a failed turn and makes no text of its own (#746): the print mode line is `the turn failed: <text>` (`CodingAgent.Print`), and the TUI error cell is `error: <text>` (`Helyx.TUI.ViewModel`). A provider gives an error with a text for the user as an exception whose message is the provider id and that text, `<id>: <text>`, the text cut at 2,000 bytes; its other fields, such as the subtype of a program result or the HTTP status, stay in the reason, and neither the text nor the log shows them (#756). The bundled providers do this with `Helyx.ProviderError` for every error that holds a text of the program or the server (#746, #760): the error result of a harness turn (`docs/features/long-lived-harness.md`, "Errors"), a Codex error answer to a request, a Claude Code error answer to `initialize` or to an interrupt, a failed compaction, and an OpenAI HTTP error body or the `message` of an `api_error` object (`kind: :api_error`; Helyx keeps no other field of the object, so a large object does not take all the visits of the walk before the message). A provider error with no text keeps its term, which shows as `inspect` output, such as `{:codex, "turn/start", ""}`, `{:http_status, 401, ""}`, or `{:missing_env, name}`. The start error of a harness program (`{:not_started, text}`, the text of the watchdog) keeps its term too. A crash, `{error, :stacktrace}` bare, under any atom tag such as `:task_exit` or `:provider_stop`, in `{:provider_error, kind, reason}`, or as the exit of a call `{reason, {GenServer, :call, args}}`, gives the message of the error that `Exception.normalize/3` makes, which is shorter than the term. This unwrap is not a safety step: the cleaning keeps the stacktraces out. An exit signal `{:EXIT, from, reason}` is not unwrapped: no process of the provider path traps exits, and the term shows as `inspect` output. A provider error whose second element is the atom `:stacktrace` reads as a crash, accepted. Core calls the `message/1` of the exception itself: a plugin `message/1` that raises, throws, exits, or gives no string makes the name of the exception. Any other reason shows as `inspect` output of at most 50 items, and a binary in it shows at most 4000 characters of its source, at most 16000 bytes of text, so a large term makes at most about 800 KB of text before the cut. Core inspects with `safe: false` in a catch of every class: a plugin `Inspect` that raises or exits makes the plain term with no struct implementation. Two Elixir fallbacks turn the raise of plugin code into text with the stack of that raise: a safe `inspect` (the `#Inspect.Error<...>` form, for a plugin `Inspect` that raises) and `Exception.message/1` (for a `message/1` that raises). The message of an Elixir error such as `MatchError` or `KeyError` runs a safe `inspect` of its term, and a plugin exception or a plugin `Inspect` can call either fallback. Core does not scan the text for such a stack: a label is not a reliable test, and a valid message can hold the text `Stacktrace:` (#633). A message and an `inspect` output keep their text up to the cut. A string that plugin code put into the reason is plugin text, as a string reason is: a stack in it stays. The message of an exception has no bound before the cut. The log gets the kind of the reason only, `turn failed: <kind>` ("Log and crash reports"). The text has a bound. The work of the text has the bound of the walk. Measured on 2026-10-12: a reason that holds a map of a million items takes about 130 ms, most of it the garbage collection of the heap that holds the reason; a tuple of a million items takes 13 ms, and a list under 1 ms. No real provider returns an error term of that size, and a handler for plugin output that breaks the contract needs evidence.
6. The hands get the cleanup request (`Hands.request_cancel/2`): always at an abort or a failure, and at `done` when a Helyx tool still runs. They kill the Tasks of the turn and release their handles.
   While a Helyx tool call of the turn runs (`ToolQueue.running` is not empty), `turn_end` of step 5 waits for the answer to this request, and goes out before the notice of a failed cleanup (#595). The hands handle their messages in order, so a start answer of a background run that they took before the request reaches the session first, and the run counts before `turn_end`. A turn with no running call gets `turn_end` at step 5, also at an abort or a failure. The release of the call delays `turn_end` too: the grace of a `bash` process group at an abort, up to the release deadline for a stuck release (`docs/features/tool-resource-release.md`). The run whose start answer came first lives: the call got `aborted`, and the end of the run joins a later turn (`docs/features/background-bash.md`). While `turn_end` waits, the snapshot shows the turn as running with no partial message, and the events of the wait come before it: a `queue_update`, such as the count of a start answer, and the `queue_dropped` of an abort in the wait. Hands that die in the wait, and a stop of the session in it, end the session with no `turn_end`: the client gets the end of the session, as at a stop in a turn.
7. Only an abort of a turn in `submitting` or `submitted` sends `{:interrupt, turn_id}`. It goes after the `aborted` answers of step 4, so the provider process gets them first.

## The wait

`Wait` holds the parts that must end before the next turn: `hands` (the cleanup answer) and `reply` (the answer to an interrupt or an idle close). A provider process that ends also holds the wait: it stays in `State.conn` with `ProviderConn.status` `:ending` until the hands' `provider_down`. A provider start with no answer of the hands yet holds the wait too: a turn that ends in `preparing` ends with an abort or a failure, so its cleanup request goes to the hands after the start, and the hands answer in order. So no idle session has a `conn` with no pid. `TurnLoop` ends the wait when no part is left and no provider process is `:ending`. Then the abort callers get `:ok`, a provider process of another model gets `:close`, and the queue starts the next turn (`Queue.drain/1`): every queued steer together, or with none the first follow-up. Each follow-up is a turn of its own, and each normal turn end starts one more while the queue holds a text. With no queued text, background ends that do not hold open a turn with no user message of its own; they join it at the send.

- While the wait lasts, the session starts no turn. A prompt and a follow-up queue as follow-ups, and a steer queues as a steer. So a new turn never runs tools beside a Task of the old turn.
- An interrupt answer `:ok` keeps the provider process. Any other answer, or its armed kill, stops it, and the wait lasts until its `provider_down`.
- A failed cleanup gives one `notice` with a fixed text. The abort still replies `:ok`.
- An abort in a wait gives the queued texts back in a `queue_dropped` event with a nil turn id, as the abort of a turn does, and its caller gets `:ok` at the end of the wait. An abort with no turn and no wait replies `:ok` at once.
- A resume id of the session's provider process for the turn that the wait ended is recorded as in a turn, with the turn id of that turn (#518). Both bundled providers send it while they handle `{:turn, ...}`, so after an abort it comes before the answer to the interrupt, in the wait. Only the process in `State.conn` with status `:ready` records it: the provider process sends its pid with the event. A resume id at any other time, or of another turn, is dropped. `Transcript.resumable/3` still decides at the next start whether the id is reused.

## Deadlines

Every request of the session to the provider process has a kill armed at the OTP timer server (`ProviderRequest.ask/3`). The loop cancels the kill when the provider replies, and sends the reply after the cancel. A blocked callback blocks the cancel too, so a blocked loop is killed at the bound, whatever the session and the hands do. The OTP timer fires at the bound or later, so a bound is the least wait, not an exact time.

- The connect kill is armed by the hands as the first act of the provider process, and the loop cancels it after `init/3`, before `{:provider_ready, pid}`. The wait for `:start` from the session is inside this bound.
- The prepare Task arms its own kill as its first act, before any plugin code, and cancels it before it sends the context.
- The timer can fire during the cancel, so a reply can still be followed by the kill. Then the `provider_down` decides the end, not the reply.

## Steer

The session gives each sent steer a `steer_id` and keeps it in the ledger of `Helyx.Session.Queue` until its `user_message` and its answer. Delivery is at most once.

| Answer to `{:steer, ...}` | Session |
| --- | --- |
| `:ok` | waits for `{:user_message, steer_id}` |
| `:rejected` | queues the steer for the next turn |
| `{:error, _}`, or the armed kill | the steer is unknown. It is never sent again |

- At `{:user_message, steer_id}` the open assistant message closes, each open call gets `aborted`, and the session appends its own text of the steer. An unknown or repeated id is dropped.
- A steer with `:ok` or an unknown answer and no `user_message` at the end of its turn gets a `steer_unconfirmed` event with its text. At `done` a late `:rejected` still queues it; at an abort or a failure it gets the event at once. A background end gets no event: it goes back to the ends (`docs/features/background-bash.md`).

## Provider death

The session monitors its provider process, and the hands send `{:provider_down, pid, reason}` after they release its handles. The two messages have no order between them. `reason` is `:provider_timeout` after an armed kill, the stop reason after an exit with `{:shutdown, reason}`, `{:task_exit, reason}` after any other exit, or `{:error, text}`, with the fixed text of `Helyx.Session.Hands.Release.error/1`, when the release left handles unconfirmed.

- The session holds its provider process in one place, `State.conn`. Its `status` is `:starting` until `{:provider_ready, pid}`, then `:ready`.
- The start is a request to the hands (`Hands.start_provider/3`), not a call: the hands can be busy with a release, so the session waits for their answer in its loop (#677). Until the answer `{:provider_start, ref, result}`, `conn` has the ref in `start` and no pid; the turn stays `preparing`, and the session takes client calls and an abort. An answer `{:error, text}` fails a turn with `text`; in a wait it only clears `conn`. With `{:ok, pid}`, in the turn or in the wait after it, the session monitors the process and sends it `:start`. So a turn that ends before the answer keeps the process, as one that ends after it does (#726). The process is `:starting` until its `{:provider_ready, pid}`. The next turn of its model takes it; after a model switch it closes (`close_switched/1`). The process waits for `:start` before `init/3`: `{:provider_ready, pid}` comes from the process and the answer from the hands, and two senders have no order. The process of a summary call (`docs/features/summary-compaction.md`) waits for `:start` too, but a call that ended before the answer stops its process at the answer: that process serves only its call.
- The process is `:ending` until its `provider_down`. Four events make it `:ending`: an answer to an interrupt or an idle close that stops it (`Wait.answered/3`), a stop by the session (`TurnLoop.stop_provider/2`), the `:close` of a model switch (`close_switched/1`), and its `:DOWN` outside a sent turn (`monitor_down/1`). In a sent turn, its `:DOWN` and an error answer to `{:turn, ...}` leave it `:ready`.
- Only `provider_down` takes the process out of `conn`. An `:ending` process holds the wait (`TurnLoop.progress/1`), and `TurnLoop.connect/1` never reuses it.
- Outside a turn, the `:DOWN` makes the process `:ending` and starts a wait, so the next turn waits for its `provider_down`.
- In a sent turn (`submitting` or later), the `provider_down` fails the turn with `reason`.
- In `preparing`, the `:DOWN` holds back `{:turn, ...}`. When the process was started by an earlier turn, its `provider_down` makes the turn connect a new one, once, and the queued steers stay for that turn: `Queue.provider_down/2` settles only the steer ledger. A process that this turn started fails the turn.
- At `provider_down` each sent steer with no notice gets `steer_unconfirmed`, except a background end, which goes back to the ends, and the ledger drops every entry of that process.
- Provider output outside the contract (a bad event, a context request outside `submitted` or while one is open (`TurnLoop.handle/2`), a message over a bound) stops the provider process with `{:shutdown, reason}` and fails the turn.

## Idle close

With a ready provider process and no turn and no wait, the session arms one idle timer (`provider_ms.idle`). Each arm has a new ref, and a timer message with an old ref, or during a turn or a wait, is dropped. When it fires, the session sends `:idle_close` with the close bound and waits. `:ok` ends the process, and the wait lasts until its `provider_down`. `:busy` keeps it, and the timer is armed again.

## Subscribers

`Helyx.Session.subscribe/1` returns `{:ok, snapshot, ref}`. The session adds the entry and takes the snapshot in one call, so every later event reaches the caller. `ref` is the caller's monitor of the session: its `:DOWN` ends the stream. The session monitors each subscriber and drops its entry at its `:DOWN`. The rules are in `docs/features/session-subscribers.md`.

## Session stop

`terminate/2` runs `Helyx.Session.Server.Stop.run/1` on the list of `TurnLoop.work/1`. In a turn, the prepare Task is killed, and the provider process ends with the hands. With no turn, the provider process gets `:close`, also when it is `:ending`, with its armed kill. Then the session stops the hands (`Helyx.Session.Hands.stop/3`) and waits for them, and deletes its background folder.

- The stop of the hands kills every Task that still runs, the provider process of a turn and a background run too, and releases their handles with `:cancel`, as an abort does (`docs/features/tool-resource-release.md`, rule 10). Its answer is every handle that a release of the hands left unconfirmed: at a delivery, at an abort, or at this stop.
- The stop report (#752). `Helyx.Sessions.stop/1` returns `:ok` only when every handle of the session was released, and `{:error, {:not_released, handles}}` when a release failed or timed out. `handles` is the list of the handles still held, the terms of the plugins that hold them, or `:unknown` when the stop got no answer of the hands: hands that did not answer within the bound of their stop and were killed, or a session that another end, such as a second stop or a Core stop, stopped first, also during the abort of the stop. `{:error, :session_not_found}` means that no session ran at the call. The stop has no time parameter and no retry: its bounds are those of the row "session stop" in "Bounds". A stop by another path, such as `GenServer.stop/3` or a Core stop, runs the same releases, and its report goes to no caller; the log names the handles.
- A child session of the agent tool counts: its owner stops it with `Helyx.Sessions.stop/1`, and the release of the parent keeps the child held when the report of the child is not `:ok` (`docs/features/agent-tool.md`, "The stop report of the child"). `Helyx.Sessions.stop/1` also takes the pid of a session process, and then acts on that process only.
- The wire op `stop` keeps its answer `{}` after the session ended, also with handles that are not released: the wire does not carry them (`docs/features/wire-protocol.md`).
- A child process that left its process group (for example with `setsid`) can survive any stop; a caller that must be certain runs Helyx in a container or a cgroup.

## Late calls

A client call of `Helyx.Session` with a timeout exits its caller at the timeout, but its message stays in the session's mailbox. A session that is busy past the timeout, in a slow file write for example, takes the message later, when no caller waits (#679).

- `call_pid/3` in `Helyx.Session` is the one path of every session call. A call with a timeout goes as `{:until, deadline_ms, request}`, where `deadline_ms` is the monotonic time in milliseconds at which the caller gives up. A call with `:infinity`, `abort/1` and the `:stop` call of `Helyx.Sessions.stop/1`, has no deadline.
- `Helyx.Session.Server.Calls` takes the request only before its deadline. At or past it, the call does not act and gets no reply: a late `prompt` starts no turn, a late `steer`, `follow_up`, or `compact` queues nothing, a late `set_model` changes nothing, and a late `subscribe` adds no subscriber. No event goes out for it. A subscribe that times out still ends an earlier subscription of its caller: the caller cleans up after the timeout (`Helyx.Session.subscribe/1`). The session logs one `Logger.info` line with the op name, never the text.
- A timeout tells the caller that it does not know the result. A call that the session takes before its deadline acts, and its reply can come after the caller's timeout. A subscriber sees the result in the event stream.
- The deadline is a monotonic time of the caller's node. Every caller of the session API runs in the session's node. The wire transport of ADR 0008 also runs in that node.
- Core does not count the calls that wait in the mailbox. One caller process has at most one call in flight, but a caller that catches the timeout and calls again adds one more call for each call timeout. So the count grows with the time that the session stalls, and each call keeps its text of at most 4 MiB until the session takes it. An `abort/1` has no deadline: it waits until the session takes it, and then it acts. The TUI starts one abort for each Esc. The stall itself is out of scope (#677). The wire bounds its remote callers per connection (#660).

## Log and crash reports

The log lines that Core writes in a session hold no message text: no prompt, reply, thinking, tool call, tool result, or error text of a provider or a tool (#756). The crash reports of its three GenServers hold none (#756), and neither does the log of a crash of a process that Core starts for plugin code (#788). The holes are in the "Out of scope" item. A client reads the text in its events, such as the `error` of `turn_end` ("Turn end", step 5). The log lines are those of the session process (`Helyx.Session.Server`), its hands (`Helyx.Session.Hands`) with their tool Tasks, its sync worker (`Helyx.Session.Sync`), its prepare Task, and its provider process.

- **A plugin term in a log line.** `Helyx.Reason.log/2` writes `<label>: <kind>` and nothing else of the term. The kind of a struct, an exception too, is its module name; the kind of an atom is the atom; the kind of a tuple is the kind of its first element; any other term, a string too, has the kind `term`. So `{:task_exit, {%RuntimeError{}, stack}}` logs `:task_exit`, and a `Helyx.ProviderError` logs `Helyx.ProviderError`. Every log line of a plugin term in a session goes through it: a failed turn (`turn failed`), a tool that raises, throws, exits, crashes, or returns a value outside its contract, and a memory recall or sync that fails. The handles that a release did not confirm keep their term (`Helyx.Reason.log_term/2`): a handle names a resource, such as a process group or a child session, and an operator needs it to free the resource (`docs/features/tool-resource-release.md`). The kind is one atom in `inspect` form, so the line has a bound, and its work is one step for each level of first elements. The other log lines of a session hold a fixed text, a count, a tool or op name, a file error of the session file, or the exit reason of the lock port.
- **A crash report.** The session process, the hands, and the sync worker implement `format_status/1` with `Helyx.Reason.crash_status/1`: the report shows the state and the last message as `:redacted`, an empty debug log, and the reason as its kind; `:sys.get_status/1` shows the state as `:redacted` too. A `FunctionClauseError` or a failed BIF keeps the arguments of the call in its stack frame, such as the message and the state of a callback, and Logger prints them. So every callback of the three runs in `Helyx.Reason.no_args/1`, but the `init/1` of the hands and of the sync worker, which set a flag and a monitor only. `no_args/1` lets a raise, a throw, or an exit go on with the arguments of each frame replaced by their count. The exit reason that links and monitors get keeps its term: a client gets it in the end signal (`docs/features/end-signal.md`), and the hands, which trap exits, end with it and write no report.
- **A crash of a process of plugin code** (#788). Core starts these processes for plugin code in a session: the prepare Task (the ModelContext and the Compaction plugin), a recall call and a sync call of the Memory plugin, a release Task of a tool, and the provider process. The crash report of `Task` prints the exception, its message, the stack, and the arguments of a stack frame. So each of them runs its body in `Helyx.Reason.task/2`, where Core starts it, and a plugin needs no change. A raise, a throw, or an exit of the body that `Task` reports logs `<label>: <kind>` as an error in place of the crash report. The labels are `prepare task crashed`, `memory recall crashed`, `memory sync crashed`, `tool release crashed`, and `provider process crashed`; the kind is that of "A plugin term in a log line", and a throw has the kind `:nocatch`. Then `task/2` turns off the log of this process only (`Logger.put_process_level(self(), :none)`), and the crash goes on with its class and its reason, with the arguments of each stack frame replaced by their count. So `Task` handles the crash as it handles any crash, and the process ends with the exit reason of a Task crash. The report of `Task` is not logged. The level filter of Logger drops it, and it runs after the translator of Logger; for the hole of a `message/1` that throws or exits, see "Out of scope". The exit reason is `{error, stack}` for a raise, `{{:nocatch, value}, stack}` for a throw, and the reason of an exit. Each link and monitor gets the reason of the original crash, and the consumers do not change. The stack of the reason has two more frames, those of `task/2` and `no_args/1`. A client reads the message of a prepare or provider crash in the `error` of `turn_end` ("Turn end", step 5), and a failed recall or sync logs its kind. `task/2` turns on the trap of exits as the first act of the crash handling, and never turns it off. So a linked process that ends while the crash is handled gives a message, which the process never reads, and the reason stays that of the crash (`test/helyx/data/reason_crash_test.exs`). The history is in `docs/reviews/2026-10-19-788-task-reports.md`. A linked process that ends between the crash and the trap still sets the reason, as in a bare Task; an exit signal `kill` cannot be trapped, so the kill at a deadline (`:timer.kill_after/1`) still ends the process with `:killed`. An exit with `:normal`, `:shutdown`, or `{:shutdown, term}` goes on with no line: `Task` does not report it. A Task has no proc_lib crash report: `Task.Supervised` starts it with `spawn_link/3`, not with `proc_lib`. A SASL-domain event of a process at the level `:none` is dropped too (probe of 2026-10-19). The loop of the provider process ends with `{:shutdown, reason}` (L1 in `docs/features/one-provider-path.md`), which `Task` does not report. A tool Task catches every raise, throw, and exit of its tool (`Helyx.Session.Hands.Run`). The model Task of `Helyx.Provider.Loop` catches every raise, throw, and exit of its model call. Each makes the crash its result, so neither runs in `task/2`.
- **Out of scope** (accepted). With the SASL reports on (`handle_sasl_reports: true` in the Logger config), the proc_lib crash report of a session GenServer and the supervisor report hold the exit reason as it is and the message queue. The supervisor of a crashed Task logs its report in its own process, so the level of the Task does not drop it: the report holds the exception and its message. The exit reason that links and monitors get keeps its term, the message of an exception too: Core makes the text of a client from it, and a process that a plugin links to the provider process gets it. A process that a plugin starts itself, such as the owner of a port or a Task of its own, writes its own crash report. The wire transport is not a session process: it logs a start error with its term (`Helyx.Reason.log_term/2`). A plugin that sets the level of its process to `:none` before the crash also drops the kind line, as it dropped the report of `Task` before #788. Logger's translator runs before the level filter, in the crashed process, and it runs plugin code: the `message/1` of an exception and the `Inspect` of a term in the reason. Accepted (orchestrator decision of 2026-10-19, option C): a plugin exception whose `message/1` throws or exits crashes the translator. `:logger` removes the translator from the node and passes the event on, untranslated and with no other filter, so the raw report of `Task`, with the fields of the exception, can reach the handlers; with no translator, the supervisor reports of the node reach them too. Reason: such an exception breaks the contract of a plugin, and a contract break gets the generic answer; a handler for the case needs evidence that a real plugin does it (AGENTS.md). Master had the same hole for every bare Task. A `message/1` that raises another exception does not crash the translator: it rescues the raise, and the level filter drops the event (`test/helyx/data/reason_crash_test.exs`). Open, with no decision (round 5 of the review of #788): an `Inspect` of a term in the reason that throws or exits, such as `exit(%Helyx.Test.ExitInspect{})`, crashes the translator in the same way; and a `message/1` that raises its own exception makes `Exception.message/1` recurse with no end, so the process grows until a kill ends it, and, with its trap on, it does not end at an abort or at the end of its owner. A bare Task recurses too, but it ends with its owner.
- **Replaced mechanism.** Before #756, `Helyx.Reason.log/2` wrote the term: its stacktraces, the integer cap, at most 50 items, strings of at most 160 characters. That writer is now `Helyx.Reason.log_term/2`, with the same bounds, for the handles and the wire start error (`test/helyx/data/reason_test.exs`). The other lines lose the term: the log no longer shows the stack of a tool that raises, throws, or exits, the integer marker of a thrown value, the message of a provider crash, or the subtype of a program result (#746 kept it in the log; it stays in the `kind` field of `Helyx.ProviderError`, which no output shows). Before #788, a Task of plugin code and the provider process wrote the crash report of `Task`, with the exception, the stack, and the arguments of a stack frame, and a release Task also with its handles, its mode, and its deadline. The log now shows `<label>: <kind>` and no stack. No test read that report. The tests of the old lines now check the kind (`hands_test.exs`, `stream_events_test.exs`, `provider_process_test.exs`, `claude_code/turn_test.exs`). A crash report showed the state, the last message, the reason, and the arguments of a stack frame; it now shows none of them. A reader of the log who needs the text reads the event stream or the session file.

## Current limits

- A cut with no block stores no message. The last stored assistant message is then an older one, so a later turn can resume an older provider session (`Transcript.resumable/3`).
- An abort with a tool call joins the message with the stop reason `:tool_use`, not `:aborted`. So `Transcript.resumable/3` still resumes the provider session, which may not keep that partial message.
- A stop reason that arrives while a steer waits is lost in two cases (#539). `Helyx.Provider.Loop` drops a `done` with no content while a steer is held, before the stream check, so nothing checks its stop reason and no message joins; a `done` after content keeps its stop reason in the `message_end` it sends. `Helyx.Provider.ClaudeCode` holds a `result` that comes while a steer is unresolved, and drops it when the steer starts; the session closes the open answer with `:end_turn`, or `:tool_use` when it has a tool call (`Records.take_steer/2`). In both cases a `:refused` or `:max_tokens` answer before the steer shows no stop line in the TUI. Accepted: the user already sent new input for the turn, so the missing line does not change the next step.
- An armed kill of a request of the old turn (a steer, a tool result, a context) can fire in the next turn and fail it. Only a provider that did not answer within its bound does that.
- A provider process of an earlier turn that ends after the context is prepared, before the session reads its `:DOWN`, ends in `submitting`, and the turn fails.
- At a session stop during a wait for an interrupt or an idle close answer, the armed kill of that request still runs beside the kill of the close. When it fires first, it kills the provider process before the close answers. The release still runs.
