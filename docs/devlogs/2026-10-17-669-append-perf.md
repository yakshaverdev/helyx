# 2026-10-17: the cost of append and file append in long sessions (#669)

Done:

## Where a batch goes

Probes at 30,000 messages, not in the bench, made with probe scripts that are not in the repository, built on an earlier version of the bench script. That version did not check the outcome of a batch or the persistence mode, and the probe outputs are only in this devlog. The `:tprof` probe ran with 1 KiB results and persistence on.

- `:tprof` call time on the session process, over 5 batches of 1 x 8 calls: `erlang:send/2` 54.9 % (225 calls, 714 us each under trace), `gen_server:loop/5` and `decode_msg/4` 26.7 %, `erlang:'++'/2` 9.7 % (125 calls), and `lists:reverse/2` 6.3 % (215 calls). The file code is under 0.1 %.
- A send trace of the session process over one batch, with `:erts_debug.flat_size/1` of each message. In a 1-round batch, 4 sends hold the whole transcript, about 1.83 M words each. One is the `:turn` request to the provider process (`turn_loop.ex:262`), and one is the `:context` request (`prepare.ex:115`). The other 2 are 5-tuples that start with the session pid, to a process that was gone when the tracer read it: the start of the prepare Task, whose function holds `state.transcript` (`prepare.ex:35` and `:51`). A 4-round batch has 4 `:context` requests (7.34 M words). All the other sends together are about 4,000 words in a 1-round batch and 13,700 in a 4-round batch.

Thus the cost of a batch grows with its provider rounds. At each provider round of a tool loop, the session builds the context again. The start of the prepare Task copies the whole transcript into the Task. The Task sends the built context back, and the session sends it to the provider process.

From the 1-round and 4-round batches, each extra round with its 9 messages costs 50 to 106 ms at 30,000 messages, and 11 to 27 ms at 9,999. The costs that the ticket names are at most about 2.5 ms per message at 30,000: append at most 0.81 ms, `open_calls/1` at most 1.3 ms, and file append at most 0.34 ms. That is at most about 27 ms of a 1-round batch (89 to 146 ms) and at most about 93 ms of a 4-round batch (243 to 419 ms). The profile gives `++` and `reverse` 16 % of the session time.

Persistence: at 999 messages, a batch of 1 KiB results with persistence on costs 0.1 to 0.2 ms more for each message than with it off, which agrees with the file append part. With 64 KiB results the difference is 0.006 to 0.47 ms for each message. At 9,999 and 30,000 messages, the difference is about as large as the spread between runs of one mode, so these runs do not show it.

Under heavy load the file append costs more. A review agent ran the bench and a probe while 20 `yes` processes of another session kept the load average over 100. It reported that one append took 2 to 20 ms, still flat in the file size, and that a 4 x 8 batch at 30,000 messages took 1,273 ms with persistence on and 612 ms with it off. The bench numbers above are not from that state.

## Decision

Step 2 of the ticket makes no change:

- `transcript ++ [message]`: at most 0.81 ms at 30,000 messages. A reversed list would add a reverse at each read of the transcript, and the context of each round reads all of it.
- `Transcript.open_calls/1`: at most 1.3 ms at 30,000 messages.
- `File.write/3` with `[:append]` for each entry: 0.06 to 0.34 ms in all runs, flat in the file size. A session-owned append handle would change the write-failure path (the handle has a state to lose) for no gain that the numbers show.

The dominant cost is the full context of each provider round. A fix changes the context request of `Helyx.Provider.Loop` (ADR 0002) or the prepare Task, whose kill bounds the plugin time (`docs/features/session-lifecycle.md`). That is not the smallest change of step 2, so it needs a ticket of its own. The copy into the prepare Task is the first one to remove. A Compaction plugin cuts only the built context: after a summary of `Helyx.Compaction.Summary`, the sends to the provider get small (`summary.ex:95`), but the Task start still copies the whole transcript at each round.

Assumptions (owner away):

- The bench is in `plugins/bundled/bench/`, next to `view_model.exs`, not in a root `bench/`: the batch needs `Helyx.Provider.Fake`, which the root project cannot see.
- A batch runs with no ModelContext or Compaction plugin. A product with `Helyx.ModelContext.Default` also runs plugin code over the whole transcript at each round, so the per-round cost is at least what the bench shows.
- "Persistence off" is the state after a real write failure, because a resumed session with no file has no API.
- The heap of a part is the words that its result keeps, because `garbage_collection_info` gives the sizes of the heap blocks, not the used words.
- The timing ran on this machine, not on the precommit host.

What broke:

- The first heap metric read `total_heap_size` before and after a part. It gave 0.0 KiB for the append, which allocates 469 KiB at 30,000 messages. `heap_size` in `garbage_collection_info` is also a block size. The bench now uses `:erts_debug.size_shared/1`.
- `:erts_debug.size/1` (written in Erlang) made two runs take 166 and 185 s (their outputs were not kept). `size_shared/1` (a BIF) takes about 2 ms on the transcript of 30,000 messages.
- `:tprof` is in the `tools` application, which `mix run` does not load. The probe called `Mix.ensure_application!(:tools)` first.
- 20 `yes` processes of another session loaded the machine from about 20:25 to 20:40. One run of the bench in that window did not end in 200 s. The three runs above came after it.
- Bench and probe runs that did not end left 5 `helyx_bench_*` folders, 123 MiB, in the temp folder. They are still there. The bench now deletes its folder in an `after` block, and each size runs in a worker that is not linked, so that a crash of the worker does not stop the `after` block. A probe with a crash in `run/2` showed that the folder was deleted.

- The first `HELYX_SLOW=1 .claude/skills/ship/precommit.sh` run failed in `apps/coding_agent` at `nice mix dialyzer --no-compile`: `the app file at "_build/test/lib/helyx_plugins/ebin/helyx_plugins.app" is invalid` and `** (Mix) Can't continue due to errors on dependencies`. The parallel `mix test` step of the same project was compiling `helyx_plugins` after the fast-forward to new master commits. The second run passed: 705, 80, and 871 tests with 0 failures, Credo with no issues, and Dialyzer with 0 errors in each project.
