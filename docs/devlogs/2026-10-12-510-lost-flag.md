# 2026-10-12: the lost flag on a reused provider process (#510)

## What was done

- `resumed` moved from `Helyx.Session.Turn` to `Helyx.Session.Server.ProviderConn`. `connect/1` of `TurnLoop` sets it when it starts the provider process. `Records.resume_id/3` reads it to compute `lost`, and clears it, so only the first resume id after the start can say "lost".
- The stream event `{:resume, id, cut}` is now `{:resume_id, id, cut}`, and the client event `:provider_session` is now `:resume_id`, in `Helyx.Provider`, `Helyx.Event`, Core, the Claude Code and Codex providers, the TUI, and the feature docs. The names on disk (`harness_session`, `harness_session_id`) stay, as `lib/helyx/session/file.ex` documents.
- Test: the test provider has a model `lost_label` whose `init/3` waits for a message and then has lost its resume id. The test aborts the turn while `init/3` waits, prompts again on the same process, and gets `lost: true`. On master it got `lost: false`.

## What broke

Nothing.

## Open

- A `resume_id` event of a turn that was aborted after `{:turn, ...}` went out is dropped, because it arrives in the `Wait` (`lib/helyx/session/server.ex`, the stream event catch-all). The user then sees no "lost" notice, and the next session resume asks for the lost id again. Master has the same defect. It needs a decision on the turn id of an event after `turn_end` and on the transcript length that the resume id stores. Ticket: #518. See `docs/reviews/2026-10-12-510-lost-flag.md`.
