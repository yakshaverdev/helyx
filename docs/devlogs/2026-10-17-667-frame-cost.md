# 2026-10-17: the frame cost during a long reply (#667)

## What was done

- `plugins/bundled/bench/view_model.exs` now also times the frames of a growing reply: 200 text deltas of 150 bytes, a paragraph break after every fourth, a reply of 30,100 bytes in a fixed 100x40 viewport. A delta frame folds one delta and draws the transcript (`Transcript.screen/3` and `widget/1`), as the TUI does for each event; a spinner frame draws it with no change, as for a busy tick (50 frames). Each line gives p50 and p95 of the time and of the reductions, and the words that the garbage collector reclaimed over the frames, per frame. The sizes are arguments (`mix run bench/view_model.exs 100000`), so each size is one run that ends in under 60 s on a loaded machine.
- `Transcript.screen/3` with no position (the view that follows the newest output) walks the cells from the newest and stops at the screen. Each item that it shows is wrapped once; before, `bottom/3` wrapped the items of the last screen and `rows_from/3` wrapped them again, and the open message is one of them. A frame no longer builds the list of all items. A scrolled view is as before.
- A run of information lines is one cell of the view model, `{:infos, texts}`: `ViewModel` joins a line to an information cell before it. So a cell is an item, the item count is the array size, and the walk reads the array by index. The rule that joined the run was in `Transcript.items/1` before.
- `/resume` reads the session list in a Task (`SessionList.new/3`). The list shows `reading the sessions of this folder` until the answer comes, and only Escape acts then.

## Machine and method

Apple M4, 10 cores, 16 GiB, Elixir 1.19.5 on OTP 28. This is not the precommit host. Other worktrees ran tests at the same time. A first set of runs saw load averages from 50 to 171, with several `yes` processes of another session at about 40 % CPU each; those times are not used. The numbers below are from one interleaved set, master and the change one after the other, three runs of each size, at load averages from 15.2 to 18.0. Each number is the median of the three runs. The longest run took 11.4 s. The reductions and the allocation do not depend on the load. The time does.

The two costs on master were the second wrap of the open message (half of every frame at all sizes) and, at 100,000 cells, the list of all items: its reductions were about 0.6 M of 2.5 M, but its time was most of the frame, because the list stays live while the wrap allocates, so each collection copies it. With the change, the reductions and the allocation of a frame are the same at every size. The p95 of a delta frame at 100,000 cells (20.5 ms) is still above the others; the reductions are not, so it is the collection of the larger heap. The one static frame of the old bench is one sample right after the folds: 3.8 and 5.2 ms at 999 cells, 38.7 and 41.0 ms at 99,999 cells, about the same on both.

An earlier version of the change counted the items in a fold of all cells on each frame, because a run of information cells was one item but several cells. At 100,000 cells that fold cost about 0.33 M reductions per frame, and the rule that joins a run was in three places. The cell shape above removed both.

## `/resume`

A probe made a folder of 300 session files and timed `Scan.list/2`, 5 times in each of 3 runs, at load averages from 5.8 to 6.3. Medians of the run medians:

| head of each file | time |
| ----------------- | ---: |
| a small header and a user message, in a file of 200 KB | 41 ms |
| a header line of 65,400 bytes | 60 ms |
| a small header, then 5,100 short lines that are no message | 342 ms |

Each is more than one frame of 16.7 ms, so the scan left the event handler, as the ticket comment says.

## Assumptions

- One frame is 16.7 ms (60 Hz). The TUI has no frame rate of its own; even its busy tick of 100 ms is under the worst case of the scan.
- No cache: the one wrap of the open message per frame stays. It is now the largest cost: about 0.95 M reductions and 16 MiB of allocation per spinner frame at a reply of 30,100 bytes, that is, it grows with the reply. A memo of the rows of the settled lines of the open message would remove it, but it needs a width key, a place in the TUI state (a render cannot keep one), and a rule for a fence that a later line closes. The ticket prefers a change of the order or the shape.
- A scrolled view still folds all cells into a list on each frame, as on master. The ticket names the frames of a long reply, which follow the newest output; with a cell as an item, the scrolled view could read the array by index too.
- The list scan Task stops when the list closes (`SessionList.close/1`), so an open and close does not leave a scan running. At quit it is not stopped: it reads at most 256 heads, but its stats of the folder have no bound.
- A crash of the list scan leaves the list at `reading the sessions of this folder` until Escape: ExRatatui traps exits, so the TUI stays. `tui.ex` is at its 400 lines, and a clause for the `:DOWN` would add lines. `Scan.list/2` returns no error and raises only on a bug.
- The bench gives the allocation as a mean per frame, from the collector counter of the node, and not as p50 and p95: a count for each frame needs a forced collection after each frame, which would change the times. The reductions give the spread.
- `read_branch_after_turn/2` became an `if` in the event clause, and a comment of `layout/2` got wider lines, so that the clause for the answer of the scan keeps `tui.ex` at 400 lines.

## What broke

- One run of `mix test test/helyx/tui` at a load average over 100 had one failure, whose text was not kept. The next two runs of the same files passed.
