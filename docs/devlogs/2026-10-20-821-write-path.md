# 2026-10-20: the wire connection reads while it writes (#821)

- Traced the cause: with the write in `Helyx.TUI.Wire.Connection`, a steer of 4 MiB of `\u0001` and then a follow-up left the client and the Bandit process of the server both in `prim_inet:send/4`, until a send timeout ended the connection.
- Fixed it in the mechanism: a linked writer process encodes and sends every frame in order; the connection reads while a frame goes out. At most one pong waits for the writer (round 1). Decision 15 of `docs/features/tui-attach.md` states the rule.
- Tests: the acceptance test in `link_test.exs` (slow), the pong rule, the end of the writer, and a write past the send timeout in `connection_test.exs`.
- Broke: the first precommit run, on the loaded host: the follow-up got a timeout, as its deadline counts the events that the server sends before the reply. Now an accepted hole; the test takes both answers.
- Broke again: the second precommit run. A client that reads a steer of 4 MiB of `\u0001` about one second late passes the 64 MiB outbound queue of the server, which closes it with 4408, and a failed write can show that close as nil. Not committed.
- Orchestrator decision: a plain 4 MiB text is the acceptance; the worst form meets the 4408 of the server (accepted hole, tested). The writer reports a failed send, and the connection reads what the socket holds.
- Found: `gen_tcp` drops the unread bytes at a failed send (both backends), the kernel keeps them. So the writer (`Helyx.TUI.Wire.Writer`) sends on its own `:socket` descriptor, and `Reader.held/3` reads the close code after a failure. The queue: 16 request frames, one batch of the latest pong and acks.
- Round 3 (authorized): the close code holds in every probe. Open: the `unsubscribe` of a late `subscribe` reply passes the 16 (up to 32, a server that breaks the contract), and the writer needs the `inet` backend.
